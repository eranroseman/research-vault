# Import terminology: industry vocabulary for the K1-K8 concepts — evidence

- **Date:** 2026-09-04
- **Method:** as the note records below (its own method section is unchanged)
- **Spec:** 2026-09-06-import-redesign-design.md
- **Binds:** nothing — evidence the spec was built from and absorbed; the spec is the current state, this file is not

Research note, 2026-09-04. Industry-terminology evidence for the import redesign glossary.

**What this is.** A survey of the terms four bodies of practice use for eight concepts the vault needs to name during the import redesign. Every row quotes a primary source verbatim and records where the quote sits, which of the eight concepts it touches, and what the term means elsewhere.

**What consumes it.** The 2026-09-04 import brainstorm and the import redesign spec. The glossary in `CONTEXT.md` currently defines Admission, Import, Screening state, Citekey and Item with working labels; those working labels are reproduced below as given, not as adopted terms.

**The concepts.** The vault is a private git repository of markdown notes fed from a local Zotero library; an LLM agent operates it.

- K1: The whole process of getting a source from outside the vault into the vault (working label: import).
- K2: The human decision that a source is accepted into the library (working label: admission).
- K3: The act of creating the library record in Zotero, whether by a human or by an agent on the human's instruction (working label: admission / add / save).
- K4: The deterministic copy of a record's metadata, attachments, annotations, and derived text into the vault, with provenance (working label: capture).
- K5: The LLM step that turns a captured source into wiki pages: summary page, concept-page updates (working label: digest).
- K6: Detecting that the library-side record changed, vanished, or was re-keyed after capture, and refreshing the vault copy (working labels: drift check, refresh, sync).
- K7: The stable identifier the vault uses for a source across its life (working labels: citekey, item key, identity).
- K8: A source that was accepted but later excluded, superseded, or removed, with the record kept (working labels: screening state, tombstone).

**Nothing here is a decision.** The tables carry no ranking and no recommendation. A working label appearing in a collision column records where a field already uses that word; it does not settle whether the vault keeps the label.

**Conventions.** The verbatim definition column reproduces source text unchanged, including its punctuation. Authored text (the standardness note column, the collisions column, the collisions and gaps sections) is the note's own wording. Where a source uses a vertical bar inside a quote, it is escaped for the table. Field labels name the body of practice and, in parentheses, the source family.

## Gaps

Every one of K1 through K8 has at least one primary-source term in at least one field, so no concept is unnamed everywhere. The gaps below are per field, and per facet of a concept where a field's term covers only part of it.

### Fields with no term for a concept

- K2 (human acceptance decision): no term in reference managers (the decision is folded into the 'save' click, a 'Keep' checkbox, or an 'Add to project' button; none is a named state or event); no term in OAIS (acceptance is modelled once in the Submission Agreement, and 'appraisal' and 'accession' have zero hits in M-3); no term in data engineering (membership is a configuration-time include/exclude filter). 'admission' occurs once across all sources, in the llmwikis.org MATM agent-memory context, not for bibliographic sources.
- K3 (creating the library record): no term in evidence synthesis (records are retrieved from databases and bulk-imported; the singular act of authoring a record is not named; JBI allows records that never enter the reference manager at all); no separate term in LLM-wiki sources (dropping the file into raw/ is the record, so K3 collapses into K4; 'source record' in llmwikis is vault-side metadata); no term in PREMIS's own glossary (the 'accession' event lives only in the LOC vocabulary).
- K5 (LLM step to wiki pages): no term in digital preservation (Derived AIP, DIP, Descriptive Information and Derivation Relationship are structural neighbours, none names authored synthesis); no term in reference managers (Zotero 'Reports' renders metadata and notes, which is K4 output); no term in evidence synthesis that separates it from K4 (data collection, extraction and charting all describe judgement-laden reading; 'synthesis' and 'summary of evidence' operate on charted data; the field's name for any LLM step is 'automation tools'). Only the LLM-wiki sources name it ('compile'), and none of them uses 'digest' for it.
- K6 (producer-side drift): no field names the case where the source system's record changed, vanished or was re-keyed while the archive's copy stayed the same. Preservation 'fixity' checks the archive's own copy; OAIS 'Refreshment' is a media copy; reference-manager 'sync' is a bidirectional merge; Cochrane 'update' is a new edition and its IV.4.1 passage on corrections and retractions has no single term; PRISMA-S notes in one sentence that 'Citations already in the database may also be updated' and attaches no term; PRISMA's updated-review flow diagram has no box for a previously included study that changed or vanished. Data engineering 'change data capture' covers all three cases in a push model; the polling analogue, Sqoop 'incremental import', cannot see deletes or re-keys. hermes 'drift' and nvk 'refresh' check upstream URLs, not a library record. The Zotero local API supplies most of the mechanism (object versions, Server ID, `GET /deleted?since=`, `includeTrashed`) without a user-facing name.
- K7 (a report-level stable identifier): evidence synthesis keys identity at the study, links reports by registry numbers, and has no requirement that a report carry a stable key; DOI is the only report-level persistent identifier its glossaries define, and grey literature has none. LLM-wiki sources use the filename or slug as identity and none contains 'citekey' or 'item key'. The llmwikis 'identity' preflight means attribution, not an identifier.
- K8 ('accepted then later excluded, superseded, or removed, with the record kept'): evidence synthesis has no term; its excluded-studies tables cover near-misses never included, 'superseded' has no equivalent (a newer report is linked to the study rather than retiring the older one), and the accepted-then-removed case appears only as Cochrane IV.4.1 guidance with the removal reported. Reference managers have only Trash (time-limited, reversible, expiring) and EndNote's Retractions group. Both data-engineering 'tombstone' senses exist so that data can eventually be removed. 'screening state' occurs in no source. Preservation's PREMIS 'deaccession' (inventory) versus 'deletion' (storage) split is the one standard vocabulary that separates status change from removal.

### Working labels found in no primary source with the vault's meaning

- 'import' for a post-admission projection (K4): every field places import before any decision.
- 'admission' for source acceptance: one occurrence, in a different context.
- 'capture' for the deterministic copy with provenance: used in that sense only by hermes-agent; PREMIS, SAA and Debezium each use it for something else.
- 'digest' for the LLM synthesis step: no occurrence; the dominant sense in both LLM-wiki and data-engineering sources is a hash.
- 'sync' for a one-way refresh of a derived copy: Paperpile and Mendeley do use 'sync' for one-way derived files, but every vendor's primary sense is bidirectional merge.
- 'identity' for a stable key: the one occurrence means attribution.
- 'screening state' as a lifetime status: no occurrence; 'screening' is a phase in every evidence-synthesis source.
- 'tombstone' for a kept record: no occurrence outside data engineering, where the marker's purpose is eventual removal.
