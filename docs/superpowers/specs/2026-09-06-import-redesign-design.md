## 0. Purpose and boundary

Ingest is the process that gets a source from outside the vault into the vault. It is the last of three garbage-in gates (setup, lint, ingest). This spec covers the whole ingest path and the setup and lint machinery ingest depends on. It follows one priority order throughout: adopt an existing component as-is, else adapt one, else build. Capture and its linter are mechanical and built here; the compile step is adopted.

Chosen scope (2026-09-04):

- Source classes: scholarly and grey-literature documents, meaning anything Zotero can hold as an item with a file or DOI (papers, preprints, standards, reports, books, theses). Web pages, repositories, and product documentation are deferred — **and the deferral is mechanical, not stated**. Measured 2026-09-07: 138 of 1,455 top-level items are URL-shaped classes and **130 carry no attachment at all**, so Zotero holds no text for them. Capture writes their note and reports the text checks **SKIPPED — does not apply**, filing no finding: a source class this iteration does not handle is not a capture failure, and 130 unclearable findings would drain nothing (ADR 0002). Acquisition is lane 2's, below.
- Post-capture events covered: identity changes, removal, and content drift. Substrate absence (Zotero not running, a clone with no Zotero, CI with no Zotero) is deferred, so a live Zotero at every mechanical check is assumed.
- Trigger: capture on demand; a drift check at every mechanical chokepoint. Nothing writes the vault unattended.
- Greenfield: no existing vault content must survive. The repository holds no literature notes (decomposition §15.16), so §1.1's frontmatter-key migration runs over zero files today and carries risk only if notes exist when the plan runs. **Stated to the operator, 2026-09-13 (Part A Task 19):** on a vault that does hold older notes, `capture --all` after the rename rewrites each note whole from Zotero, so prose an older note carried does not survive and acknowledgments made against it lapse (their scope moves from the old fixity hash to `managed-sha256`); the setup skill says so before the person runs it.
- Derived full text lives in the vault as a gitignored cache, regenerable from Zotero.
- Screening decisions belong to a review, not to the source. The hand-edited note status is retired.

Terms in this document are the terms proposed in §1.1. Each is traced to `2026-09-06-import-redesign-terminology-evidence.md` beside this spec, either to a primary source or, where the note records that no field names the concept, to that gap: **ingest** (the whole process), **selection** (the human decision), **add** (creating the Zotero item), **capture** (the deterministic copy into the vault), **compile** (the LLM step), **drift** and **refresh** (change detection and re-copy), **item key** and **citation key** (identity and name). The brainstorm's working labels were import, admission, capture, and digest; §1.1 records why each stays or goes.

Invariants (**chosen 2026-09-07**):

1. Identity is assigned exactly once, at capture, and never reused.
2. Every provenance tuple carries the Zotero server id. Versions and keys are meaningful only within one server id.
3. No transition deletes a note. Records deprecate; they do not vanish.
4. Every transition is visible: a finding in the review queue or a line in the log. `added` is the one exemption, and §1's table says so.
5. The linter runs at capture, at verify, and at pre-commit, through one code path. **The pre-commit leg is held**, and the hold has a stated trigger rather than being an omission: the hook runs `verify --offline` today and this linter needs a live Zotero, so §6 prices the hook going online. Measured 2026-09-07, the quality lane had been red for twelve days unread and `main` carries no branch protection — adding a non-blocking signal to a channel with a demonstrated history of being ignored buys nothing. **Capture and verify bind now; pre-commit binds when the write-side gate is settled — the decomposition's §15.20, which records that `main` has no branch protection and no rulesets and that no `pre-commit` hook exists in this checkout; lane 1's plan reports its finding and the author settles it.** Reported 2026-09-13 at Part A's close (merge `f2d3921`): no protection, no rulesets, no hook, measured again; the decision is tracked as **#130**.
6. Every mechanical step must be **falsifiable** — by a linter, by a test, by four-state honesty, or by a design in which the failure cannot occur. A linter is one instrument, not the requirement.

Invariant 6 is a reframing of the 2026-09-04 draft's *"a mechanical step without a named linter is incomplete"*, and the change is deliberate. Read literally, the original requires a checker for every step, which is a rule that manufactures mechanisms — the opposite direction from this repository's own ladder. The evidence is local and recent: the disposition system was 2,033 lines of exactly that instinct, a linter guarding a marker, and deleting it lost nothing because the purge eliminated the problem the marker managed. What survives is the part worth keeping — no mechanical step gets to be unverifiable — without prescribing the instrument.

The reframing has a consequence worth naming. Under the original, §3.5's propagation linter existed because the invariant demanded one. Under invariant 6 it must earn itself by naming what would otherwise be unfalsifiable, which for a vault-wide rewrite of human-authored content it can: after a pass, no citation-key-bearing surface may still name a key the rename log maps away, and nothing else in the vault can attest that.

**The full-map read is a requirement, not a cost.** The 2026-09-04 draft framed three reads as a price worth paying; measurement makes them the only correct route. `?since=` cannot substitute, because a window returns only what changed and a key that vanished appears in neither the window nor the trash. The full-text map is worse still: measured 2026-09-07, **449 of 1,367 entries sit at version 0**, and `?since=1` returns 918 of them with none at version 0 — so a third of this library's indexed attachments are unreachable by any incremental sweep. Zotero's local API charges nothing for the full read: it *"does not impose a default or maximum limit"* and *"does not currently apply rate limiting"*, and `/fulltext?since=0` returned all 1,367 entries in one 29 KB response.

Cost: a whole-vault classification is three reads, not two, and §9 records each. The two versions maps answer current, drifted, trashed and deleted: `/items?since=0&format=versions` for every key including children and annotations, and `items/trash?format=versions` for the trashed set. `/items/top` would hide every child, so the first read is `/items`. Those two maps cannot answer re-keyed or merged, because a key-to-version map carries neither the live citation key nor `dc:replaces`, so a third read of `/items/top?format=json` supplies both fields. Top-level scope is right there, since only top-level items carry either. Refresh fetches are needed only for a note that classified as drifted.

## 2. Selection and adding to Zotero

Selection is the human act, recorded where it is made: the review's selection log, or an ad hoc request. The keystrokes that add the item are not the decision, so the agent may perform them. Capture runs on the returned keys at once, so adding and capture are one conversation. Record creation by the person — browser connector, drag-in, add by identifier — stays valid and reaches capture the same way.

**The write path is Path A, the documented local API write** (`POST /api/local/authorize` for a key, then ordinary write requests). Zotero's own documentation settles it, not a balance of costs: authorize is *the* documented mechanism for local writes, returning `{"key": "<32-character key>", "remember": <bool>}` from a dialog offering *"Allow"*, *"Always Allow"* and *"Deny"*, with keys that *"can't be created in advance"*. Its cost is that the caller supplies Zotero item JSON, so the vault owns a small metadata mapping it otherwise never touches. The authorize endpoint is rate-limited to five dialog-producing requests a minute. `Zotero-Write-Token` is supported but *"cached in memory, so they're forgotten when Zotero restarts"*.

**`Zotero-Server-ID` is required on writes and optional on reads** — 428 without it, 412 on mismatch (§9). A wrong id is refused **before any key is presented**, so writing to the wrong Zotero is not a hazard this design guards against with a rule; the server refuses it unauthenticated. **The guard holds only for a client that sends the id it recorded**, as §5 requires. A client that reads the live header and echoes it back passes against any instance — the obvious lazy implementation, and it defeats the mechanism entirely. `research_vault/zotero.py` sends no id at all today, so this is a fork the plan takes deliberately.

**What the attended trial established (2026-09-07).** **Always Allow** returned a 32-character key with `remember: true`, persisted to the profile's `localAPIKeys.json` under the caller's `appName`; that one key then carried `POST /collections`, `POST /items`, a trashing `PATCH` and a `DELETE`, all successful, with no re-authorization. **The caller names the collection**, so where an item lands is unambiguous. And one detail that is a step in the plan: **Better BibTeX assigns the citation key, but not in time to ride the create response.** The body carries `citationKey: null`, and the key was present when the item was re-read six seconds later — Better BibTeX fills keys after `fillKeyAfter`, two seconds by default. So §3.3's capture cannot read the key off the create response; it re-reads the returned item keys, polling until `citationKey` is non-null or a ten-second ceiling passes, then reports the item unkeyed rather than writing a note without one. The measured fill was two seconds by preference and six in practice, so the ceiling is a bound, not an expectation. Asserting the convenient version would have shipped a capture step that intermittently wrote a note with no citation key.

**Undo does not cover this, by construction.** Zotero 10 supports undo *"for modifications to existing objects — creating or permanently deleting an object isn't undoable (trashing is, since it just sets the object's `deleted` flag)"*, and the `undoAction` label that makes a change undoable is a **plugin API** parameter on `saveTx`, unavailable to an HTTP caller.

**Path B, the connector server, is dropped.** It is what browser extensions use: `POST /connector/import` runs Zotero's own import translator over an RIS, BibTeX or CSL JSON body, so the vault would never build Zotero item JSON — the whole attraction. It was retained for a case where a translator does work no mapping of ours could, which is real but hypothetical and has never arisen. Against that: **no consent dialog guards it**, so anything on the machine can write to the library; its session id cannot be reused; the attachment endpoint wants a numeric item id, not the item key this design uses; and the save target is whatever the Zotero window has selected. Zotero 10 also now drops browser-like requests *"without a response"*, which says who the path is for. Dropping it also deletes a question that existed only because it did — where a connector save lands. If the translator case arrives it returns as a sourcing question with a named need, the treatment §3.8 and §4.1 gave everything else.

**Tags are carried verbatim; normalise-at-read is dropped.** Lane 0 measured 2,673 tags in 280 near-duplicate clusters, and the tempting fix is to canonicalise them as the note renders. That would create a second tag vocabulary known only to this repository — the two-copies-to-reconcile shape this design keeps eliminating, and a contradiction of "Zotero is the source of truth". Lane 2 fixes the clusters where they live, at rest. Capture copies what it reads.

**No citation-key pinning.** Under item-key identity a later key change is a rename, not a lost address.

**The URL-only cut.** A source that is cited, or plausibly will be, goes into Zotero — a URL-only source included, rather than through parallel machinery of the vault's own. **There is no second category**: a source either enters through Zotero and the whole process, or it is not in the vault, and consulting something in a session creates no vault record to rule about. The asymmetry decides the first half: a wrong save costs a junk item the attachment scanner already cleans, a wrong skip costs an unrecoverable dead link. The claim that a URL-only entry gains nothing from Zotero is right about organisation and wrong about identity — a cited URL needs a bibliography entry with an access date, and Zotero with Better BibTeX is the only thing here that mints one.

**What that retires, with its cost.** The vault's own link-rot machinery goes: `research_vault/archive.py`, `lint_web_archive`, verify's `_archive_outcomes`, and the `archive-url` field (§3.2). It was a **second writer** into a record §3.2 declares capture alone owns, and Zotero has fields for both an archive URL and an access date. **The snapshot carries `accessDate` and not `archive`** (§3.2's list is closed). **Measured 2026-09-07, the two halves are not equally strong**: `accessDate` is non-empty on 379 of 398 sampled bibliographic items, while `archive` is non-empty on 0 and `archiveLocation` on 1. The access date rides along; the archive URL is a field Zotero offers and this library does not populate, so retiring `archive-url` gives up a capability the vault was exercising and Zotero is not. The cost is real and unreplaced: **automated snapshotting leaves this design**, and nothing takes over. If link rot proves to bite, it returns as a sourcing question — an archiving tool or a Zotero plugin — not a second writer into the vault's frontmatter.

## 3. Capture

### 3.1 Identity and name

The vault's identity for a source is the Zotero item key qualified by the Zotero server id. Item keys are assigned by Zotero, are not user-editable, are unique within a library, and survive metadata edits and citation-key changes. The citation key is the source's name: it names the file and appears in prose citations and the CSL file. A citation-key change is a rename of a thing whose identity did not change, so propagation is mechanical.

This answers the two objections the author raised against making the citation key the identity: that a third party can change it, since Better BibTeX regenerates keys from metadata, and that its uniqueness is not guaranteed, since a suffix freed by a deletion can be handed to a different source later. Neither holds for the item key, which Zotero assigns, does not expose for editing, and does not reuse within a database. A freed suffix (`chen2025a` reused for a different source) is detected because the item key differs from the one recorded under that name.

Filename (chosen): `literatures/<citation key>.md`. The title is carried in frontmatter and in `aliases`, so Obsidian resolves `[[Title]]` to the literature note. The tool's per-source page at `wiki/sources/<title>.md` is the second file that could answer that link; **which file Obsidian picks is unprobed, and the documentation suggests an exact filename match precedes an alias match** — if so the tool's page wins and this note does not. The plan probes it before anything rests on the answer as well as `[[citation key]]`. The file renames only on a re-key, and **the propagation task set performs it** along with the citations and wikilinks that name the old key — capture does not, because a drifted-only note is never revisited for a name change.

### 3.2 Record home (chosen: both, one writer)

Two files carry bibliographic data, and the capture verb is the sole writer of both.

**The literature note's frontmatter** carries:

- a metadata snapshot: a fixed subset of the Zotero item's data fields, copied verbatim under Zotero's own field names (`itemType`, `title`, `creators`, `date`, `DOI`, `url`, `publicationTitle`, `volume`, `issue`, `pages`, `publisher`, `ISBN`, `language`, `abstractNote`, **`extra`**, **`accessDate`**, and **`tags`**), so no field is renamed and no mapping is ours. `tags` is in that list for a specific reason: the Zotero plugins §6 adopts the DOI and metadata checks away to report their verdicts by tagging the item, with strings like `⚠️ Invalid DOI`, `⛔ No DOI found` and `MetadataHunter: No DOI`, removed again when a later run succeeds. Snapshotting tags is what keeps that verdict visible to the vault after the check itself leaves;
- a provenance tuple: `zotero-server-id`, `zotero-item-key`, `zotero-item-version`, `citationKey`, `attachments` (a list of `{key, version, md5, contentType, filename}`), `annotations` (a list of `{key, version}`; **this entry alone is deferred to lane 5, see below** — every other entry is written this iteration), `fulltext` (a list of `{attachment-key, sha256}` over the cached text; the sha256 is the comparison, because the endpoint's response body carries no version), the compile input's `sha256`, and `generated: {by, at}` (the shape of §5.2 of the **Open Knowledge Format**, the survivability spec ADR 0001 pins the vault to; already adopted). ### 3.3 The capture verb

One verb, per item or batch, keyed by citation key or item key. For each item it:

1. reads the item JSON from the local API (`/api/users/0/items/<key>?format=json`);

2. reads the children (`/items/<key>/children`): attachments with `md5`, `mtime`, `contentType`, `filename`, and the file URL from `/items/<attachment>/file/view/url`; notes. **A plain `/children` call omits annotations** (measured, §9): it returns none from the item key and none from the attachment key, even though an annotation's `parentItem` is the attachment. `/children?itemType=annotation` does return them, from either key, and that is the route capture uses. Two alternates stand, and capture takes one when the primary route returns no annotation, reporting which route it used. **No field recorded in §9 advertises annotation presence on an item or attachment**, so the plan settles the trigger against a live read before building the fallback: `/items?itemType=annotation` filtered on the attachment key, and Better BibTeX's `item.attachments`, which returns them nested per attachment with key, type, page label and text. `md5` exists only for stored-file attachments, so a linked attachment carries no fixity and the tuple says so rather than omitting the field. Zotero child notes are read here too, and unlike today they are rendered (step 5);

3. reads the attachment's indexed full text (`/items/<attachment>/fulltext`) into the gitignored cache. PDFs report `indexedPages` and `totalPages`; other content types report `indexedChars` and `totalChars`; the cache entry records whichever pair it received. A 404 means Zotero has no indexed text. **A 200 is not by itself a usable text**, and two separate tests are needed. The page test: Zotero truncates PDF indexing at `extensions.zotero.fulltext.pdfMaxPages`, default 100 in the installed 10.0.1 (source read), and reports the truncation as success, so `indexedPages < totalPages` marks the cache entry partial. The content test: a scanned PDF with no text layer returns 200 with `indexedPages` equal to `totalPages` and a near-empty body, so the page test alone would pass it as complete. A content floor is therefore also required, and **the floor is text-level only, because the file-level questions are already answered upstream.** `zotero-attachment-scanner` 0.5.1 is installed and tags `#nosource`, `#broken`, `#duplicate` and `#nonfile`, and §3.2's snapshot carries `tags`, so capture sees a missing or broken attachment without testing for one. Verified 2026-09-07 from its source: it never reads extracted text — no `fulltext`, no `getText`, no `indexed` — so it cannot answer the one question capture must. That question is whether the text represents the document, and the floor is **a non-empty extracted text whose length exceeds the masthead case §9 measures** — 62 to 126 characters on the three scanned PDFs — and which is complete on whichever pair the response carries: `indexedPages` equal to `totalPages`, or `indexedChars` equal to `totalChars` for the 15 attachments §9 counts that report characters instead; the plan sets the exact number against that measurement. Capture never treats a partial, empty, or absent index as full text;

4. contributes to the CSL file. **Chosen 2026-09-07: one whole-library read, not a call per item.** `GET /better-bibtex/library?/<library name>.json` returns the entire library as Better CSL JSON in a single request — measured 2026-09-07 at **0.46 s, 2.3 MB, 1,452 items, every `id` equal to its `citation-key`**, which matches the independently counted 1,452 bibliographic items exactly. Capture filters that to the captured set. This removes the draft's batch-failure mode outright: `item.export` *"takes a list and fails the whole batch on one unknown key"*, so a batch capture had to call per item or chunk-and-retry.

   **The route is undocumented.** It appears in no Better BibTeX documentation page; it was found by reading how `obsidian-reference-map` reaches Better BibTeX. An undocumented endpoint is an unpinnable dependency of exactly the class §3.8 prices, so the fallback is named here: `item.export([citation key], "Better CSL JSON")` per item, which is the documented call and what the 2026-09-04 draft specified. If the library route breaks, capture degrades to it and reports which route it used.

   Original reasoning, retained: `item.export`'s single call is keyed by the name, not the identity, because that is the only key the method takes; the citation key used is the one just read from the item JSON in step 1, so it cannot be a stale one. The method takes a list and fails the whole batch on one unknown key — the failure mode the whole-library read removes. The per-item and chunk-and-retry shapes are what it replaces, recorded so the route is not re-derived;

5. renders the note: frontmatter, then **only what frontmatter cannot carry** — the attachment list with its file links, annotations as a list with page labels and verbatim highlight text (deferred, §3.2), and the item's Zotero child notes. It also carries **three mechanical pointers**, which is what makes the note the single place a person reads a source from. `![[<page path>]]` **embeds each compiled page the source produced** — `pages[]` is a list, so a source that yielded a source page and a concept page embeds both — with paths taken from the ledger rather than guessed, so a page the tool renames is repaired on the next refresh; embedding by path rather than by title is what keeps §3.1's `[[Title]]` ambiguity out of it. **The two constraint sets agree by construction** (verified 2026-09-07): `ledgers.py` requires each entry to be a canonical vault-relative path starting `wiki/`, with no `..`, no absolute form and no line breaks, and Obsidian resolves exactly that shape — paths start at the vault root with forward slashes, and `[[note]]` and `[[note.md]]` are documented as equivalent, so the ledger's stored extension needs no normalising. An embed is a live view — Obsidian displays the content inline and keeps it current as the source file changes — so the summary is shown and never copied, and the duplication the seam would otherwise carry does not arise. `zotero://select/library/items/<item key>` opens the item in Zotero, and `zotero://open-pdf/library/items/<attachment key>` opens the PDF. **Both URI forms are Zotero's own**, emitted by its bundled `Note Markdown` translator inside `omni.ja`, and both key on **identity rather than name**. Better BibTeX's `zotero://select/items/@<citation key>` is declined: Zotero's own staff describe it as *"a feature of Better BibTeX, not Zotero"*, and a name-keyed link would become a fifth surface for propagation to rewrite beside `[@key]`, `[[key]]`, the CSL entry id and the review-queue targets. The item key and every attachment key are already in the tuple, so the identity form costs nothing. **The embed is absent until the first compile**, because capture runs first and no page or ledger entry exists yet — a missing view, not a defect, since an embed of a file that does not exist is inert and §3.4 already reports a note needing recompile. **Title, creators, venue and identifiers are not re-rendered into the body**: they are in the frontmatter, Obsidian displays them as properties, and rendering them again would put the same metadata twice in one file, which is the duplication this spec removes everywhere else. Rendering the child notes is new, and it is what gives a person's own prose about a source a home now that the free region retires: they write it in Zotero, where they already annotate, and capture projects it like everything else;

6. writes the cache; the CSL file is regenerated whole at the end of the run from step 4's single read, so no per-item contribution happens here;

7. compares the rendered projection with what is on disk and reports MATCHED with a NOOP label when nothing changed — NOOP is the exit label the repository already uses, not a fifth state (`CONTEXT.md` fixes the four).

Steps 1 to 3 read per item through two subsystems and step 4 reads the library once for the whole run, so no step is atomic with the others and an edit between them would be captured half-old. **The re-read boundary is per item**: after step 3, capture re-reads that item's version and restarts the item if it moved. Step 4's library read is checked once against the run's own `Last-Modified-Version` and re-read once for the whole batch if that moved — **provided the Better BibTeX route returns that header, which §9 does not record**; the plan measures it and re-reads unconditionally if it does not. The tuple records the version that was current across the whole read.

Every mechanical outcome is four-state. UNREACHABLE (Zotero not answering) writes nothing and files an outage finding. A malformed response writes nothing.

### 3.4 The lifecycle linter (**chosen 2026-09-07**)

One check, one code path, run at capture (before rendering) and at verify, with **the pre-commit leg held** until the write-side gate is settled (invariant 5). The code path is one whether or not that third caller exists. It:

1. reads every literature note's provenance tuple;
2. sends the recorded server id as the `Zotero-Server-ID` request header on every call, which Zotero answers with `412 Precondition Failed` when it is talking to a different database. The linter does not compare the value itself; it reports database-changed on the 412 and stops. Zotero's documentation directs clients to partition cached versions by that id, which is what the tuple does;
3. fetches three things: the whole key set with `?since=0&format=versions`, the trashed set with `items/trash?format=versions`, and **`/items/top?format=json`, which is the only one of the three carrying `citationKey` and `relations.dc:replaces`** — without it step 4 cannot classify `re-keyed` or `merged` at all. The full set is required, not `?since=<lowest recorded version>`: a `since` window returns only items that changed, so a key that vanished appears in neither the window nor the trash and would read as current. The full set arrives in one response, at the size §9 records, so it costs nothing;
4. classifies every note by comparing **every** key in its tuple, the item and each attachment and each annotation, against the versions map and the trash set: current (all match and none trashed), drifted (any version differs), re-keyed (live `citationKey` differs), merged (a live item's `dc:replaces` names the key, whether that key is **trashed or absent** — §1's precedence, which a test on absence alone would invert, because Zotero trashes the predecessor of a merge), trashed (any key in the trash set), deleted (item key in neither set). The comparison is per object because Zotero versions objects independently; classifying on the item's version alone would report a swapped PDF or a new annotation as current;
5. on a drifted note, names the cause from which key moved, and where an attachment moved, compares its `md5` and the cached text's sha256 to say whether the file changed or only its metadata did;
6. files one finding per non-current note, carrying the **first** transition that matches in this order: `database-changed`, `merged`, `deleted`, `trashed`, `re-keyed`, `drift`. **`merged` outranks both `deleted` and `trashed`**, because Zotero trashes a merge's predecessor and a later purge makes it absent — testing for absence or trash first would classify every merge as a loss, which is the inversion step 4 warns about. Otherwise identity outranks name and name outranks content, so a note both drifted and re-keyed reports `re-keyed`, and blocks nothing except database-changed.

Were the pre-commit leg bound, it would cost a running Zotero at every commit, which follows from the scope in §0: substrate absence is deferred. The leg is held (invariant 5), so today it costs nothing. Until it is taken up, a commit made with Zotero closed reports the linter UNREACHABLE, and the pre-commit hook treats an outage as it treats any other: it files the finding and does not block. The plan states that behaviour as a test, so an outage never silently reads as a clean classification.

Reason codes, proposed: `drift`, `re-keyed`, `merged`, `trashed`, `deleted`, `database-changed`, `outage`. `drift` already exists in the registry. `superseded-note` is retired with the note status. `not-admitted` stays in service, because `find-sources` still files it (§6).

### 3.5 Re-key detection, and why propagation ships with it

**Detection is specified here. The vault-wide rewrite is a task set in this spec's plan.**

A re-key is detected by the lifecycle linter alone: the item's live `citationKey` differs from the recorded one under an unchanged item key. Better BibTeX's `item.regenerate_key` is a **mutating** call that assigns new keys, so it is never a detection source; if a person uses it deliberately, its returned old-to-new mapping feeds the propagation pass. §3.4 classifies the note `re-keyed`, files a finding with that reason code, and blocks nothing. The item key is unchanged throughout, so identity is never in doubt and the finding is a rename report, not a loss. **One refusal, added 2026-09-13 (Part A's whole-branch review):** capture refuses to refresh a `re-keyed` item while `literatures/<old>.md` still exists, reason `re-keyed — old → new; run propagate` — otherwise the refresh derived the path from the live key, wrote `<new>.md` beside `<old>.md`, and propagation refused over the existing file. Propagation's own recapture proceeds, because the rename has already moved the old note away.

**Propagation is a distinct task set, not a distinct document.** Everything else here is a one-directional projection *into* `literatures/`: capture writes literature notes and the CSL file and touches nothing a person wrote. Propagation is the opposite — a vault-wide mutation over human content, rewriting `[@old]` citations in drafts, `[[old]]` wikilinks anywhere, the CSL entry id, and the review-queue and acknowledgment targets that name a key. That difference in blast radius is why it stays separately reviewable; it is not a reason to ship it separately. Shipping it separately would open the very window the dependency below describes. It carries one structural question, the rename log's site, which the plan's first task settles (open point 12).

> [!WARNING]
> **§3.1's filename choice is sound only because a re-key propagates.** The filename is the source's *name*, and the name changes. Until propagation lands, every re-key leaves a note whose filename contradicts its own recorded `citationKey`, and every `[@key]` and `[[key]]` naming it dangles — §3.4 reports each one and repairs none, so findings accumulate while the vault passes every check it has. Propagation lands with ingest, in the same plan.

**The trigger set, measured.** `resetKeyOnChange` defaults to **false** and is unset on this machine, so editing metadata does *not* re-key. The vectors are all deliberate: an explicit right-click Refresh, `item.regenerate_key`, and cloning an item, which clears the key before `fillKeyAfter` mints a new one. That makes re-keys **rare, not absent**, which changes the urgency, not the order — a rare divergence with no repair is still permanent.

Detection's own obligation is discharged here: `re-keyed` is a lifecycle state (§1), it has a reason code (§3.4), and the linter that finds it runs at capture and at verify through one code path, with the pre-commit leg held (invariant 5).

**Deletion is not always a deliberate act, measured 2026-09-07.** `extensions.zotero.trashAutoEmptyDays` defaults to **30** and is unset on this machine, so Zotero purges aged trash on its own: the test instance's trash held 504 keys at 11:47 and 212 at 12:02, and a database copy taken at 11:42 still carried 487 rows in `deletedItems` — so the items were present before this session's restarts, and about **280 of them left the library during one**, with no user involvement. The purge is this instance's own, not something inherited from the copied library. Two consequences. A design reading a disappearance as intent would misread every one of them; and because the local API has no `/deleted` endpoint (§3.7), nothing distinguishes a purge from a considered removal after the fact. Detection is therefore a key-set diff, and what it finds is a *fact*, never a decision — which is why the vault deprecates its own record rather than deleting it.

### 3.5.1 What Better BibTeX's own documentation says about keys (read 2026-09-07)

**Measured 2026-09-07, and the measurement is stronger than the documentation.** The test instance was given a copy of this library, a fresh profile whose Better BibTeX key store was empty, and — unintentionally at first, which is what makes it a test — a *different* citekey pattern: BBT's default `auth.lower + shorttitle(3, 3) + year` against the library's own `authEtal2.lower.len + year`. If keys were derived from metadata at read time, every key would have come back in the other shape. All **1,452** shared bibliographic items returned the key production reports, disambiguation suffixes included (`graham.etal2019a`). Then the pattern was set to the library's and the keys were re-read: unchanged again. Two patterns, in both directions, zero re-keys. So a citation key is **stored state that travels with the database**, not a projection of the metadata — which is why §3.1 can use it as a filename and why another machine reproduces these names by syncing rather than by matching a Better BibTeX configuration.

Read at the **v9.0.63 tag**, matching the measured build, rather than from `master`.

**Pinning no longer exists, and the key is Zotero's own field** (measured live 2026-09-13 on the test instance, research records 449–451: `PATCH /api/users/0/items/<key>` with the native `citationKey` and `If-Unmodified-Since-Version` answers 204, Better BibTeX adopts the new key within seconds, `extra` is untouched; the legacy Extra line was never needed)**.** BBT's front page: *"With the advent of Zotero 8, items have a Zotero-native citation key field. This has replaced the BBT citation key field… Zotero will have moved all pinned keys out of the `extra` field into the native field… The concept of pinning keys is gone; keys are always pinned now… Upside to all of this is that keys will sync."* Measured here: `autoPinMigrated` is true, every sampled item carries a populated native `citationKey`, and `extra` is empty. The `pinned()` formula function is documented as a no-op kept only for legacy formulas.

Two consequences for this design, both favourable and neither planned:

- **`zotero.py` reads the authoritative store.** §3.3 step 1 takes `citationKey` from the local API's item JSON, which is now Zotero's own synced field, not a Better BibTeX projection. The vault's detection route survived the largest architectural change in BBT's history by accident, and nothing needs to parse `Extra` for a pinned key.
- **§3.1's stated objection has weakened.** It answers the worry that *"a third party can change it"* by moving identity to the item key. That answer is still right, but the worry is smaller than it was: keys now sync, so a change made on one machine propagates rather than diverging silently.

**The regeneration triggers, measured rather than assumed.** `resetKeyOnChange` (*"Regenerate citation key when item changes"*) defaults to **false** and is unset on this machine, so a metadata edit does not re-key. `fillKeyAfter` defaults to **2** seconds and only fills a key for an item that has none — it mints, it does not change. BBT's own summary is *"BBT is conservative about citation key changes"*, and editing the key formula explicitly does not retro-apply: *"A new formula takes effect for items changed from that point forward."*

So the live vectors are three, all deliberate: an explicit right-click **Refresh**, **`item.regenerate_key`** over JSON-RPC (which this design never calls, per §3.7), and **cloning** an item, which clears the key before it is re-filled.

**This lowers the rate and leaves the design unchanged.** §3.1's item-key identity still holds, because a key that changes rarely still changes. §3.4's detection still holds. And the ordering in the decomposition's decision 29 still holds, on the argument that a rare divergence with no repair is permanent rather than tolerable.

### 3.6 Paths and the full-text layer (**chosen 2026-09-07**)

No absolute paths in the repository. The file URL from Zotero is a Windows `file://` path, percent-encoded; the existing `wslpath` shim resolves it at use time. The shim works because this host runs WSL2 with `networkingMode=mirrored`, which is also why a Windows-side Zotero answers on localhost at all.

**The extracted text becomes a vault layer, `fulltext/<attachment key>.md`, gitignored and OKF-conformant.** One file per indexed attachment, carrying frontmatter with a `fulltext` type, its `sha256` recorded in the literature note's provenance tuple.

Four properties decide it, and the 2026-09-04 draft's "gitignored cache folder" had only the last:

- **Obsidian indexes it.** Gitignored is a git concept, not an Obsidian one, so the text of every paper is searchable in Obsidian's own search box. Nothing else on the table delivers that: `qmode=everything` answers a *Zotero* query, and reading Zotero's cache at use time is invisible to the vault.
- **The path is vault-relative**, so it does not depend on where Zotero's data directory happens to live on a given machine.
- **Frontmatter earns it a walk.** Because the files are OKF-conformant they need no exclusion from `verify`'s rglob, unlike the tool's own `.raw/captured/` store, which §4.3 gitignores *and* excludes. That store is unused (§4.4), which is the stronger form of the same point: this layer is walkable, and the alternative needed two exemptions to be tolerable.
- **Derived, so never committed.** 1,335 files, 103.6 MB, mean 79 KB — measured 2026-09-07. Regenerable in one pass, so git carries none of it, and the decomposition's §12 cutover does not inherit another 100 MB the way it inherited 260 MB of transcripts.

**`fulltext/` takes no entry in `structure`'s folder-to-type map**, because its notes carry a `fulltext` type no folder rule derives, and `okf-frontmatter` asks only for a non-empty one. **It does not join `scaffold.VAULT_DIRS`**: `check_tree` reports UNMATCHED for any member that is not a directory and `tree` sits in `DOCTOR_HARD_UNMATCHED`, so a gitignored derived tree would hard-fail a fresh clone before capture had run. **One attachment is the compile input, and the tuple says which.** An item with two indexed attachments has two `fulltext/` files but one compile input: the wrapper names the attachment Zotero reports as the item's best attachment, and the tuple's scalar compile-input `sha256` is that file's. The `fulltext` list carries every indexed attachment regardless, so nothing is lost and the two hashes stop being ambiguous. **Named by attachment key, not item key.** Measured 2026-09-07: 1,306 parent items each carry exactly one indexed attachment and none carries two, so item-key naming would work today — but Zotero does not guarantee it, an item with two PDFs would collide, and the failure mode is a silently overwritten file. The attachment key is collision-proof by construction, it is already the key the tuple records, and it gives the 5 indexed attachments that have no parent a home.

**The recorded hash is machine-local, measured 2026-09-07.** The same attachment indexed on the two instances does not yield the same bytes: `568BWIT7` returns 34,024 bytes on production and 33,822 here, with different hashes. So the `sha256` in the provenance tuple certifies *this machine's* derivation against *this machine's* Zotero. That does not weaken the mechanism — the hash is only ever checked against the instance that produced it, which is the sole comparison §3.4 makes — but the tuple's hash is not a portable fact and must not be synced as though it were.

**A second machine derives it rather than receiving it.** Full-text sync is off and attachment storage is WebDAV (measured 2026-09-07), so Zotero syncs the *items* and the *files* but never the extracted text — the cache belongs to the machine that indexed. Another machine therefore syncs, downloads, indexes, and regenerates this layer locally, at a first-run cost. That is a property of the configuration, not of the design: turning full-text sync on would change it.

Zotero's index is the source of truth for extracted text and `.zotero-ft-cache` is its store; **verified 2026-09-07, byte-identical to `GET /items/<key>/fulltext` in 4 of 4 sampled attachments**, so either route yields the same bytes and the choice between them is about convenience, not fidelity. This layer is a projection of that, and the note's recorded `sha256` is what makes a disagreement visible. A disagreement is always resolved by re-reading Zotero, never by preferring the local copy.

**The change signal is the content, not a version.** Measured 2026-09-07 on the test instance: all 1,142 rows of `fulltextItems` sit at `version` 0, and the column's schema default is 0. That instance indexed every one of its attachments locally after the profile was unsynced, so **local indexing assigns no version** — the nonzero values on the production instance (up to 35,545, in the *library* version space, whose value in the test database is 35,774) are stale numbers left by a sync that is now off. Two consequences follow and they point the same way: `fulltext?since=N` for any `N ≥ 1` returns **nothing at all** on the test instance while 1,115 entries exist, and recording each entry's version and diffing it later inherits exactly that blindness, because a re-index moves the version from 0 to 0. So this layer ignores `version` entirely and compares the `sha256` it already records against a fresh read. That is affordable rather than clever: fetching the whole corpus is **26 seconds and 97 MB across 1,367 attachments** (measured 2026-09-07, 19 ms per attachment), so a full pass needs no incremental mechanism to guard it. Attachment `md5` and `mtime` are available as a cheaper gate — present on 1,311 of 1,312 attachments (§9) — and are not used, because a 26-second pass does not need one and a gate that can be wrong is worse than a scan that cannot.

**Page boundaries survive.** The served text carries form feeds at page breaks — verified 2026-09-07, `content.split('\f')` yields exactly `indexedPages` segments in order. Page attribution therefore needs no second extraction pass and no PDF library, which is what the foundation spec's §5 quote-provenance machinery had assumed.

### 3.7 API use (measured 2026-09-04)

- Zotero 10.0.1 local API, version 3, serves item JSON with `key`, `version`, `citationKey`, `dateModified`, `relations`; children with `md5` and `mtime`; `/file/view/url`; per-attachment `fulltext`; `fulltext?since=`; `?since=&format=versions`; `items/trash`; a `Zotero-Server-ID` header on every response. It has no `/deleted` endpoint — re-measured 2026-09-07 on **two** instances, so this is a property of the local API and not of one database's state, and deletion detection is therefore a key-set diff or nothing.

- **The local API mints its own version numbers.** The versions it serves are not the ones in the database behind it: measured 2026-09-07, the test instance's API reports item versions in 0–1,681 while its own `items.version` column runs to 14,595 and its library sits at 35,774. Zotero's instruction to partition cached data by server id is therefore not advice about two libraries drifting — the numbers are per-instance by construction, which is why §3.2's provenance tuple carries the id, not the version alone.

- Every translator-based format on the local API (`format=csljson`, `format=bibtex`, `include=csljson`) returns HTTP 500 on 10.0.1 — measured 2026-09-04. **Measured again 2026-09-13 by Part A's Task 16 live leg: `GET /api/users/0/items/top?format=csljson&limit=1` answers 200 with a CSL JSON body on both 10.0.1 and 10.0.2.** A route observed closed and open within nine days is not a basis to build on; decision 13 stands, Better BibTeX `item.export` stays the CSL renderer, and doctor's `translator-formats` probe reports the route's state as a warning (Part A Task 16; Part B Task 5 re-measures and records).

- **A shipped path is dead on this stack.** `research_vault/zotero.py`'s `export_csl(None)` — the whole-library branch — pages `/api/users/0/items/top?format=csljson`, which is a translator format, so it raises `local API HTTP 500`. The per-citekey branch goes through Better BibTeX `item.export` and works. §3.2 regenerates the file from the captured set, not the library, so the branch has no caller in this design; it is recorded because it is live in the tree today.

- Better BibTeX renders the CSL file through the whole-library HTTP route rather than JSON-RPC (§3.3 step 4). Its JSON-RPC surface is used twice more: as the annotation fallback (§3.3 step 2) and for doctor's `api.ready` probe (§5). Its auto-export is not used, and `item.regenerate_key` is never called, because it mutates (§3.5). `item.attachments` is the named fallback for reading annotations.

- The Zotero web API is not used, for three reasons. They are not the same API at two base URLs: Zotero's local-API page exists to enumerate *"the notable differences from the Web API"*, and lists nine.

  **The surface differs.** `format=atom` returns 501. `q` uses Zotero's local quicksearch, so *"the set of items returned by a given `q` value may not match the Web API exactly"*. The local API *"does not impose a default or maximum limit"* and *"does not currently apply rate limiting"* — both in our favour, and both meaning code written against the Web API's ceilings is dead weight here. It answers 403 when the local-API preference is off, and 501 for an unsupported API version. And *"in Zotero 10+, local versions are unrelated to the versions in this API, so clients must partition cached data by server ID"* — `must`, the strongest modal on the page.

  **It also serves things the Web API does not**, and one of them is load-bearing: `<userOrGroupPrefix>/items/<itemKey>/file` and `/file/view/url` are **local-only**. §3.6's path shim and §9's `file:///D:/Zotero/storage/…` probe both depend on that endpoint, so repointing the base URL at `api.zotero.org` does not degrade the design — it breaks the attachment path outright. **Device independence is therefore an architecture, not a configuration change**. `searches/<searchKey>/items` is likewise local-only: the Web API exposes search metadata but never executes a search.

  **The data differs too**, and that half stands. `extensions.zotero.sync.fulltext.enabled` is **false** and `sync.storage.protocol` is **webdav** (measured 2026-09-07), so no extracted text was ever uploaded and the web endpoint returns nothing for the one input capture most needs. Flipping that preference would fix the data half and leave the surface half untouched.

- The bib-file export is not used.

Two repositories in this ecosystem carry a recent `pushed_at` over frozen code and were silently archived, so activity was judged on the last commit touching source.

No user-editable template, which this vault does not want, having one shape. No annotation image extraction, deferred with annotations. And no offline read: §0 defers substrate absence, and ZotLit's ability to read with Zotero closed is the capability that deferral postpones.

Device independence is an architecture, and this line does not survive as an argument for building; the four in the verdict do. `zotero-api-client`, the JavaScript client ZotFlow builds on, already exposes `apiScheme` and `apiAuthorityPart`; ZotFlow, one of the screened candidates above, simply never passes them.

### 4.3 Adoption (**ratified 2026-09-07**): claude-obsidian unmodified, driven by a wrapper

The compile step adopts AgriciDaniel/claude-obsidian at pin `ad67087`, installed whole and configured through its own mode system, with no edit to the tool. Every accommodation is on this vault's side, which is where nothing binds.

**The verdict is `adopt`, and it survived a serious attempt to make it `adapt`.** The tool's Python core does two things — renders a template tree once, and validates agent-authored transaction bundles against path-scope, hash-precondition and schema rules. Everything else (page bodies, frontmatter values, index entries, `sources:` backlinks) is written by an LLM following prose in `skills/`, `agents/` and `WIKI.md`, which invites vendoring that prose and bending the methodology toward PRISMA-S. **The upstream release model forbids it economically.** Measured at the pin: of 49 prose files **zero were unchanged across 90 days**; turnover is 2.06× overall and **2.85× on the mixed methodology files worth owning**; and **98.5% of that churn arrived in one release-promotion commit** of 81,000+ lines, because the public repository is a distribution mirror populated wholesale from a private tree. A fork re-derives its edits against a rewritten tree every release — roughly 2,800 conflicting lines per cycle on the subset worth adapting. No override seam exists: "custom scaffold" is prose pointing at prose, `extensions.py` is legacy compatibility, modes are a closed four-value enum, and no config key names a prose file.

**So research-vault drives it through a wrapper of its own** (§4.5) — glue tier under `docs/agents/sourcing.md`, the low bar — and upgrading is `git pull` with no conflict surface. Two consequences. **The methodology question defers to lane 5, and the churn is the weaker of two reasons.** The stronger one is that it may not be ours to answer. Lane 4 curates research skills — MedSci, K-Dense — and screens them against exactly the floors this methodology would be bent toward: PRISMA-S, PRISMA-ScR, the ACM guidelines. If a curated skill carries the method, we adopt it rather than writing it into a forked prose surface, and the tool's own generic knowledge-wiki practice never needs touching. Bending it now would risk building what lane 4 supplies. Lane 5's gap pass is where that resolves either way: it walks the obligations index and sources only what nothing answers, which is the shape this question already has. And **the ledger points at what capture already wrote**, `fulltext/<attachment key>.md`, which `ledgers.py` already accepts as a vault-relative canonical path — the `inbox/`-or-`.raw/` restriction is instruction, not validation. No third copy of the text is made, and the ledger's `content_sha256` is the provenance tuple's number by construction.

**One constraint a later lane should not rediscover**: `provenance.md`'s authority tiers and review states are **closed enums in `ledgers.py:25-49`**, code-validated, so PRISMA-S screening stages cannot live in the source ledger without patching Python. They belong in free-form frontmatter values and page structure, which the tool permits — it checks that six keys exist and never validates what they hold.

**The plugin arrives whole or not at all.** Curating it down is unreachable, measured against Claude Code 2.1.260: it ships a `plugin.json` at its repo root, so a marketplace entry that also lists components is rejected — *"has conflicting manifests: both plugin.json and marketplace entry specify components"* — and at `strict: true` the list supplements directory discovery rather than replacing it (*"Custom paths supplement default directories - they don't replace them"*), so all fifteen skills, three agents and both hooks load anyway. A `git-subdir` source pointed at `skills/` would curate but severs the `claude_obsidian/` engine, and every skill hard-gates on `$PRODUCT_ROOT/scripts/claude-obsidian.py`. So §4.2's component inventory is what a session carries. Two subsetting routes exist as fallbacks, neither proposed, because the surplus is a context cost, not a correctness one: **vendoring** the wanted skills under a provenance header drops the hooks by geometry but drags the engine along (~50 files, a megabyte); **an in-tree marketplace entry** works because the loader's subtraction branch fires when `source` is `"./"`, confirmed by a probe on this vault's geometry, at the price that the entry then governs this vault's own skills too. Cheaper still if the surplus bites: `permissions.deny` on a skill namespace mutes execution, though the skill still loads and the context cost remains.

**Modes.** Four ship, and their folder names are configuration; all validate through `mode_config.validate_wiki_folder`, which requires the first path segment to be `wiki`, so none escapes that parent. **`generic`'s four keys are `sources_folder`, `entities_folder`, `concepts_folder` and `sessions_folder` — there is no `synthesis` key** (measured 2026-09-07). The cross-source layer is therefore `concepts_folder` set to `wiki/synthesis/`, which validates because the check tests canonical form and the `wiki` root, not the name. Taking the tool's default `wiki/concepts/` instead would work equally well and cost the vault its own word for the layer. `generic` is the structural match — its sources-to-concepts split is this vault's per-source-to-cross-source split. **What the tool cannot read, and why that is fine.** Of its seven capture adapters exactly one is implemented, accepting markdown, text, JSON, CSV, YAML and HTML; PDF, EPUB and images are `metadata-only` — identified and described but not extracted — and need an external runner it does not ship. ### 4.3.1 The `wiki/index.md` deviation, and why the vault bends, not the tool

**The tool writes `wiki/index.md` with frontmatter; OKF §8 forbids it on any index file.** The path is hard-coded in three code sites plus `config/capabilities.json`, and the tool's own lint requires six frontmatter keys on every page under `wiki/` — so a frontmatter-free index fails *its* check as surely as a frontmatter-bearing one fails ours. `_ORPHAN_EXCLUDED_NAMES` is orphan-only and does not reach the frontmatter loop; there is no config escape and no environment variable. The finding is exit-0 on `lint` but blocks `checkpoint` outright (`LINT_FAILED`, exit 4), whose only bypass discards dead-link and provenance gating too.

**Resolved by amending ADR 0001 rather than patching the tool (2026-09-07).** A cleaner on a trigger was considered and rejected: it does not avoid the patch — stripping the frontmatter is what *creates* the blocking finding — and it adds a third writer racing a transactional system's hash preconditions. The one-line patch was considered and rejected on the release-model evidence above. What remains is a bounded deviation: one file, in a machine-owned tree, whose frontmatter an OKF consumer ignores under OKF §4.1's producer-key rule. ADR 0001 carries the exemption and `docs/terminology.md` prices it at cost class 1. **The vault's own `structure.py` must gain the matching exemption** — its nested-index rule would otherwise fail the vault on its own check — which is plan work, not a further decision.

### 4.4 The seam between capture and compile

**The captured set is the citable set, and one lint enforces it (adopted 2026-09-07; one addition 2026-09-13 — a note under `literatures/` the reader cannot take, unreadable, not UTF-8, unparseable or tuple-less, is a row from this lint, `UNREACHABLE` for the read fault and `UNMATCHED schema-violation` for the rest, never a silent drop from the set; the lifecycle walk still skips it, which is why this lint carries the row).** A compiled page may cite only a source capture wrote. Nothing enforced that: no check tied a `[[citation key]]` or `[@citation key]` under `wiki/` back to a `literatures/<citation key>.md`, and the adopted tool's own dangling-link check resolves against every file in the vault rather than against the captured set — so a page citing an invented key, or a key belonging to a note the vault never rendered, passes today. That is this project's founding thesis with no mechanism behind it, at the one seam this lane exists to design.

**This is the one place in the lane where building is the answer, and the build bar is met by naming what no candidate can supply**: "captured" is a fact about *this* vault's evidence layer, and nothing external knows what it means. The bar is also low in the way `docs/agents/sourcing.md` cares about — it is a lint over a set the vault already holds, not a subsystem. **The guarantee is structural and the lint guards the one gap it leaves.** A compiled page exists because the wrapper put a source in the ledger, and the wrapper names only sources capture wrote (§4.5), so a page cannot correspond to an uncaptured source by construction. What construction does not cover is **prose**: the tool's LLM writes page bodies, and a body can cite a key nobody captured.

So the lint has two halves. **Structural**: every ledger record's `origin.locator` must name a file capture wrote, which is checkable against the evidence layer and fails loudly if the wrapper is bypassed. **Textual**: any `[[key]]` or `[@key]` under `wiki/` must resolve to **the captured set**, with the remainder reported as a finding. §1.1 records that the captured set is undefined — the keys capture wrote notes for, or the filenames now under `literatures/` — and task 0 settles it before this lint is built, because the two readings differ exactly when a note has been deleted by hand.

**The textual surface is usually empty, and that is the design working rather than the check being vacuous.** Verified at pin `ad67087`: the tool's page vocabulary has no citation-key property — `sources:` holds wikilinks to the tool's *own* page titles, and the source-page fields are `source_type`, `author`, `url`, `source_id`, `sha256`, `authority`, `review_state`, `key_claims`. Nothing it writes by default carries a citation key, so the check fires only when an LLM invents one, which is exactly the failure it exists to catch. Frontmatter values are scanned with the body, because a citation key appearing there would be as invented as one in prose. The tool's own dangling-link check is left alone rather than replaced; it answers a different question, and two checks over one surface is what §6 refused, not two checks over two.

- Capture is the only writer of the literature note and the text cache, and **the text cache is the compile input** — there is no third file. §4.5 names `fulltext/<attachment key>.md` as each source's `origin.locator`, which the tool's `ledgers.py` already accepts as a vault-relative canonical path. No separate compile input file is written into the tool's inbox directory: it would be a second copy of bytes the vault already holds, with a second hash to reconcile. Two constraints bind that input, and both are satisfied by construction rather than by rule: the input's filename is the **attachment key**, so it can never equal `<citation key>.md`, and its frontmatter carries a `fulltext` type with no `title` and no `aliases`, so no wikilink to that source becomes ambiguous across two files. Markdown is not a convenience here, it is the tool's only implemented input format (§4.3).
- Where Zotero has no indexed text, or only a partial index, capture writes no compile input and files a finding. Nothing is compiled from an abstract alone, and nothing is compiled from a page range that Zotero truncated.
- **No second copy of the text exists.** The tool's `.raw/captured/` store would hold one if its own `capture` were run; it is not run (§4.3), and the ledger points at `fulltext/` instead. The gitignore and walk exclusion stay as cheap insurance, guarding a store nothing writes.
- `wiki/synthesis/` is the cross-source layer, and it sits there because **the tool cannot write outside `wiki/`** — its ingest is scope-refused from any other path. **Root `synthesis/` does not survive beside it** (§6): the two would be one epistemic class in two folders, so the layer moves rather than forking. That is the same role `synthesis/` was always intended to serve, so the layer keeps its meaning and its name and moves one level down.
- **The per-source page lives in `wiki/sources/`, not in the literature note.** The vault would have preferred one file per source, but the tool's engine has only whole-file create and replace, so it cannot write part of a note another writer owns. Splicing the page in outside the tool would cost the tool its wikilinks, its index entry and its ledger locator, and its next lint would report both as broken. Two files per source, in two trees, is the price of not editing the tool. This is also why the note's free region retires rather than waiting for a splice that is not coming (§6).
- Compile runs when the person asks, after capture, for one source or a batch. The tool's own gate is the human gate: inspect the proposed bundle, approve it by its plan hash, apply it atomically or not at all. No second gate is added.
- **Capture** records the compile input's sha256 in the note, because §3.2 makes capture the note's sole writer and §3.4's linter only reads and reports — which is now the same `sha256` the provenance tuple already records for the text cache, since they are one file (§3.6). A refreshed note whose hash changed is reported as needing recompile, which the tool then performs.
- Reading across the boundary already works, and **it is how a reader crosses in both directions**: the tool's page carries `[[<citation key>]]`, which resolves into `literatures/` with no dead link and puts that page in the literature note's backlinks. **Reversed 2026-09-07: the literature note embeds the compiled page** (§3.3 step 5). The three objections were to a forward *link*, and none carries to an embed. Capture running first leaves an inert missing-file view rather than a dangling link; `[[<title>]]`'s ambiguity disappears when the target is a path; and the tool renaming its pages is repaired on refresh, because the path comes from the ledger's `pages[]` rather than a guess. What the embed adds over the backlink is that it removes duplication instead of recording a relation — the compiled summary is displayed in the note, never copied into it.

### 4.5 The wrapper: what it owns (2026-09-07)

§4.3 adopts the tool unmodified, so something must drive it, and that something is research-vault's own. Naming a component without bounding it would leave the tier claim unscreenable — `docs/agents/sourcing.md` prices prompt-bearing components at the high bar and glue at the low one, and "glue" spans a shell alias to a subsystem.

**It owns four things.**

1. **Selection** — which captured sources are compiled. The tool cannot decide this: it has no notion of the captured set, which is why §4.4's lint exists at all, and the evidence layer is the vault's.

2. **Locators** — naming `fulltext/<attachment key>.md` as each source's `origin.locator`. The tool's prose says material comes from `inbox/` or `.raw/`, but `ledgers.py` validates only that a locator is a vault-relative canonical path. The wrapper supplies its own locator rather than evading a constraint; the restriction it steps past is instruction, not validation (§4.3).

3. **Ledger records**, at `wiki/meta/ledgers/source-ledger.json` — filling `origin.kind`, `origin.locator`, `title`, `content_kind`, `authority` and `review_status` from the captured metadata. **`fulltext/<attachment key>.md` is confirmed valid as a locator** (read 2026-09-07): the `kind: "file"` branch enforces only canonical vault-relative form and `assert_within`, with no prefix allowlist, so nothing restricts a source to `wiki/`, `inbox/` or `.raw/`. **And no operation type can write there** — `ingest` and `generic` are confined to `wiki/`, `capture` to three-part `.raw/captured/` paths — which is the property the design wants: capture creates the file, the tool only ever reads it.

   **`review_status: "active"` is the demanding value, and the wrapper meets its terms or picks another.** It requires `content_sha256` present *and equal to the file's current bytes*, an observed date (`retrieved_at` or `ingested_at`), an explicit `refresh_due` at or after it, and **every path in `pages[]` to exist**. Since `pages[]` is populated by the compile that has not run yet, a record is written `unreviewed` at capture and moved to `active` only once its pages exist. **The ledger's names are not the page's**: it takes `review_status` and `content_sha256`, while the tool's *page* frontmatter convention spells the same ideas `review_state` and `sha256` and adds `source_id` — documented in `skills/wiki/references/frontmatter.md` and enforced by no code. The record ID is not the wrapper's to choose: it must equal `stable_source_id(kind, locator, content_sha256)`, a truncated digest over the three joined by NULs. — **and note the collision §1.1 asks to be named**: this `authority` is the compile tool's ledger enum, unrelated to the vault field of the same name that §3.2 retires, and setting `content_sha256` to the hash the provenance tuple already records, so the two systems agree by construction rather than by comparison.

4. **Bundle authoring and the two-step apply** — measured 2026-09-07, and it is more than a command call. **There is no `ingest` subcommand**: `ingest` is an `operation_type` inside a hand-authored transaction bundle, and the wrapper composes that JSON itself — `{schema: "claude-obsidian.transaction.v1", operation_id, operation_type: "ingest", expected_hashes, writes[]}`. It then runs `transaction inspect`, reads `approval_sha256` off the result, and runs `transaction apply --approved-plan-sha256 <hash>`; the hash is **mandatory** on apply and a changed bundle raises `PLAN_CHANGED`. `inspect`'s `changed_paths` includes writes the engine expands (the address counter, for one), so the wrapper reports the post-expansion set. Outcome is four-state as everywhere else, with exit 75 meaning re-read and rebuild, and `transaction recover` after an interruption.

**It owns none of these.** Rendering wiki pages, which the tool's own agent does under the tool's own prose. Methodology, which defers to lane 5. Writing under `wiki/` **outside a transaction**. The ledger lives at `wiki/meta/ledgers/source-ledger.json`, inside the tool's tree, so the wrapper does write there — as a `writes` entry in a bundle the engine validates and applies, never as a direct file write. That is the distinction the boundary rests on, not the folder. And lint: §4.4's captured-set check is a vault check on the commit surface beside verify's others, not a wrapper function.

**The tier claim is conditional and it expires.** Bounded this way the wrapper carries no prompts — it selects, fills a record, calls a CLI — so glue is the honest tier today. **Lane 5's methodology work makes it prompt-bearing**, and at that point the tier changes and the component is re-screened rather than grandfathered. Recording that here is what stops a low-bar verdict outliving the shape that earned it.

The linter never compares two stored copies — it sends the recorded id as a header and lets Zotero answer 412 (§3.4). The standing facts file is deleted rather than repaired. `docs/environment.md` recorded Zotero 9.0.6 and Better BibTeX 9.0.57 while 10.0.1 and 9.0.63 were running, while claiming to be live-verified throughout. Live values come from `probe`, and nothing keeps a second copy to go stale. That removes the failure class rather than watching for it, the same reasoning §6 applies to the DOI and metadata checks.

Retired from setup: the whole-library auto-export step and its staleness probe. Kept: the human-only wizard steps for Zotero plugin installs.

Every mechanical step in this spec is falsifiable, and for most the instrument is a linter (invariant 6 makes a linter one instrument, not the requirement): setup has doctor; capture, the CSL file, and the text cache have the lifecycle linter through recorded hashes and versions; adding has capture, which runs immediately on the returned keys and reports what it could not read.

**Live legs** against Zotero 10 on a scratch collection, under the existing `live` marker: capture round-trip, and linter classification after a live edit.

**`verify --as-of YYYY-MM-DD`, defaulting to today.** A *stamp* records when something happened and reads one clock; a *check* decides whether something is stale and must take the instant as an argument, or its verdict is not reproducible. Three surfaces compare dates — the update-notice check, the inbox's `oldest_age_days`, and the ledger's `refresh_due`. **The vault does the third comparison, because nothing else does** (read 2026-09-07): `ledgers.py` defines `source_is_stale(record, as_of=)` but its only callers gate whether a source counts as standalone evidence for a claim; the lint engine never calls it, so a record past its `refresh_due` produces no finding from the tool. The vault therefore reports it — **using the tool's own predicate rather than a bare `refresh_due < as_of`**, so the two can never disagree about what stale means: `due is None or observed is None or observed > as_of or due < as_of` — and threading one argument to them replaces four hidden `datetime.now()` call sites (`__main__.py:268` and `:613`, `searchlog.py:80`, `inbox.py:342`). **This is what makes the fixtures above replayable**: without it a recorded fixture's verdict drifts with the clock, and a note that verified `current` in September fails in December for no reason present in the fixture. It is also OKF §5.5's own reasoning from the consumer side — OKF fixes an absolute instant on the producer so the reader's `now` is the only variable left, and `--as-of` makes that variable explicit.

**Gates unchanged**: coverage, mutation baseline, form owners.

07. ~~The acknowledgment scope has no hash.~~ **Closed 2026-09-07: stop choosing a hash and derive the identity.** *Built in Part A Task 18 (2026-09-13), with two refinements the build forced: every scope leg strips verify's own `[failed-verification::]` marker bytes before hashing, and the note canonicaliser excludes the verifier-owned `failed-verification` event list as it excludes `verified` events — otherwise an acknowledgment was orphaned by its own clear, or oscillated fail → pass → fail on a note without a `managed-sha256`.* An acknowledgment is identified by `sha256(check_id \0 target \0 target_content_hash)`, so a changed target yields a different id, the ack no longer matches, and the finding re-fires — which is `CONTEXT.md`'s rule with no comparison logic to get wrong. For a note-targeted finding the third component is `managed-sha256`, which §3.2 already writes. **It also closes the decomposition's §15.22**: a doctor row has no path or hash today, but `target` takes a probe id and the third component takes whatever the probe observed, so one identity shape covers note findings and doctor rows. `__main__.py:581-648` already plumbs `target_hash`; this replaces passing a hash with deriving one. The pattern is `stable_source_id`'s, and OKF §5.1 gives the argument for it in its own case — keys are stable rather than positional *"because agents constantly rewrite these documents"*.

08. *Plan-level, not a design decision (2026-09-07).* **`[retraction-ack:: <code>]` was defined once, for three consumers.** The syntax survives in `skills/evidence-conventions`, but §5's rule — that the update-notice gate, `publish` and `evidence-conventions` **all key on that single syntax** — does not. The single-definition-site rule is what keeps three consumers from drifting apart; nothing now states it. ~~**Open**, and cheap to close by naming the definition site.~~ **Closed 2026-09-13 (Part A Task 18):** `publish.RETRACTION_ACK_FIELD` is the one definition site, the skill's text is asserted against it by test, and the three consumers read the constant.

09. *Plan-level, not a design decision (2026-09-07).* **A human acknowledgment does not clear `[failed-verification::]`, though §5 says it should.** Measured: `_mutate_marker` has exactly two callers — `verify.py:834` stamps on UNMATCHED, `:836` clears on MATCHED. The ack path (`cmd_ack` → `inbox.append_ack`) never reaches it. This is an **unimplemented rule, not a lost one**: deleting §5 silently would have hidden a live gap between a written contract and the code. **Implemented 2026-09-13 (Part A Task 18, three rounds):** `ack` clears the marker where verify writes it — every project note carrying the anchor for an anchored target, every project line citing the key for verify's own bare-key `citation-key` findings, the named file for a repo-path target, hand-authored literature notes included and `wiki/` skipped as the writer skips it — and the stamp itself now runs only over outcomes no acknowledgment covers, so the clear is not undone by the next run. The marker's meaning became: a raw failure no person has acknowledged, closed and reopened together with its inbox row.

10. **Web-Annotation context capture is unowned by the document that specifies capture.** foundation spec §5 required quote claims to capture `exact` plus 32-character `prefix`/`suffix` at extraction time, on the reasoning that it is *"nearly free at capture, unreconstructable later"*. This document has zero occurrences of `selector`, `prefix`, `suffix` or `TextQuoteSelector`. The cost asymmetry is the whole argument and it is real — if capture does not take the context, no later pass can. **Open**, and it interacts with the annotation deferral: annotations defer to lane 5 (§3.2), so the anchor whose durability §5 guaranteed is deferred with them.

11. **The re-anchoring cascade lost its trigger.** foundation spec §5 deferred it *"gated on a consistency check, only if the slice shows prose-parsing bottlenecks."* The surviving register entry carries the deferral without the condition, so nothing says when to revisit it. **Open** — a deferral with no trigger is indistinguishable from an abandonment.

12. ~~The rename log has no site.~~ **Closed 2026-09-07: the applied plan is the log.** Propagation computes a plan, prints it, and applies only against that plan's hash — the shape §3.5's blast-radius argument has always implied and the one mutation in this design that touches human content. The applied plan already carries the old→new mapping, every surface it rewrote, and one hash, so a second artifact would be a copy of it. Capture takes no such gate and needs none: it is deterministic, idempotent by render-compare, and writes only machine-owned trees, so an approval step would guard nothing. OKF does not reach this — §1 puts runtime out of scope — but §10's attestation is the same shape, sanctioning a computation and comparing what ran against it, and §10.3 gives the reason: a fixed surface is what makes *"did the sanctioned thing run"* a mechanical comparison rather than a judgement call.

13. **Export configuration is pinnable, even though the version is not.** BBT supports `preferencesOverride` and `postscriptOverride`: a `preferences.json` or `postscript.js` placed **in the export directory** overrides the global preference for that export alone — committable, reviewable, and immune to another project's global setting. The decomposition's **decision 12** says Zotero-side components are declared and observed, never pinned; that is right about the *version* and too pessimistic about export *behaviour*. **Not taken now, because the auto-export retirement removes the export directory it would live in.** Recorded so that if a configured export ever returns, the pin is known to exist rather than rediscovered.

14. **A deprecated `Extra` syntax exists that our snapshot would not make legible.** BBT still honours `{:pmid: 123456}` alongside `PMID: 123456`, describing it as *"supported but considered deprecated"* and still showing it in its docs. BBT destructures both into CSL; §3.2 copies `Extra` verbatim and parses neither, so an item in the brace form would carry a value in `bibliography.json` and an opaque string in the note. **Measured 2026-09-07: zero of 440 items with a non-empty `Extra` use the brace form**, so this is a watch-item, not a case to build for.

15. **Two pull-export aliases in BBT's own documentation are wrong on 9.0.63.** `pull.md` lists `csljson`, `yaml`, `yml` and `cslyaml` as valid `format` values; measured, several return HTTP 500. The working spelling is `json`. Recorded because `csljson` is the intuitive choice and the documentation invites it — and because §3.3 step 4's route is undocumented, so its neighbours' documentation is the only guide a later reader has.

16. **BBT's export worker is self-described as experimental and self-disabling.** *"a wild departure from how translation works in Zotero"*, and a single error silently flips the whole instance to foreground exports until a human intervenes. Every pull-export request defaults to the worker path. Not a blocker — but if capture's CSL read becomes slow rather than failing, this is the first thing to check.
