# Evaluating summary quality in Python — stdlib repurposing vs. purpose-built libraries

Two distinct option sets exist for scoring "how good is this summary" in Python. The standard library has **no function built for this** — every stdlib approach is a general-purpose text/sequence tool bent to the task, with the semantic blindness that implies. The third-party ecosystem has purpose-built metrics, but they split into three methodologically different generations: lexical n-gram overlap (ROUGE/BLEU-era, 2002–2004), embedding-based semantic similarity (BERTScore/MoverScore/BLEURT-era, 2019–2020), and LLM-as-judge (G-Eval-era, 2023–). Each generation trades cost and setup complexity for closer correlation with human judgment. This note catalogs both sets against primary sources — no metric's characterization here comes from a blog post rather than its own docs, code, or paper.

## 1. Standard-library-only approaches

None of these were designed for summarization. They are sequence/collection primitives that happen to produce a number when pointed at two texts.

### `difflib.SequenceMatcher` — matching-block ratio

`SequenceMatcher.ratio()` returns `2.0*M/T` where `M` is the number of matching elements found by the longest-matching-block algorithm and `T` is the total length of both sequences combined; `1.0` means identical, `0.0` means nothing in common, and the docs give "over 0.6" as a rule-of-thumb threshold for "close matches" ([`difflib` docs](https://docs.python.org/3/library/difflib.html)). In summary evaluation this gets repurposed as a crude extractive-overlap check — "how much of the summary is verbatim, contiguous text from the source/reference." Cheap variants `quick_ratio()` and `real_quick_ratio()` trade accuracy for speed and are documented to always return values `>= ratio()`, i.e. they overestimate similarity.

**Limitations:** operates on whatever sequence you feed it (characters or word tokens — the caller decides), has no notion of synonymy or paraphrase, and rewards verbatim contiguous spans rather than meaning — an abstractive summary that correctly compresses and rewords the source will score low even when it is a good summary.

### `collections.Counter` — bag-of-words overlap

`Counter` is a `dict` subclass for counting hashable objects, with multiset operators `&` (intersection, `min(c[x], d[x])`) and `|` (union, `max(c[x], d[x])`) ([`collections` docs](https://docs.python.org/3/library/collections.html)). Fed word-tokenized summary and reference, `len(Counter(summary) & Counter(reference))` divided by summary or reference length gives hand-rolled precision/recall proxies — this is, in miniature, what ROUGE-1 computes, minus stemming, minus the official tokenization/aggregation rules. The docs' own worked example (`Counter(words).most_common(10)` on the text of *Hamlet*) is exactly the word-frequency use case this gets bent toward.

**Limitations:** pure bag-of-words — no order sensitivity at all (an anagram of the reference scores perfectly), no semantics, and precision/recall have to be computed by hand since `Counter` itself doesn't produce a ratio.

### `statistics` — length and compression ratios

The module computes numeric descriptive statistics (`mean`, `stdev`, `variance`, `correlation`, etc.) and is explicitly scoped by its own docs as aimed "at the level of graphing and scientific calculators," not a NumPy/SciPy competitor ([`statistics` docs](https://docs.python.org/3/library/statistics.html)). It has zero text-awareness; the only summarization-relevant use is post-hoc arithmetic on numbers derived elsewhere — e.g., `len(summary_tokens) / len(source_tokens)` as a compression ratio, or `statistics.mean`/`stdev` across a batch of ROUGE scores to report a dataset-level result. It measures nothing about the summary's *content*.

### `re` — tokenization plumbing

Not a metric at all, but every stdlib technique above needs tokens, and the standard incantation is `re.findall(r'\w+', text.lower())` — the same pattern the `collections` docs use in their own Hamlet example ([`collections` docs](https://docs.python.org/3/library/collections.html)). This is whitespace/punctuation-naive tokenization: no handling of contractions, hyphenation, or multi-word expressions, which is part of why hand-rolled `Counter` overlap diverges from what ROUGE implementations report (they apply stemming and defined tokenization rules on top).

**Honest summary of §1:** stdlib gives you sequence-alignment and multiset arithmetic, not a summarization metric. Everything here is order-sensitive-but-meaning-blind (`difflib`) or meaning-blind-and-order-blind (`Counter`), with no synonym handling, no compression-aware scoring, and no way to detect a fluent, well-compressed summary that simply uses different words than the reference. Useful only as a zero-dependency sanity check, never as a quality score to optimize against.

## 2. Third-party libraries

### Lexical n-gram/LCS overlap: ROUGE

ROUGE ("Recall-Oriented Understudy for Gisting Evaluation") was introduced by Chin-Yew Lin, "ROUGE: A Package for Automatic Evaluation of Summaries," Text Summarization Branches Out workshop, ACL, July 2004, Barcelona ([ACL Anthology W04-1013](https://aclanthology.org/W04-1013/)) — recall/precision-oriented n-gram and longest-common-subsequence overlap between candidate and reference summaries. Three Python implementations exist, none of which is the original Perl `ROUGE-1.5.5`:

- **`rouge-score`** (pip: `rouge-score`) — Google's "pure python implementation of ROUGE-1.5.5," computing ROUGE-N, ROUGE-L, and a summary-level `rougeLsum` variant, with optional Porter stemming and bootstrap-resampled confidence intervals; the README states it deliberately **omits stopword removal** because the original word list's licensing and content (day/month names) were unsuitable, and that "not all options provided by the original perl ROUGE script are supported" ([PyPI](https://pypi.org/project/rouge-score/), [source](https://github.com/google-research/google-research/tree/master/rouge)). PyPI's latest tagged release is 0.1.2 (July 22, 2022); the surrounding `google-research` monorepo shows commits touching that path as recently as July 2026, though not release-tagged — treat it as lightly maintained-by-accretion rather than actively released.
- **`py-rouge`** (pip: `py-rouge`, GitHub `Diego999/py-rouge`) — "a full Python implementation of the ROUGE metric, producing same results as in the official perl implementation," supporting ROUGE-N, ROUGE-L, and ROUGE-W (weighted LCS) ([GitHub](https://github.com/Diego999/py-rouge)). Latest PyPI release is 1.1, uploaded September 15, 2018 ([PyPI JSON API](https://pypi.org/pypi/py-rouge/json)) — no release since, effectively unmaintained.
- **`rouge`** (pip: `rouge`, by pltrdy) — "Full Python ROUGE Score Implementation (not a wrapper)," latest release 1.0.1 (July 20, 2021); its own README carries the disclaimer "this implementation is independent from the 'official' ROUGE script... Results may be slightly different" ([PyPI](https://pypi.org/project/rouge/)). No activity since 2021.

ROUGE is the closest thing this space has to a de facto standard for **extractive** and near-extractive summaries, since it directly rewards wording overlap with a reference. For abstractive summaries it systematically under-credits correct paraphrases, which is the motivating complaint behind every metric that follows.

### MT metrics repurposed via NLTK: BLEU and METEOR

`nltk.translate.bleu_score` provides `sentence_bleu()` and `corpus_bleu()`, computing modified n-gram precision (guarding against the "the the the..." degenerate case) with a brevity penalty for hypotheses shorter than the reference, and eight built-in smoothing methods for handling zero n-gram overlap ([NLTK API docs](https://www.nltk.org/api/nltk.translate.bleu_score.html)). Without smoothing, **BLEU returns exactly 0 if any n-gram order has zero overlap**, because the score is a geometric mean across n-gram orders. `nltk.translate.meteor_score` implements METEOR per Lavie & Agarwal (2007): sequential exact/stem/WordNet-synonym unigram matching, then a fragmentation penalty over the resulting alignment, tunable via `alpha` (precision/recall weight, default 0.9), `beta` (fragmentation-penalty shape, default 3.0), and `gamma` (fragmentation-penalty weight, default 0.5); the docs note it returns 0 outright if no words align ([NLTK API docs](https://www.nltk.org/api/nltk.translate.meteor_score.html)). Both are pulled in via `pip install nltk`. Both were designed for machine translation, where the standard use case is one hypothesis against reference translations of comparable length; applying them to summarization means scoring against reference *summaries* rather than the source, but the metrics themselves stay MT-shaped — BLEU is precision-oriented over the hypothesis's own n-grams, where ROUGE was named and designed to be recall-oriented over the reference's n-grams instead (Lin 2004, cited above). NLTK's own docs give no summarization-specific guidance for either metric.

### Embedding-based semantic similarity: BERTScore, MoverScore

- **BERTScore** (pip: `bert-score`) computes token-level cosine similarity between contextual embeddings of candidate and reference text, then greedily matches tokens to derive precision, recall, and F1 — "rather than exact matches ... employs contextual embeddings to assess token similarity" ([Zhang, Kishore, Wu, Weinberger, Artzi, "BERTScore: Evaluating Text Generation with BERT," ICLR 2020](https://arxiv.org/abs/1904.09675)). Latest PyPI release 0.3.13 (Feb 20, 2023); ~130 supported backbone models, with the README recommending `microsoft/deberta-xlarge-mnli` over the default `roberta-large` for better human correlation. The README states explicitly: BERTScore "can be computationally intensive... a GPU is usually necessary," similarity is undefined beyond 510 tokens per sequence (BERT's max length, so longer text is truncated), and — most relevant here — **it measures semantic similarity, not factual accuracy**, i.e. no hallucination/factuality check ([GitHub](https://github.com/Tiiiger/bert_score)). No archive notice on the repo as of this research.
- **MoverScore** applies Earth Mover's/Word Mover's Distance over contextualized (BERT/ELMo) embeddings — "a monolingual measure of evaluating the similarity between a sentence pair written in the same language" ([Zhao, Peyrard, Liu, Gao, Meyer, Eger, "MoverScore: Text Generation Evaluating with Contextualized Embeddings and Earth Mover Distance," EMNLP 2019](https://arxiv.org/abs/1909.02622)). Installable via `pip install moverscore` (v1.0.3, last released April 9, 2020, maintained on PyPI by paper co-author Wei Zhao) or by cloning the original repo directly ([GitHub `AIPHES/emnlp19-moverscore`](https://github.com/AIPHES/emnlp19-moverscore)). No commit activity since January 2023 — dormant.

### Trained/learned metric: BLEURT

BLEURT is "a trained metric, that is, it is a regression model trained on ratings data," transfer-learned from BERT/RemBERT and fine-tuned on WMT Metrics Shared Task human-adequacy ratings ([Sellam, Das, Parikh, "BLEURT: Learning Robust Metrics for Text Generation," ACL 2020](https://arxiv.org/abs/2004.04696); [GitHub](https://github.com/google-research/bleurt)). **No PyPI package** — install is `git clone` + `pip install .` (TensorFlow ≥1.15 and `tf-slim` required); a community PyTorch port exists separately (`pip install git+https://github.com/lucadiliello/bleurt-pytorch.git`). The most recent documented milestone is the BLEURT-20 checkpoint upgrade, dated October 8, 2021, in the repo's own README — no evidence of activity since, despite no formal archive notice. Because it's a *trained* metric, quality is bounded by its training distribution (WMT translation-adequacy judgments); applying it to summarization is a domain transfer the original paper doesn't evaluate.

### Benchmark/toolkit: SummEval

SummEval, "a toolkit for summarization evaluation to unify metrics and promote robust comparison of summarization systems," from Yale LILY and Salesforce Research ([Fabbri, Kryściński, McCann, Xiong, Socher, Radev, "SummEval: Re-evaluating Summarization Evaluation," 2020, arXiv:2007.12626](https://arxiv.org/abs/2007.12626); [GitHub](https://github.com/Yale-LILY/SummEval)) bundles 14+ metrics behind one interface — ROUGE, ROUGE-WE, BERTScore, MoverScore, Sentence Mover Similarity, SummaQA, BLANC, SUPERT, METEOR, S3, CIDEr, CHRF, BLEU, plus syntactic/statistical measures — alongside human-annotated relevance/consistency/fluency/coherence judgments over CNN/DailyMail system outputs. Install: `pip install summ-eval`. Last commit August 14, 2023 ("Merge pull request #45... update-rouge-install-commands"), with prior activity clustered in 2022 — effectively dormant. Best treated as a fixed benchmark/reference corpus plus a snapshot of how these metrics compare, not as a live dependency to build a pipeline on.

### Unified wrapper: Hugging Face `evaluate`

`evaluate` (pip: `evaluate`, HuggingFace Inc.) is a "community-driven open-source library for evaluation" that standardizes loading and running metrics — `load("rouge")`, `.compute()` — across NumPy/Pandas/PyTorch/TensorFlow/JAX, drawing on implementations (ROUGE, BLEU, BERTScore, METEOR, and others) hosted on the Hub's metric registry at `huggingface.co/evaluate-metric` ([PyPI](https://pypi.org/project/evaluate/)). Latest release 0.4.6 (September 18, 2025) — actively maintained. It invents nothing new: it's a convenience layer over the same `rouge-score`/`sacrebleu`/`bert-score` packages listed above, so its limitations are inherited from whichever metric you load, not intrinsic to the wrapper.

### Not an evaluator: `sumy`

`sumy` (pip: `sumy`, by Mišo Belica) is **a summarizer, not an evaluator** — "a simple library and command line utility for extracting summary from HTML pages or plain texts," implementing LexRank, LSA, Edmundson, and Luhn extractive algorithms ([PyPI](https://pypi.org/project/sumy/)). It does bundle a secondary `sumy_eval` command and "a simple evaluation framework for text summaries" for scoring its own output against references, but that framework is incidental to the package's purpose and not a general-purpose summary-quality library — including it in a "which evaluator should I use" comparison would be a category error. Latest release 0.13.0 (August 12, 2026) — actively maintained as a summarizer.

### LLM-as-judge: G-Eval, deepeval, ragas

G-Eval is a methodology, not a package: "large language models with chain-of-thoughts (CoT) and a form-filling paradigm" score generated text against custom criteria, without needing a reference summary at all ([Liu, Iter, Xu, Wang, Xu, Zhu, "G-Eval: NLG Evaluation using GPT-4 with Better Human Alignment," 2023, arXiv:2303.16634](https://arxiv.org/abs/2303.16634)). Evaluated on summarization and dialogue generation, GPT-4-based G-Eval reached **0.514 Spearman correlation with human judgment on summarization**, "outperforming all previous methods by a large margin" over ROUGE/BERTScore-class metrics — but the paper also documents a **self-preference bias**: LLM evaluators tend to score LLM-generated text more favorably. Two packages operationalize this approach:

- **`deepeval`** (pip: `deepeval`) ships both a generic `GEval` metric (custom-criteria LLM-as-judge) and a purpose-built `SummarizationMetric`: it generates closed-ended yes/no questions, answers them against both the source and the summary, and combines an **Alignment Score** (detects hallucinated/contradictory content) with a **Coverage Score** (detects missing content) as `min(alignment, coverage)` ([docs](https://deepeval.com/docs/metrics-summarization)). Very actively maintained — latest release 4.1.10, August 21, 2026 (3 days before this note).
- **`ragas`** (pip: `ragas`) is a broader LLM-app/RAG evaluation toolkit that also ships a named `SummarizationScore` metric: it extracts keyphrases from the reference context, generates questions about them, and scores QA-based **coverage** (ratio of correctly answered questions), optionally blended with a **conciseness** penalty (`1 - min(summary_len, context_len) / context_len`) via a weighting coefficient (default 0.5, applied as `coverage * (1 - coeff) + conciseness * coeff`) — explicitly designed so a summary that merely copies the source can't score perfectly ([ragas docs](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/summarization_score/)). It also supports rubric-style custom `DiscreteMetric`s for other LLM-as-judge criteria ([GitHub](https://github.com/explodinggradients/ragas)). Actively maintained — latest PyPI release 0.4.3 (January 13, 2026).

Raw prompting (asking any chat-capable LLM to score a summary 1–5 against stated criteria, optionally with CoT) is the zero-dependency version of the same idea; `deepeval`/`ragas` mainly add structured scoring, caching, and dataset-level aggregation on top.

### Self-check reliability: naive self-critique vs. SelfCheckGPT

"Ask the LLM to check its own output" covers two methodologically different things in the literature, with opposite evidence.

**Naive intrinsic self-correction** — one extra pass, same model, no external signal, asked something like "did you make any mistakes?" — is not well supported. Huang, Chen, Mishra, Zheng, Yu, Song, Zhou, "Large Language Models Cannot Self-Correct Reasoning Yet," ICLR 2024 ([arXiv:2310.01798](https://arxiv.org/abs/2310.01798)), find that intrinsic self-correction without external feedback fails to improve reasoning accuracy and can *degrade* it. Kamoi, Zhang, Zhang, Han, Zhang, "When Can LLMs Actually Correct Their Own Mistakes? A Critical Survey of Self-Correction of LLMs," TACL 2024 ([ACL Anthology](https://aclanthology.org/2024.tacl-1.78/), [arXiv:2406.01297](https://arxiv.org/pdf/2406.01297)), surveying the broader literature, report no consensus and mostly negative results for self-correction that lacks external or oracle feedback.

**SelfCheckGPT** (Manakul, Liusie, Gales, "SelfCheckGPT: Zero-Resource Black-Box Hallucination Detection for Generative Large Language Models," EMNLP 2023, [arXiv:2303.08896](https://arxiv.org/pdf/2303.08896); pip: `selfcheckgpt`, [GitHub](https://github.com/potsawee/selfcheckgpt)) is a different mechanism entirely, and it is evaluated: rather than one self-critique pass, it draws **N stochastic samples** from the same model on the same prompt and measures cross-sample consistency — the premise being that hallucinated content varies across samples while facts the model actually "knows" stay consistent. It ships five variants (`SelfCheckBERTScore`, `SelfCheckMQAG`, `SelfCheckNgram`, plus NLI- and prompt-based scorers); on the WikiBio benchmark the best variant (SelfCheck-NLI/Prompt) reaches AUC-PR 92.50 for detecting non-factual sentences, beating grey-box baselines that require access to token probabilities. Real cost: N generations per output (the paper uses N=20), not one extra call — meaningfully pricier than the naive version, but with actual detection evidence behind it. Latest PyPI release 0.1.7 (March 10, 2024); no releases since — dormant but not abandoned mid-project.

**Bottom line:** a single "did I hallucinate?" self-critique prompt is cheap but has literature actively arguing it doesn't work reliably without external grounding. The self-check approach that *is* validated for hallucination detection costs ~N× generation calls, not 1×.

## 3. Generation-side factor: context isolation for the summarizer itself

Separate from how the summary is *scored*, evidence exists that where/how the summary is *generated* affects its quality — specifically, whether the LLM produces it in a fresh, isolated context versus deep inside a long, cluttered multi-turn conversation.

**Irrelevant context measurably hurts accuracy.** Shi, Chen, Misra, Scales, Dohan, Chi, Schärli, Zhou, "Large Language Models Can Be Easily Distracted by Irrelevant Context," ICML 2023 ([arXiv:2302.00093](https://arxiv.org/abs/2302.00093)), introduce GSM-IC (Grade-School Math with Irrelevant Context) and find model accuracy drops sharply when unrelated information is present in the input, even when the model could in principle disregard it.

**Multi-turn conversations degrade generation reliability.** Laban, Hayashi, Zhou, Neville, "LLMs Get Lost In Multi-Turn Conversation," 2025 ([arXiv:2505.06120](https://arxiv.org/abs/2505.06120)), simulate 200,000+ conversations across six generation tasks and find an **average 39% performance drop** for multi-turn versus single-turn delivery of the same task. The degradation is mostly unreliability, not aptitude: models prematurely commit to assumptions early in a conversation, over-rely on their own earlier (possibly wrong) turns, over-weight the first and last turns, and produce more verbose output — and once off-track, they "get lost and do not recover."

Applied to summarization: generating the summary in a fresh, isolated context (source text plus instruction only, no accumulated unrelated conversation history) should outperform generating it deep inside a long-running multi-turn session. The mechanism is context cleanliness, not agency — any fresh single-turn call gets the same benefit; a subagent is simply one convenient way to force that isolation. This is a generation-quality lever, independent of and complementary to which evaluation metric (§1–§2) is used to check the result afterward.

## Practical recommendation

- **Quick sanity check, zero dependencies:** `difflib.SequenceMatcher.ratio()` plus a `Counter`-based token-overlap ratio. Good enough to catch a summary that's near-identical to the source (undercompressed) or wildly divergent (likely hallucinated/off-topic); not a quality score to optimize against.
- **Real quality scoring, general case:** `rouge-score` (Google's) for lexical fidelity, ideally loaded through `evaluate` for convenience, plus `bert-score` if paraphrase/abstractive credit matters — this pairing is what most current summarization papers report as a baseline.
- **Research-grade / cross-system comparison:** SummEval as the benchmark harness and reference human-judgment data, reporting ROUGE + BERTScore + MoverScore together the way the SummEval paper does, rather than trusting any single metric's correlation with human quality judgments.
- **Nuanced abstractive quality (factuality, coverage, custom criteria), when LLM budget is available:** `deepeval`'s `SummarizationMetric` (purpose-built alignment/coverage scoring) or a G-Eval-style custom-criteria prompt via `deepeval`/`ragas` — the G-Eval paper's 0.514 Spearman correlation is the strongest human-alignment number in this whole set, at the cost of LLM API calls, latency, and self-preference bias that a fixed formula doesn't have.
- **Hallucination check specifically, don't reach for a single "did you hallucinate?" self-critique prompt** — the literature (Huang et al. 2024, Kamoi et al. 2024) finds intrinsic self-correction without external feedback unreliable. If a self-check approach is wanted (no separate reference/source-grounded metric), use SelfCheckGPT's sampling-consistency method instead — it's the one actually validated for this, at the honest cost of N generations per output, not one extra call. `deepeval`'s `SummarizationMetric`/G-Eval-style prompting (source-grounded, not self-critique) remains the better-evidenced choice when LLM budget is available at all.
- **Before reaching for any evaluator, generate in a clean context.** If summarization currently happens inline in a long-running multi-turn session, moving it to an isolated call/subagent (source text + instruction only) is a free, well-evidenced quality lever (§3) — cheaper than any metric above and addresses generation quality rather than just detecting problems after the fact.
