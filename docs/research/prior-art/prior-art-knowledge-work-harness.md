# Prior art: a Claude Code harness for knowledge work

Disposition: historical (2026-09-06) [should-be-scoping-review]

Research note, 2026-08-16. Resolves wayfinder tickets #2–#6 (eranroseman/knowledge-harness). Scope: what already exists for the academic-research arc (question → literature → synthesis → draft → submit) on our substrate — fresh Obsidian vault under git, local Zotero as reference source of truth — and what we must build to hit the success criterion of zero fabricated citations. All API behavior in §5 was live-verified 2026-08-16; repo activity dates are from the GitHub API at research time.

## Summary: what exists vs. what we must build

**Exists and is adoptable.** The vault-format layer (kepano/obsidian-skills), the Zotero access primitives (Zotero local API, Better BibTeX JSON-RPC, pyzotero), a mature Zotero MCP server (54yyu/zotero-mcp), a settled set of Obsidian↔Zotero note conventions (citekey filenames, pandoc `[@key]`, managed/persist regions), and a completely free, live-verified citation-integrity API pipeline (doi.org → Crossref → OpenAlex → Semantic Scholar). Proven architectural patterns exist in the literature: PaperQA2's closed-citation-universe drafting, Elicit's quote-plus-locator evidence records, scite's stance-tagged citation statements.

**Missing — must build.** No official or community artifact combines these into a trustworthy pipeline on our substrate. The closest end-to-end suites either lack Zotero entirely under a non-commercial license (Imbad0202/academic-research-skills, CC-BY-NC 4.0) or match the substrate but are small and unproven (WenyuChiou/ai-research-skills, MIT, 207 stars). The citation-verification linter (draft citekeys → real Zotero items → live DOI/retraction checks), the source-note/claim-ledger scaffold, and the research-process skills are ours to author — as thin glue over the adoptable primitives above, in the Agent Skills format (https://code.claude.com/docs/en/skills) so they mirror to Codex.

## #3 Zotero surface (local API, Better BibTeX, watching for changes)

**Local read API — the primary search surface.** The Zotero desktop client serves a local implementation of Web API v3 at `http://localhost:23119/api/` (user library under `/users/0/`). Reads need no auth, only the pref Settings → Advanced → "Allow other applications…" (else 403); it works offline, has no rate limits, returns unpaginated results by default, and supports most Basics/Full-Text endpoints (https://www.zotero.org/support/dev/web_api/v3/local_api; stable, official, doc updated 2026-07-29). Zotero 8 added annotations and `/fulltext` endpoints to it. The cloud web API (https://www.zotero.org/support/dev/web_api/v3/basics; stable, official) is the reference spec the local API mirrors — needed only as a fallback for remote/group libraries.

**Local writes are version-gated.** Zotero 10+ adds POST/PUT/PATCH/DELETE to the local API, gated by a local API key from `POST /api/local/authorize` (triggers a user confirmation dialog); earlier clients return 501 (https://www.zotero.org/support/dev/web_api/v3/local_api; new in Zotero 10). The harness must feature-detect and treat local write as optional. Likewise `?since=` polling with `Last-Modified-Version` operates on per-library local versions **documented only for Zotero 10+** (same source) — not version-robust alone.

**Better BibTeX JSON-RPC — the citekey trust anchor.** BBT exposes an unauthenticated JSON-RPC 2.0 endpoint at `http://localhost:23119/better-bibtex/json-rpc` (https://retorque.re/zotero-better-bibtex/exporting/json-rpc/; stable API of an actively maintained plugin). Methods cover the citekey-centric workflow: `item.search` (CSL-JSON items tagged with citekey + library), `item.citationkey`, `item.export`, `item.bibliography`, `item.notes`, `user.groups`, `api.ready`. Critically, `item.attachments(citekey)` returns per-attachment `path: att.getFilePath()` — the **absolute disk path** of the PDF — plus a `zotero://open-pdf` URI and extracted annotations, verified in source (https://github.com/retorquere/zotero-better-bibtex/blob/master/content/json-rpc.ts). This is the only surface found that resolves citekey → PDF-on-disk directly.

**Watching for new items — the version-robust answer is auto-export, not polling.** BBT's "Keep updated" auto-export re-exports a library/collection on change (modes: on change / on idle / paused; targeted collection exports recommended over whole-library for performance) (https://retorque.re/zotero-better-bibtex/exporting/auto/; stable, long-standing). An on-change CSL-JSON/BibTeX export into the repo plus a file watcher or git diff detects additions on any Zotero 7+ client. BBT even has built-in git integration (`git config zotero.betterbibtex.push true` → pull/export/add/commit/push per export), with the documented caveat that the commit is not file-bound and will sweep up other edited files — so target a dedicated directory/repo or replace with the harness's own commit step (same source; flagged "for the technically inclined"). The only push feed is the **cloud-only** streaming API `wss://stream.zotero.org` (library-level topic events, no item data, API key for private libraries; not served by the local client) (https://www.zotero.org/support/dev/web_api/v3/streaming_api; stable, official) — ruled out for local-first.

**Python tooling.** pyzotero 1.13.7 (released 2026-08-14, Python ≥3.10; https://pypi.org/pypi/pyzotero/json; actively maintained) supports the local API via `Zotero(..., local=True)`; its docs still describe local mode as read-only (a November-2024 snapshot predating Zotero 10 write support) — treat local mode as read-only until it catches up. pyzotero now ships first-party extras (https://github.com/urschrei/pyzotero; new, from the long-maintained project, 1.4k stars): a CLI (`pyzotero[cli]`) and an MCP server (`pyzotero[mcp]`, run as `pyzotero-mcp`) exposing search, get_item, get_children, list_collections, list_tags, get_fulltext plus Semantic Scholar tools. A minimal first-party MCP/CLI surface — but no BBT citekey resolution.

**Third-party MCP.** 54yyu/zotero-mcp (https://github.com/54yyyu/zotero-mcp; active, pushed 2026-08-13, 4,667 stars, MIT, 530 commits) is the dominant server of ~8 found: 40+ tools, local (default, read-only) / web (read-write) / hybrid modes, BBT citekey lookup, PDF annotation extraction with page numbers, full-text, BibTeX export, add-by-DOI/URL/ISBN, optional embedding-based semantic search; explicitly lists Claude Code as a client. Tradeoffs for us: 40+ tools is context-heavy, and its semantic-search index is a derived layer — a trust-first harness must treat vector hits as hints, not evidence.

**Security note:** the BBT JSON-RPC endpoint has no authentication mechanism at all (searched docs and source) — any localhost process can read library metadata and disk paths once the Zotero pref is enabled. Accept as a known property of the local trust boundary.

## #4 Obsidian + Zotero conventions (note formats, plugins, vault access)

**Plugin landscape: one live bridge, two convention donors.**

- **ZotLit** (https://github.com/aidenlx/zotlit — moved from aidenlx/obsidian-zotero; active, pushed 2026-08-15, 990 stars, v2.0.1) is the actively maintained Obsidian↔Zotero bridge as of 2026. v2 supports exactly one configuration: Zotero 9+ with the ZotLit companion plugin; it reads Zotero via direct SQLite (works with Zotero closed), `obsidian://zotlit/...` protocol links, and an optional HTTP push channel (https://zotlit.aidenlx.site/docs/concepts/how-zotlit-connects-to-zotero).
- **Zotero Integration** (https://github.com/community-archive/obsidian-zotero-integration — transferred from mgmeyers to the community-archive org; caretaker mode, last push 2026-03-06, 1,750 stars, requires BBT) — legacy convention source, not a build target. Its Nunjucks templating contributed the `{% persist "name" %}` → `%% begin name %% ... %% end name %%` pattern: persisted regions survive mechanical re-import while the rest of the note is regenerated (https://github.com/community-archive/obsidian-zotero-integration/blob/main/docs/Templating.md; stable, documented).
- **Citations plugin** (https://github.com/hans/obsidian-citation-plugin; stale — last push 2024-06-13, 1,335 stars, 159 open issues) — do not build on it, but it established the `@{{citekey}}` literature-note title, title/authors/year frontmatter, and Pandoc-style insertion the ecosystem expects.

**The conventions to adopt wholesale (ZotLit v2 defaults, ecosystem-convergent):** note filename = citation key, in a dedicated `literature/` folder; frontmatter `title`, `related`, `collections`, `citekey` plus reserved identity keys `zotero-key`, `zotero-note-key`, `zotero-lastmod`; generated content inside `%%zt-managed%% ... %%/zt-managed%%` markers so human/agent prose outside survives regeneration (https://zotlit.aidenlx.site/docs/tutorial/first-note; stable v2 docs). Citekey links are pandoc-style and bracket-required — `[@key]`, `[@key, p. 3]`, `[@a; @b]`; bare `@key` is plain text. Links resolve via the frontmatter citekey property of notes that also carry a valid `zotero-key`, falling back to Zotero lookup (https://zotlit.aidenlx.site/docs/concepts/how-citekey-links-work). Net: **citekey is the canonical join key** — filename, frontmatter property, `[@key]` in prose, zotero:// backlinks, managed regions for safe regeneration.

**Citekey ownership — Zotero core stores, BBT generates.** Zotero gained a native Citation Key item field in 7.0.31 (Jan 2026); per Zotero dev dstillman: "The only change we made — in 7.0.31 — was to introduce an official Citation Key field… Any special functionality about citation keys is entirely BBT" (https://forums.zotero.org/discussion/130917/zotero-8-9-bbt-and-citation-keys; shipped in core, interplay still settling). ZotLit v2 reads only the native field (`zt.citationKey`) and "writes null when the Zotero item has no citation key" (https://zotlit.aidenlx.site/docs/how-to/configure-frontmatter-properties) — so **a stack without BBT gets null citekeys and broken `[@key]` resolution**. BBT keys are deterministic (`auth.lower + shorttitle(3,3) + year`, a/b/c disambiguation), pinnable, and stable regardless of which library subset is exported (https://retorque.re/zotero-better-bibtex/citing/; active, pushed 2026-08-12, 7,025 stars) — the foundation of a `[@citekey]` written today still resolving at submission time. BBT auto-export gives the repo a continuously fresh .bib/CSL-JSON so every vault citekey is verifiable in CI without Zotero running (https://retorque.re/zotero-better-bibtex/exporting/auto/), and the CAYW picker at `http://127.0.0.1:23119/better-bibtex/cayw` plus JSON-RPC `item.citationkey`/`item.search` provide the programmatic real-item check (https://retorque.re/zotero-better-bibtex/citing/cayw/).

**Programmatic vault access.** The Obsidian Local REST API plugin (https://github.com/coddingtonbear/obsidian-local-rest-api; active, pushed 2026-08-03, 2,798 stars) exposes vault CRUD at `/vault/{path}` on HTTPS 127.0.0.1:27124 (API-key bearer auth, self-signed cert), PATCH targeting a heading/block/frontmatter key, and an embedded MCP server at `/mcp/` with documented Claude Code configuration. The official Obsidian URI scheme supports only open/new/daily/unique/search/choose-vault — no content reads (https://obsidian.md/help/Extending+Obsidian/Obsidian+URI; stable, first-party) — so reads/verification go through the REST API or, for our git-tracked vault, direct file access (the simplest, most auditable path).

## #5 Citation-integrity APIs (existence, metadata match, retraction, contexts)

**The whole verification pipeline is free.** All legs live-verified 2026-08-16, total cost zero using mailto polite pools:

1. **DOI existence** — `GET https://doi.org/api/handles/{doi}`: responseCode 1 = resolves (payload has target URL), 100 = not found; agency-agnostic (Crossref, DataCite, mEDRA), no Crossref quota spent (https://www.doi.org/the-identifier/resources/factsheets/doi-resolution-documentation; stable). A hallucinated DOI fails here before any metadata work.
2. **Metadata match** — `GET https://api.crossref.org/works/{doi}?mailto=…` returns title/author/container/year for comparison against the draft's citation (https://www.crossref.org/documentation/retrieve-metadata/rest-api/; production, actively maintained).
3. **Retraction check — free in the same Crossref call.** Since Crossref acquired the Retraction Watch database (Sept 2023), a retracted work's record carries `updated-by[]` entries `{DOI of notice, type, source: "retraction-watch", date}`. Verified on the Wakefield paper (10.1016/S0140-6736(97)11096-0): `updated-by` holds both a 2004 `correction` and a 2010 `retraction` — so **filter `type=="retraction"`** (types: Retraction, Correction, Expression of concern, Reinstatement), never test mere presence (https://www.crossref.org/documentation/retrieve-metadata/retraction-watch/; RW data updated every working day).
4. **Cross-check / non-Crossref coverage** — OpenAlex `is_retracted` boolean ("per the Retraction Watch database") plus `cited_by_count` in one call: `GET https://api.openalex.org/works/https://doi.org/{doi}&select=is_retracted,cited_by_count` — verified false on a normal work, true on Wakefield (https://help.openalex.org/data/works/attributes/; stable field).
5. **DataCite branch** — Crossref `/works` 404s on DataCite DOIs (verified on 10.5281/zenodo.3678326). Fallback: DOI content negotiation against `https://doi.org/{doi}` with `Accept: application/vnd.citationstyles.csl+json` (also x-bibtex, RIS, text/x-bibliography) works across all agencies — closes the datasets/software/preprints gap (https://citation.doi.org/docs.html; stable, relocated from citation.crosscite.org).
6. **Citation contexts** — Semantic Scholar Graph API `GET /graph/v1/paper/DOI:{doi}/citations?fields=contexts,intents` returns the actual quoted citing sentences — the only free source of contexts among the surveyed services; `paper/DOI:{doi}` also gives citationCount, influentialCitationCount, externalIds (https://api.semanticscholar.org/api-docs/; active, S2AG ~214M papers).

**Batch/offline retraction checking:** the full Retraction Watch database is a single `retraction_watch.csv` in the public GitLab repo, committed daily at 23:00 UTC (verified: commits for 2026-08-13 and 2026-08-14) — a nightly `git pull` gives whole-vault batch checks with no API traffic and git-history auditability (https://gitlab.com/crossref/retraction-watch-data; daily automated commits).

**Rate limits / access models (as observed 2026-08-16):**

- Crossref: Public / Polite (`mailto=`) / Plus tiers; polite pool confirmed live via headers `x-api-pool: polite-single`, 10 req/s, 3 concurrent (https://github.com/Crossref/rest-api-doc/blob/master/api_tips.md; etiquette prose lives in the legacy repo, numbers verified live). Always send mailto.
- OpenAlex: keyless = 1,000 credits/day ($0.10), free API key (openalex.org/settings/api) = 10× ($1/day), 100 req/s hard cap, singleton lookup = 1 credit; paid tiers above (https://help.openalex.org/api/authentication/; **pricing model changed in 2026** — credit/USD budgets replaced the old polite pool). Register the free key.
- Semantic Scholar: free; anonymous pool "1000 req/s shared among all unauthenticated users" (throttles under load), free key = dedicated 1 req/s (https://www.semanticscholar.org/product/api). Request a key for reliability.
- Unpaywall v2 (`GET https://api.unpaywall.org/v2/{doi}?email=…`): free, no key, returns `is_oa`, `oa_status`, `best_oa_location` with a direct OA PDF URL — the legal full-text link for verifying claims against source text. Real email required (example.com → HTTP 422, verified). Documented 100k calls/day, but that page is JS-rendered and only cross-checked via secondary snapshots (https://unpaywall.org/products/api; rebuilt May 2025 under OurResearch).

**Counts are index-relative facts.** For 10.1038/nature12373 measured live the same day: Crossref 1,801, Semantic Scholar 1,808, OpenAlex 1,980 (https://api.crossref.org/works/10.1038/nature12373). Any count the harness records must carry its index and retrieval date — treating counts as absolute is itself a subtle fabrication class.

## #6 Assistant architectures (how trustworthy pipelines are actually built)

**PaperQA2** (https://github.com/Future-House/paper-qa; active, v5+ codebase = "PaperQA2", CalVer since Dec 2025) separates answering into three phases — Paper Search, Gather Evidence, Generate Answer — where the answer prompt sees only top-scored evidence summaries, never raw retrieval, with config gates (`evidence_relevance_score_cutoff`) dropping weak evidence pre-draft. Its RCS step has an LLM score each chunk 0–10 and summarize it, "prevent[ing] irrelevant chunks from appearing in the RAG context" (https://arxiv.org/abs/2409.13740; stable research artifact, Skarlinski et al. 2024). The citation universe is prompt-constrained: "Only cite from the context and only use the valid keys", keys resolving to source + page range. **Patterns to copy:** (a) physically separate "collect and score evidence into vault notes" from "draft only from collected evidence"; (b) drafts may only use citekeys from the closed Zotero/BibTeX set, making every citation mechanically lintable. Its WikiCrow eval also donates the audit rubric — grade every statement *cited-and-supported / missing-citation / cited-and-unsupported* (WikiCrow: 86.1% / 3.5% / 13.5% vs human Wikipedia 71.2% / 13.6% / 24.9%) — and the precision-vs-accuracy-with-refusal framing ("insufficient information" as a valid answer) (same paper).

**STORM** (https://arxiv.org/abs/2402.14207; NAACL 2024; repo stanford-oval/storm maintained but slowing, ~31k stars, pip `knowledge-storm` v1.1.0 Jan 2025) splits pre-writing from writing: perspective-guided questioning builds a curated reference set R; the writing stage retrieves **only from R**. A rule-based trust filter gates what enters R before anything can be cited. **Patterns to copy:** source admission happens at ingestion (harness equivalent: nothing is citable unless admitted into Zotero as a vetted item), and drafting cites only the frozen curated set. STORM's own eval (84.83% sentences supported) names the failure modes beyond citation existence: improper inferential linking, inaccurate paraphrasing, citing irrelevant sources, over-speculative cross-source connections, and bias/tone inherited from sources — verification must check claim-to-passage entailment and inter-claim linkage, not citekey presence.

**gpt-researcher** (https://github.com/assafelovic/gpt-researcher; active, ~29k stars) is the **anti-pattern**: planner/executor split with frequency-based aggregation as its anti-misinformation strategy ("choosing the most frequent information" across 20+ scraped sites) and source-level, not passage-level, citations with no claim-to-source entailment check anywhere in the docs (https://docs.gptr.dev/docs/gpt-researcher/getting-started/introduction). Repetition across web sources must never substitute for tracing a claim to a located passage in a vetted reference — that line separates it from PaperQA2/Elicit/scite.

**Elicit** (closed-source; first-party docs) extracts directly from papers with highlighted source locations and supporting quotes per extracted claim (https://support.elicit.com/en/articles/552897). **The quote-plus-locator record is the core vault convention to adopt:** every extracted claim in an Obsidian note carries the verbatim quote and locator from the Zotero-held source. Its Reports eval (17 PhD graders, top-5 claims per report, full/partial/unsupported citation support; notes most rivals "do not cite specific passages") is a ready-made human-eval protocol (https://elicit.com/blog/elicit-reports-eval/; March 2025). Its Systematic Review eval — screening recall 93.6–96.4%, extraction accuracy 94–99.4%, every decision inspectable and overridable (https://elicit.com/blog/how-we-evaluated-elicit-systematic-review; March 2025) — calibrates expectations: even the best pipeline needs a human checkpoint. Elicit's Factored Verification paper (https://arxiv.org/abs/2310.10627; George & Stuhlmüller 2023) is directly implementable: decompose a summary into atomic claims, LLM-score each for source support; measured 0.62–1.55 hallucinations per average paper summary across frontier models (self-correction lowers to 0.46–0.95) — so a post-draft verification pass is not optional.

**scite** (paper: https://direct.mit.edu/qss/article/2/3/882/102990/scite-A-smart-citation-index-that-displays-the, QSS 2021, DOI 10.1162/qss_a_00146; product: https://scite.ai/features, commercial, active 2026) models a citation as a quoted citing sentence plus a classified stance — supporting / contrasting / mentioning — so contested claims can be weighed rather than counted. Its Assistant answers only against its own index (~1B searchable citation statements) so citations cannot point outside the corpus, and its Reference Check lints a manuscript's bibliography against Crossref/PubMed/Retraction Watch, flagging retracted and disputed references. **Patterns to copy:** stance-tagged citation storage in source notes, and a pre-submission Reference-Check-style lint (which §5's free pipeline implements). Caveat: scite pages block automated fetch; claims verified via domain-restricted search snippets.
