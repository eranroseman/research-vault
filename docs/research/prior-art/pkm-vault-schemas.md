# PKM vault schemas against primary sources

Research note, 2026-08-16. Feeds wayfinder ticket #7 (vault structure) of eranroseman/knowledge-harness. Scope: the seven common vault-schema families, each read against the source that owns it — not secondary write-ups — and judged for one design: a trust-first academic-research vault under git, Zotero as reference source of truth, citekey-keyed literature notes (ZotLit conventions, see prior-art-knowledge-work-harness.md §4), and a two-layer split under consideration (immutable evidence layer vs LLM-owned synthesis layer, per Karpathy's llm-wiki concept). Every claim cites the owning URL inline; unreachable primaries and unfounded claims are logged in Dead ends. This note lists options and trade-offs only — the structure decision is HITL in ticket #7.

**One-line map.** The schemas index on different dimensions: Zettelkasten on *connection*, PARA on *actionability*, LYT on *emergent curation*, Evergreen notes on *concept*, Johnny.Decimal on *number→location*, digital gardens on *maturity in public*, Obsidian-native on *machine-readable metadata*. Only two of the seven natively separate evidence from interpretation — Zettelkasten (reference apparatus vs Zettels) and LYT's ACCESS (Sources vs Cards folders) — and those two, plus Matuschak's concept-oriented synthesis pages and Obsidian properties/Bases as the carrier, are the composable parts.

## 1 Zettelkasten (Luhmann; zettelkasten.de)

**Core structure.** In Luhmann's own account, the slip box is a single numbered sequence with fixed placement: give "every slip a number" and "never change this number and thus the fixed place"; continuation and interpolation happen by branching — "57/12 can then be continued with 57/13" or supplemented "by 57/12a or 57/12b" — enabling "internal growth" without a fixed topical outline (Kuehn's translation of "Kommunikation mit Zettelkästen": https://luhmann.surge.sh/communicating-with-slip-boxes — the hosting page states no original publication date; the canonical hosting after scriptogr.am shut down, per https://zettelkasten.de/posts/luhmann-essays-online/). Retrieval runs through "a register of keywords that we constantly update" — the index, not the numbering, is the entry point. The modern canonical treatment (https://zettelkasten.de/introduction/; Sascha Fast, 2020-10-27, maintained) adds three working note kinds: atomic Zettels ("one knowledge building block per note" — "the principle of atomicity"), **structure notes** ("a Zettel about other Zettels and their relationships") and hub notes. IDs today are time-based (e.g. `202006110955`) or arbitrary-unique; the site recommends time-based for portability.

**Note-type provenance — a correction that matters.** The fleeting/literature/permanent trichotomy usually presented as "the" Zettelkasten method is Sönke Ahrens' vocabulary (*How to Take Smart Notes*, 2017), not Luhmann's. zettelkasten.de's explainer states the terms are due to Ahrens and — critically for us — that in Ahrens' own usage "a literature note is a source reference in a reference manager, such as Zotero," not a note in the Zettelkasten; permanent notes are "written as if for print" and carry "the necessary information in themselves in a permanently understandable way" (https://zettelkasten.de/posts/concepts-sohnke-ahrens-explained/; F. Lengyel, 2022-02-10). So the primary-source lineage already puts literature/reference material *outside* the thinking system, in the reference manager — exactly our Zotero-as-source-of-truth decision.

**Linking discipline.** Links are not enough: "If you just add links without any explanation you will not create knowledge" — every link needs stated context explaining why the connection exists (https://zettelkasten.de/introduction/). Luhmann recorded connections "radially" with backlinks written into the linked-to slips, and valued the system for yielding "combinatorial possibilities which were never planned" — "a kind of secondary memory, an alter ego with who we can constantly communicate" (https://luhmann.surge.sh/communicating-with-slip-boxes).

**Folgezettel debate.** Whether Luhmann's positional numbering (a note's meaning partly encoded by *where it sits* in the sequence) is essential digitally is formally unresolved. The site's own index of the "Great Folgezettel Debate" (~2015–2016 posts, https://zettelkasten.de/folgezettel/) records Daniel Lüdecke for ("Folgezettel are essential to Luhmann's style of working"; "Folgezettel provide context, links don't. They are not just one technique amongst many") and Sascha Fast against ("Folgezettel are one technique amongst many to implement an underlying principle"; "links provide vastly enriched contexts to connections"). No conclusion is declared; the site's practice (introduction, above) is direct links with context plus structure notes.

**Maintenance / shines / breaks.** High-discipline: atomizing, contextualizing links, and growing structure notes is continuous editorial work; the payoff (Luhmann's "surprises") only arrives at density. It breaks when notes are collected rather than reformulated — Luhmann is explicit that publications "do not result from simply copying what can already be found in the slip box."

**Academic-research fit.** Best of the seven. The evidence/interpretation split is native: bibliographic apparatus in the reference manager, excerpts as tools, Zettels as *own-words* synthesis carrying citations. The atomicity + mandatory-link-context rules translate directly into our claim-traceability requirement (one claim per unit, every link justified, every claim `[@citekey]` + locator). LLM ownership is clean for the synthesis side *if* the write-in-own-words and link-context rules are enforced as validators, and folgezettel is droppable: positional meaning is exactly the kind of implicit state an LLM (and a git diff) cannot see; explicit contextualized links carry the same information inspectably.

## 2 PARA (Tiago Forte, fortelabs.com)

**Core structure.** "Four top-level folders — Projects, Areas, Resources, and Archives — each containing a small number of subfolders." Projects are "short-term efforts (in your work or personal life) that you take on with a certain goal in mind"; Areas "important parts of your work and life that require ongoing attention"; Resources "topics you're interested in and learning about"; Archives "anything from the previous three categories that is no longer active" (https://fortelabs.com/blog/para/; Forte, published 2023-02-24, updated 2026-04-15 — actively maintained flagship post).

**Organizing principle.** Actionability, explicitly opposed to subject filing: "Instead of organizing information according to broad subjects like in school, I advise you to organize it according to the projects and goals you are committed to right now. This is what it means to 'organize by actionability.'" The optimization target is stated: "The ultimate system for organizing your life is one that is actionable," and "Your system has to give you time, not take time" (same URL).

**Linking/discovery.** None specified — PARA is a folder discipline, platform-agnostic; discovery is by knowing which time-horizon bucket a thing serves. Items drain toward Archives when "no longer active"; no formal transition rules are given beyond that (same URL).

**Maintenance / shines / breaks.** Lowest maintenance of the seven — four buckets, shallow depth, archive-by-default. It shines for operational life: active commitments surface, everything else sinks. It breaks precisely where a research vault lives: knowledge is cumulative, not project-scoped. A literature note is not more or less "actionable"; a topic synthesis serves every future project, so under PARA it either duplicates across project folders or rots in Resources/Archives when the current project closes.

**Academic-research fit.** Poor as the knowledge layer, useful as a sliver. There is no evidence/interpretation distinction — a note's folder encodes the *user's current commitments*, state an LLM cannot observe or own, and archiving active-becomes-inactive material is the opposite of an immutable evidence layer. The one adoptable element: a Projects-like area for *manuscripts and deliverables in progress* (drafts are genuinely project-scoped and do complete), kept strictly separate from evidence and synthesis.

## 3 LYT / MOCs / ACCESS (Nick Milo, linkingyourthinking.com)

**Core structure.** Two mechanisms at different levels. (a) **MOCs** — "An MOC is just a note where you collect a bunch of related notes, then you stare at it, and think," serving to gather, develop, and navigate ideas; unlike a table of contents it "doesn't have to follow a linear format" and is "constantly reshuffled" (https://blog.linkingyourthinking.com/notes/lyt-faq; Milo, first-party FAQ). (b) The **ACCESS** folder scheme, six top-level folders — Milo's own definition: "The ACCESS folder structure stands for: • Atlas • Calendar • Cards • Extras • Sources • Spaces. It's not the gospel. It's meant for you to tear apart and make your own." (https://x.com/nickmilo/status/1530162446459019265; Milo on X, May 2022; text recovered via search snippet — direct fetch blocked, see Dead ends). The published LYT Kit vault itself runs this layout (e.g. its FAQ lives at `Cards/` in https://notes.linkingyourthinking.com/Cards/LYT+FAQ). The current commercial iteration, Ideaverse Pro, has consolidated toward **ACE** — Atlas (knowledge), Calendar (time), Efforts (action) (https://www.linkingyourthinking.com/ideaverse-pro; product page, current).

**Organizing principle.** Anti-premature-structure. Folders "bury notes" and "reduce your potential avenues towards note retrieval"; MOCs curate access without limiting it — an "augmented overlay" adding "context without constraint, freedom without friction" (LYT FAQ, above). The founding statement of when to structure: make a MOC at a "Mental Squeeze Point," and "making MOCs don't distract from note creation/writing, they *are* note creation/writing" (https://forum.obsidian.md/t/on-the-process-of-making-mocs/1060; Milo, 2020-06-02 — the concept's origin thread). Lineage: Milo's "Maps" ("just notes with links to other notes") date to his Evernote period; folder-dominant frameworks rejected because "Our brains don't work naturally within a folder-dominant framework. It makes it difficult to develop ideas" (https://medium.com/@nickmilo22/my-pkm-story-3763985b7a3e; Milo, 2020-09-16). The IMF kit (2020) became LYT Kit v4 became Ideaverse (https://forum.obsidian.md/t/lyt-kit-now-downloadable/390; thread live since 2020, kit reported 70k+ downloads).

**Linking/discovery.** Links first; MOCs as curated middle layer between search and folders; the few folders are *types of thing*, not topics — which is the load-bearing observation for us: ACCESS puts external material (**Sources**) and own atomic ideas (**Cards**) in *different top-level folders*. That is a first-party folder-level evidence/synthesis separation. (Per-folder rationale page was not reachable; the six names and the kit's use of them are first-party — see Dead ends.)

**Maintenance / shines / breaks.** Medium: MOCs are gardening work by design (that is Milo's point — curation *is* thinking), and un-gardened MOCs silently stale. Shines for emergent topic organization at 100s–1000s of notes. Breaks if treated as a filing system: MOCs assert no completeness and no canonical hierarchy, so nothing guarantees a note is reachable from any map.

**Academic-research fit.** Strong for the synthesis layer specifically. A MOC is structurally what Karpathy-style LLM-owned topic pages are: a rewritable curation note over stable atomic material. LLM ownership is clean — regenerating/reshuffling a MOC destroys no evidence, and staleness is detectable (notes not linked from any topic page). The Sources/Cards split maps directly onto evidence-vs-synthesis folders. What LYT does not provide: any claim-grounding discipline (nothing requires a Card to cite a Source) — that must come from the Zettelkasten/our-own rules.

## 4 Evergreen notes (Andy Matuschak, notes.andymatuschak.org)

**Core structure.** No folders — a flat, densely-linked web of durable notes plus transient inboxes (reading inbox, writing inbox) feeding it; the practice's principles are themselves notes: atomic, concept-oriented, densely linked, "prefer associative ontologies to hierarchical taxonomies," written for oneself by default (https://notes.andymatuschak.org/Evergreen_notes; Matuschak's working notes, continuously tended, "better note-taking" reframed as "better thinking").

**Organizing principle — concept, not source.** "It's best to create notes which are only about one thing — but which, as much as possible, capture the entirety of that thing." Too broad and "links to that note will be muddied"; too fragmented and "you'll also fragment your link network" (https://notes.andymatuschak.org/Evergreen_notes_should_be_atomic). Notes are keyed to concepts rather than to books/authors/projects so that "you discover connections across books and domains as you update and link to the note over time"; organizing by source instead leaves "a scattered set of notes on the concept, perhaps referring to it by different names, each embedded in some larger document" (https://notes.andymatuschak.org/Evergreen_notes_should_be_concept-oriented). Note titles function as APIs — precise claim-shaped titles that other notes link through (linked from the atomicity note, same site).

**Linking/discovery.** Dense links over hierarchy, citing Bush: "The human mind does not work that way. It operates by association." Let "networks of related ideas gradually emerge, unlabeled" rather than presorting; "Tags are an ineffective association structure" is itself one of his notes (https://notes.andymatuschak.org/Prefer_associative_ontologies_to_hierarchical_taxonomies, quoting Ahrens' relocation test: "In which context will I want to stumble upon it again?").

**Maintenance / shines / breaks.** Highest skill-cost of the seven: claim-shaped titling and dense linking is expert editorial work, and Matuschak's system is explicitly personal ("write notes for yourself by default"). Shines at insight accumulation across sources over years. Breaks as a team/shared convention and provides no folder-level contract at all — nothing in the schema says where evidence stops and interpretation starts; his notes cite sources by link but the practice does not mandate locators.

**Academic-research fit.** The best available *specification of the synthesis layer's internal form*: concept-oriented atomic pages with API-like claim titles are close to ideal LLM-owned topic-page targets — regenerable, diffable, linkable, and the atomicity failure modes ("muddied links," "fragmented network") are checkable properties. But it must not structure the evidence layer: concept-orientation deliberately dissolves source boundaries, and our evidence layer needs the opposite (citekey-keyed, source-bounded notes). Use Matuschak inside `topics/`, never inside `literature/`.

## 5 Johnny.Decimal (johnnydecimal.com)

**Core structure.** Three fixed levels encoded in a number: Areas in tens ("Area `10-19` groups all of the categories from `10` through `19`"), categories as single numbers within the range, IDs after the decimal — `15.52 Trip to NYC` (AC.ID notation) (https://johnnydecimal.com/documentation/areas-and-categories, https://johnnydecimal.com/documentation/acid-notation). Hard bounds are stated: "A maximum of 10 areas are possible in a system," "A maximum of 10 categories are possible in each area," "A maximum of 100 IDs is possible in each category," and "everything in a Johnny.Decimal structure is only *two levels deep*. No more endless clicking down into nested-folder hell" (https://johnnydecimal.com/documentation/the-numbers). A separate index — the JDex — records what every number means (https://johnnydecimal.com/documentation/the-jdex).

**Organizing principle.** Number→location. The system's stated purpose: "To help you find things, quickly, with more confidence, and less stress" (https://johnnydecimal.com/documentation/introduction). Category design pushes compression: "Prefer fewer, broader categories" — granular `investments`/`budget`/`savings` "created ambiguity… Compress them in to one – `money`" (areas-and-categories, above). IDs allocate sequentially ("recent things have higher numbers"); overloaded IDs split ("Split the thing in to multiple IDs if it's getting too busy") (https://johnnydecimal.com/documentation/ids).

**Linking/discovery.** None between items — discovery is remembering/looking up the number in the JDex. That is the point: bounded, stable, speakable addresses ("easy for someone else to find that document again," https://johnnydecimal.com/).

**Maintenance / shines / breaks.** Low once designed, but the up-front taxonomy design is load-bearing and revisions are costly (numbers are promised to be stable). Shines for *administrative and archival* material across fragmented storage (files, email, shared drives). Breaks for living knowledge: research topics emerge, merge, and split, which is exactly what a capped, pre-designed decimal taxonomy cannot absorb; and it indexes on location, contributing nothing to claim-level traceability.

**Academic-research fit.** Reject for both layers, with one caveat. Our evidence layer already has better IDs than JD can offer — the citekey, which is content-derived, Zotero-anchored, and citation-compatible; topic pages need concept names, not numbers. An LLM parses AC.ID trivially, but there is nothing for it to *own* — number assignment encodes human taxonomy decisions. Caveat: JD's bounded-two-levels rule is worth stealing as a *constraint* (shallow vault, no nested-folder sprawl), and JD-style numbering could serve a cold archival corner (datasets, admin) if one ever exists.

## 6 Digital gardens and adjacent (Appleton; IMF; Jenks)

**Digital gardens (Maggie Appleton, first-party essay).** "Gardens present information in a richly linked landscape that grows slowly over time," organized by "contextual relationships and associative links" rather than chronology; her six patterns are topography over timelines, continuous growth, imperfection/learning in public, playfulness, intercropping, independent ownership (https://maggieappleton.com/garden-history; essay planted ~2020, last tended ~2021 — she dates her own pages: "I also include the dates I planted and last tended a post"). The exportable element for us is **epistemic-status metadata**: growth stages (seedling → budding → evergreen) plus planted/tended dates make a page's maturity machine-readable — precisely what an LLM-owned synthesis page should carry so readers (and validators) know how settled a topic page is. The publishing/learning-in-public ethos is orthogonal to a private research vault. Lineage she documents: Bernstein's "Hypertext Gardens" (1998) → Caufield's "The Garden and the Stream" (2015) → the 2018–2020 revival.

**IMF (Milo, pre-LYT — lineage note, not a separate schema).** The kit that became the LYT Kit was "IMF v3" (https://github.com/nickmilo/IMF-v3 — README says only "This is going to become the LYT Kit v4"). The acronym has no first-party written expansion: asked directly in the origin thread, Milo answered "Maybe IMF changes; I'm less attached to the name than to the principles" (https://forum.obsidian.md/t/lyt-kit-now-downloadable/390; 2020-05-25). The commonly-cited expansion "Index, Maps of Content, fluid Frameworks" survives only in community mirrors of the kit (e.g. https://github.com/cassioborgesmenezes/pkm-imf) — treat as community reconstruction (see Dead ends). Substantively IMF is subsumed by §3.

**Academic-vault workflows (Bryan Jenks).** Jenks' Zotero→Obsidian workflow (colored-highlight semantics, citekey literature notes, maturity tags) is the most-cited *academic* vault convention set, but no first-party text documentation exists: his blog entries for the 2021 Zettelkasten workflow and the 2023 Zotero setup guide are video shells with topic lists, no written schema (https://www.bryanjenks.dev/blog/my-2021-comprehensive-obsidian-zettelkasten-workflow, 2021-08-23; https://www.bryanjenks.dev/blog/tag/zotero). Excluded from schema treatment under the primary-source rule; the conventions we'd want from that lineage (citekey filenames, managed regions) are already covered first-party by ZotLit in the sibling note (§4 there).

## 7 Obsidian-native conventions (help.obsidian.md → obsidian.md/help)

**Properties.** "Properties allow you to organize information about a note. Properties contain structured data such as text, links, dates, checkboxes, and numbers," stored "in YAML format at the top of the file"; typed as Text, List, Number, Checkbox, Date, Date & time (plus Tags); defaults `tags`, `aliases`, `cssclasses`. The design statement that matters for an LLM-driven vault: "properties are meant for small, atomic bits of information that are both human and machine readable" (https://obsidian.md/help/properties; official help, current — note help.obsidian.md URLs 301 to obsidian.md/help/).

**Bases.** "A core plugin that lets you create database-like views of your notes" — sort/filter/view files by their properties, saved as `.base` files or embedded (https://obsidian.md/help/bases; shipped as core, current). Structurally: Bases turn frontmatter into queryable tables, which means *folder membership stops being the only machine-visible grouping* — a literature table (year, status, verified, topic links) can be a view over properties rather than a directory layout.

**Daily notes, templates, canvas.** Daily notes "opens a note based on today's date, or creates it if it doesn't exist" — intended for journals/logs (https://obsidian.md/help/plugins/daily-notes) — a ready-made append-only research-log slot. "Templates is a core plugin that lets you insert pre-defined snippets of text into your active note" with `{{title}}`/`{{date}}`/`{{time}}` (https://obsidian.md/help/plugins/templates) — sufficient for enforcing note-shape consistency without community plugins. Canvas "gives you infinite space to lay out notes and connect them" in the open JSON Canvas format (https://obsidian.md/help/plugins/canvas; format at https://jsoncanvas.org) — spatial and human-oriented; treat as presentation, not structure carrier.

**Folders vs tags vs links — no official doctrine.** Obsidian's help defines tags only as "Keywords or topics that help you quickly find the notes you want" (https://obsidian.md/help/tags) and takes no position on folders-vs-links organization (searched; only forum threads exist — see Dead ends). The closest authoritative-adjacent statement is CEO Steph Ango's *personal* vault essay (https://stephango.com/vault; CEO-personal provenance, not official docs): "I avoid folders because many of my entries belong to more than one area of thought"; "Most of my notes are in the root of the vault, not a folder," with a `categories` link-property plus Bases views instead, templates for everything ("collapse hundreds of future decisions into one"), and a handful of type folders (references, clippings) as the exception.

**Academic-research fit.** This is the carrier layer, not a competing schema: typed properties are the natural home of our claim/provenance metadata (citekey, zotero-key, status, verified-date), Bases give validators and humans queryable views over both layers without moving files, templates pin the two note shapes, daily notes host the run log. The official "human and machine readable" framing of properties is as close as Obsidian comes to endorsing LLM-legible structure.

## Implications for ticket #7

**Elements that compose into the two-layer design (evidence vs LLM-owned synthesis):**

- **From Zettelkasten:** the layer boundary itself and its rules. References live with the reference manager (Ahrens' literature note *is* a Zotero entry — https://zettelkasten.de/posts/concepts-sohnke-ahrens-explained/); citekey-keyed literature notes in the vault are the evidence layer's projection of Zotero (immutable in the ZotLit managed-region sense, sibling note §4). Synthesis must be own-words with every link contextualized and every claim carrying `[@citekey]` + locator — enforceable as validators, which is the trust-first version of Luhmann's discipline. Drop folgezettel: explicit links carry the same information without positional state a diff can't see.
- **From LYT:** MOCs as the *mechanism* of the LLM-owned layer — topic pages are curation notes the LLM may freely reshuffle/regenerate because they assert arrangement, not evidence. The ACCESS Sources/Cards split is first-party precedent for evidence and synthesis as sibling top-level folders. Adopt the "mental squeeze point" heuristic as the topic-page spawn rule.
- **From Matuschak:** the internal form of synthesis pages — atomic, concept-oriented, claim-shaped API titles, densely linked — with his two failure modes (muddied links / fragmented network) as reviewable properties.
- **From Appleton:** epistemic-status frontmatter on synthesis pages — growth stage plus planted/last-tended dates — so maturity is machine-readable and staleness detectable.
- **From Obsidian-native:** typed properties as the metadata carrier, Bases as query surfaces over both layers (literature table, unverified-claims view), templates pinning the two note shapes, daily notes as the append-only run log.
- **From PARA (sliver only):** a separate area for in-progress manuscripts/deliverables — genuinely project-scoped, completable, archivable — kept out of both knowledge layers.
- **From Johnny.Decimal (constraint only):** keep the vault shallow (JD's two-levels rule as a lint), reject the numbering.

**Reject, with reasons:** PARA as knowledge-layer structure (actionability is orthogonal to evidence; archiving fights cumulative synthesis; commitment state is LLM-invisible). Johnny.Decimal for both layers (citekeys and concept titles are strictly better IDs; capped pre-designed taxonomy fights emergent topics). Folgezettel numbering (positional semantics vs git/LLM legibility). Digital-garden publishing ethos (orthogonal to a private vault — keep only the maturity metadata). Jenks-workflow adoption as a convention source (no first-party text; ZotLit already owns those conventions first-party).

**Open options for the HITL decision (not decided here):**

- **Option A — minimal two-folder + properties.** `literature/` (citekey-keyed, evidence) + `topics/` (LLM-owned MOC/evergreen pages), everything else in root, kepano-style; all other grouping via properties + Bases. Lowest structure, maximal link-first purity; risks: no home for manuscripts/log, root sprawl.
- **Option B — ACCESS-derived four/five folders.** `atlas/` (topic pages, LLM-owned), `sources/` or `literature/` (evidence), `calendar/` (daily research log), `efforts/` (manuscripts, PARA-ish), optional `extras/` (templates, canvases, bases). Mirrors a proven first-party layout and gives every artifact class one home; risks: more folders than strictly needed, Sources vs literature naming must not fork from ZotLit's `literatures/` default (sibling note §4).
- **Option C — Zettelkasten-pure flat.** Flat vault, structure notes instead of a topics folder, layer distinction carried entirely by properties (`type: literature|synthesis`). Cleanest for links, but the evidence boundary becomes metadata-only — weaker as a trust boundary (folder-level immutability rules and git path-based protections become impossible).
- Cross-cutting choice either way: whether topic-page immutability/ownership is enforced by folder path (B), by frontmatter type (C), or both (A leans both) — this determines how CI protects the evidence layer from LLM writes.
