# Knowledge-Harness Foundation — Specification

**Status note:** This specification is the project's *current contract* — amendable in place with dated notes; each statement holds until a dated amendment or an absorbing artifact (code, a skill, an ADR, a plan) supersedes it, and the goal state is a spec fully absorbed into those artifacts. It is not a constitution: rationale and rulings accrete here between passes and should not be over generalized. They are periodically absorbed outward — only ADRs carry constitutional weight (the domain-modeling three-test bar decides what becomes one). Nothing here outranks an accepted ADR; everything here outranks memory. New entries name their nature — decided, corrected, deferred, or measured — never "ruled"; a correction of a mistake is not a decision and does not harvest as one.

Consolidates the resolutions of tickets #7–#14 of the [foundation map](https://github.com/eranroseman/knowledge-harness/issues/1). Written for a reader with no shared history; every design decision links its ticket, where the full rationale and research inputs live.

## 1. Purpose and success criterion

A Claude Code plugin for trust-first academic research on a personal knowledge vault. First workload: the academic-research arc (question → literature → synthesis → draft → submit), validated by a thin slice; analysis/reports, PKM daily loop, and long-form writing are later workload maps.

**Success criterion: trustworthy output.** Every claim traceable to a real source; zero fabricated citations; anything the harness helps produce is defensible under review. Knowledge work has no compiler, so the foundation manufactures one: every gate bottoms out in a mechanical check (a DOI resolves, a quote byte-diffs after normalization, a citekey exists in the exported bibliography), with LLM judgment confined to non-blocking, human-adjudicated findings.

## 2. Substrate and environment

- **Vault**: a fresh, private git repository, separate from this plugin repo, scaffolded by `setup-vault` from templates shipped in this repo ([#7](https://github.com/eranroseman/knowledge-harness/issues/7)). Plain markdown + YAML frontmatter; Obsidian-convention but not Obsidian-dependent — all machine operations work on files + git. **The vault is a structurally conformant OKF v0.2 bundle** (ADR 0001; author ruling 2026-08-20): root `index.md` carries `type: "index"` and `okf_version: "0.2"`; root `log.md` is the single-writer regeneration target (`okf.regenerate_log`) and carries `type: "log"`; every nested `index.md` remains reserved with no concept frontmatter; every other machine-owned concept Markdown file carries parseable frontmatter with a non-empty `type`. Our schema extensions use OKF's unknown-key liberality; fleeting human notes are the tolerated residual (frontmatter arrives at triage).
- **Reference source of truth**: local Zotero (v9 at time of writing) + Better BibTeX (BBT). Verified environment facts, with dates, live in [docs/environment.md](../../environment.md): local API reachable from WSL2 (mirrored networking), BBT JSON-RPC responding, Windows→WSL path translation via `wslpath` (live-verified).
- **Version-gated features**: Zotero 10 local writes (citekey pinning, marker write-back without plugin) are feature-detected, never assumed. On Zotero 9: citekey pinning is manual; no programmatic pin path exists (live-falsified — the native `citationKey` field populates even for unpinned items and cannot serve as a pin lint).
- **Preservation boundary**: the git vault preserves everything defensibility needs (managed regions, bibliography, events, tags); the evidence *artifacts* (PDFs, snapshots) live in Zotero storage, outside that boundary — recoverability depends on the user's Zotero sync/backup, and doctor persistently warns when the vault has no remote and when Zotero storage has no stated backup. (Solo scope: this is a stated boundary, not a compliance control.)

## 3. Vault structure ([#7](https://github.com/eranroseman/knowledge-harness/issues/7))

```
vault/
├── index.md       # reserved bundle root; type: "index" + okf_version: "0.2" frontmatter
├── log.md         # single-writer regeneration target (okf.regenerate_log); type: "log" frontmatter
├── inbox/         # fleeting inbox; citable sources NEVER enter here
├── literatures/   # evidence layer: citekey-keyed projections of Zotero
├── synthesis/     # LLM-owned synthesis pages and nested reserved index.md
├── log/           # harness-written append-only daily logs
├── projects/      # manuscripts/deliverables, one subfolder per piece
├── system/        # support artifacts: templates, bases, canvases; system/bibliography.json (BBT export)
└── AGENTS.md      # typed vault facts + routing, shipped by setup-vault
```

File conventions: daily log = `log/YYYY-MM-DD.md`, with `type: "daily"` and entries `- HH:MM <actor> — <action> [links]`; the shared **review inbox** = `inbox/review-queue.md`, with exactly `type: "review-queue"` frontmatter before its append-only body. Neither append-only ledger carries `generated`, because rewriting a header on append would violate the stronger byte-preservation contract. Every hold/warn/alert flow in §6–§7 writes here, and the inbox-drain convention reads it. Entry serialization: one markdown list line of inline fields — `- [id:: <check>/<target>/<date>] [check:: …] [target:: …] [result:: …] [actor:: …] [reason:: …]` — where `target` is a claim link `citekey#^id`, a file path, or a gate-run reference, and `id` is the composite `check/target/date`. **Acknowledgment is itself an append-only entry**: `- [ack:: <id>] [actor:: human:…] [reason:: …]`. A closure is bypassed iff a matching human acknowledgment exists; **ack scope is standing for that check+target pair until the target's content changes** (its `fixity-sha256` or file hash), then it must be re-acknowledged. **Inbox drain**: `project`'s resume orientation step surfaces unacknowledged entries **with count and age** (oldest-first; an age threshold escalates the display — the Whittaker inbox-rot guard: a warn queue nobody drains is a silent failure of the doctrine's liveness bound). **Acknowledgment affordance**: the acting skill composes the ack entry's syntax; the human act is consent plus reason text, never hand-written field grammar (forced formality gets circumvented — Shipman/Marshall).

- **Two-layer trust boundary**: `literatures/` is the evidence layer — machine-projected from Zotero, protected from LLM free-writing by **both** path rules (CI/hooks key on the folder) and frontmatter type (Bases-queryable). Defense in depth is deliberate.
- **Zotero is the only admission path for evidence.** The inbox is for fleeting notes; nothing becomes citable except by being admitted into Zotero (a human act) and imported. **Gate-design rule (slice finding, ruled 2026-08-22): a human gate exists only where judgment can differ per instance — repeated identical confirmations are a rubber-stamp factory that trains click-through and degrades every gate in the system.** Corollary for admission: the human act is the *decision*, not the typing — a human-curated set admits as one reviewable approval (list reviewed, approval + list hash recorded as provenance, machine performs the entries through Zotero's own consented write path); per-item ceremony over an already-decided list is the failure mode, not the shortcut. Per-item admission remains the norm where per-item judgment is real (ongoing research finds).
- **Literature notes**: filename = citekey; a managed region (bridge-regenerated, full re-render, never hand-edited — policed by a warn hook) above a free region where human/agent prose survives regeneration.
- **Synthesis index**: `synthesis/index.md`, created by `setup-vault` — a reserved, frontmatter-free canonical index (one line per page: wikilink + one-line gist, sectioned) that registry-first dedup queries and orientation reads.
- **Synthesis pages**: one `type: "synthesis"` note kind with block-anchored claims (`^claim-id`), title-as-filename, `status: draft | stable | deprecated`, and generation metadata. The LLM creates pages without human approval, still subject to `synthesis-conventions` thresholds (§7), and logs creation in the daily note.
- **Rejected**: PARA for knowledge layers, Johnny.Decimal, folgezettel, per-claim atomic files, activity-state folders. (Rationale + survey: [research/prior-art/pkm-vault-schemas.md](../../../research/prior-art/pkm-vault-schemas.md).)

## 4. Zotero bridge ([#8](https://github.com/eranroseman/knowledge-harness/issues/8))

- **In-repo bibliography**: a single BBT auto-export of **Better CSL JSON** (sorted) into the vault repo — the canonical, CI-lintable citekey universe. **Export scope: the entire user library** (ID in docs/environment.md) — no curation step between Zotero admission and the citekey universe. **Provisioning is a one-time human creation of the whole-library auto-export in BBT Preferences, guided and verified by setup-vault/doctor** (live-falsified 2026-08-20: BBT 9.0.55's public JSON-RPC hardcodes collection scope — `autoexport.add("//", …)` 404s "path is too short" before registration storage — so programmatic whole-library registration is impossible; the harness is observation/commit-only for this contract and never calls the collection-only `autoexport.add`). The staleness lint's on-demand comparison export uses the same whole-library scope (a targeted collection is a later performance option, not a trust boundary). No machine paths in the repo, ever; PDF paths resolve at use time via BBT JSON-RPC + a `wslpath` shim with per-machine gitignored config. **Two-tier citability (ruled 2026-08-22 — the slice exposed that the user library is multi-project, so library-present ≠ citable-in-this-vault):** the whole-library export remains the single SOURCE universe (tier 1 — resolution and metadata for imports); **a claim's citekey is citable only if its literature note exists** (tier 2 — `literatures/` membership IS the vault's citation universe: cite → registry-first import → note exists → check passes). Accidental cross-project citation fails loudly with the remedy one skill invocation away; no second membership file exists to drift. **The BibLaTeX file, when LaTeX drafting starts, is a harness-regenerated PROJECTION over tier 2** (ruled 2026-08-22, superseding the second-auto-export plan): `bibliography.json` filtered by `literatures/` membership, converted CSL→BibLaTeX — the `log.md` artifact class (machine-projected, regenerated whole, never hand-edited), not a second BBT universe; BBT stays sole writer of the one universe file, and a future human BBT-configuration step is deleted.
- **Trigger and ownership**: after the human creates that auto-export, BBT is the sole writer of `system/bibliography.json` (ruled 2026-08-21); the harness stages and commits genuine BBT output but never synthesizes or writes the export. Doctor waits up to 60 seconds for the auto-export to settle; a persistent absence or mismatch is reported UNMATCHED with the exact repair to perform in BBT Preferences — the harness never registers — and is re-verified on the next doctor run. The JSON-RPC on-demand export remains comparison evidence, not replacement file content. BBT's git mode stays off because its commits are not file-bound.
- **Note generation**: harness-owned (thin skill over JSON-RPC/local API) emitting ZotLit-convention notes — so ZotLit remains adoptable later as an interactive UI, never a dependency. Annotations extracted via BBT `item.attachments` (local API as fallback).
- **Citekey stability**: the git-diffed bibliography is the rename detector; keys are pinned manually on first citation; `item.regenerate_key`'s old→new mapping drives mechanical vault-wide renames — **rename propagation, driven by zotero-key identity match, covers every citekey-bearing surface**: filename, `[@citations]`, wikilinks, claim links in stance links, review-inbox targets and ack ids; Zotero 10 local writes become the programmatic pin path behind feature detection.
- **Direction**: one-way Zotero→vault. The only write-back is a presence marker (MarkDB-Connect `has-vault-note` tag). Content write-back is banned until Zotero 10 local writes AND per-event human approval. Two-way sync is **deferred behind the same Zotero 10 local-writes gate** (re-ruled 2026-08-23, superseding the earlier permanent rejection): the absence of successful prior art on this substrate is why it is not attempted now, not a permanent ban — it is revisited when local writes exist and the per-event approval path is proven.

## 5. Provenance schema ([#9](https://github.com/eranroseman/knowledge-harness/issues/9))

The vault adopts OKF's structural conventions while retaining the research-domain deviations that make its evidence boundary explicit: citekey/Pandoc attribution; `citekey`/`doi`/`url` rather than OKF `sources`/`resource`; typed `supports`/`disputes`; PRISMA screening states; and the richer project publication lifecycle.

| Kind                            | Required and optional frontmatter                                                                                                                                                                                                 |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Common concept                  | non-empty `type`; optional `description`; optional ISO-8601 `stale_after`; machine-written mutable concepts carry top-level `generated: {by: <actor>, at: <ISO-8601 datetime>}`, where `at` is the last meaningful content change |
| Literature (`type: literature`) | `citekey`; optional `doi`/`url`, `pmid`, `version`, `archive-url`, `authority`; day-one `accessed`; list `fixity-sha256`; `status: unscreened \| included \| excluded \| superseded`; `superseded-by` when superseded             |
| Synthesis (`type: synthesis`)   | `status: draft \| stable \| deprecated`; generation metadata; no Appleton `growth`, `planted`, or `last-tended` fields                                                                                                            |
| Project (`type: project`)       | `status: draft \| parked \| published \| corrected \| withdrawn`; generation metadata; publication appends a verified event                                                                                                       |
| Verification                    | `verified` is a list of `{by, at, check}` pass events; only genuine MATCHED checks append events                                                                                                                                  |

`managed-sha256` is bridge/verifier-owned metadata over the exact managed-region bytes. It is compared with the current managed region, with HEAD during pre-commit, or with an explicit fetched/passed CI base for committed edits, deletes, and renames. It remains part of canonical content.

Literature `fixity-sha256` values are OAIS whole-object fixity anchors and ack-scope triggers, never re-import change detectors; render-first managed-projection comparison governs no-op detection. `accessed` is preserved from day one. Optional `description` and `stale_after` pass through unchanged when present and remain absent when omitted; this adoption does not create a new staleness subsystem. `generated` participates in canonical content, while a byte-identical rerender preserves the earlier `generated.at` even when a later timestamp is supplied.

**Claims, inline, per claim** (never frontmatter-only — tags must survive per-claim relays). **Quotes are blockquotes** — the tag, citation, and anchor ride the claim line; the verbatim text sits in a blockquote under it:

```markdown
- (quote) [@smith2020, p. 12] ^c1
  > Mortality fell 12% (95% CI 8–16).
- (inference) The effect likely generalizes. [@smith2020] [confidence:: moderate] ^c2
```

Per-claim `status`: `live | deprecated` — deprecation is a **transition record** carrying `[deprecated-at:: <date>] [deprecated-by:: <actor>] [reason:: <code> …]` and, where a successor exists, `[superseded-by:: <claim link>]` (bi-temporal precedent: state changes get actor + date, matching the `verified`-event discipline). **Retraction acknowledgment** is an inline field on the citing claim — `[retraction-ack:: <code> …]` — defined here once; the update-notice gate, `publish`, and `evidence-conventions` all key on this single syntax. **Machine-written verification markers travel with the claim** (the relay principle applies to failures too): an UNMATCHED result stamps `[failed-verification:: <check>/<date>]` on the failing claim, cleared on a later MATCHED or human acknowledgment.

**Reason codes**: one small controlled vocabulary (defined in evidence-conventions; free-text elaboration allowed after the code) shared by import-source holds, deprecations, acknowledgments, and not-admitted records — so reasons are countable and Bases-queryable, never free text alone.

**Anchor durability (invariant)**: `^claim-id` values in managed regions derive from stable content (Zotero annotation key, else quote hash) — **never from render order** — so full re-render preserves every claim link. Quote claims capture Web-Annotation-shaped context at extraction time (`exact` + 32-char `prefix`/`suffix`) — nearly free at capture, unreconstructable later; the re-anchoring *cascade* stays deferred (§10).

- Evidence-boundary tag: `quote | paraphrase | inference | open-question` (open-question = a claim with no derivation edge — itself lintable).
- `[@citekey, locator]` carries pinpoints (parses losslessly to CSL `locator`+`label`).
- `^block-id` anchors claims; **`citekey#^claim-id` is the global claim link** (no adoptable donor among surveyed products as of 2026-08-16; the *model* has precedent — micropublications' Support/Challenge graphs, Wikidata's per-statement references — first implementation on this substrate, not first idea; qualified 2026-08-22).
- Synthesis claims add: `confidence` (inference-only), per-claim `status`+reason, generating agent + date, and typed `supports`/`disputes` stance links to claim links (the two CiTO senses are the whole stance vocabulary; corrected 2026-08-22).

**Event integrity**: actor convention (`human:<name>` / `knowledge_harness/<version>`, per the code's `AGENT_ACTOR`) applies to every generating/verifying identity. Note-level checks (DOI, metadata, update-notice) append verified events to literature frontmatter; claim-level quote events include the claim link and comparison target (`managed-region` or `source-text`) in `check`; publish events attach to the project. Machine-confirmed trust requires all applicable note-level checks and quote claims to match; human-reviewed additionally requires a `human:` event. Deterministic gate surfaces alone write these events, and CI recomputes their passes.

**Invariants**: deprecate-with-reason, never delete; contradictions preserved, never silently resolved. **Upgrade path (deferred)**: per-quote prefix/suffix re-anchoring + a machine-owned claim ledger (Option C), gated on a consistency check, only if the slice shows prose-parsing bottlenecks. Exact inline-field syntax is validated against Dataview/Bases parsers at build time.

## 6. Trust gates ([#10](https://github.com/eranroseman/knowledge-harness/issues/10))

**Doctrine**: detect always-on and free; enforce opt-in per surface. **Mandatory, judgment-independent closure exists only at the publish boundary**; deterministic offline checks may additionally close at pre-commit/CI exactly where the table says so. Every closed surface ships a named bypass artifact + a liveness bound before enabling — missing either is a defect. **Precision is a warn-tier obligation (added 2026-08-22): a warn-tier check class whose observed inbox precision collapses is itself a defect — to tune or demote — because a noisy queue trains click-through and degrades every gate (the rubber-stamp rule, §3); the closing checks are exempt by construction (deterministic, near-zero false-positive).**

- **The closed gate**: a Stop-hook publish gate (8-block bound; bypass: a documented manual bypass token recorded in the review inbox). **"Publish" = the `publish` skill action**, not branch merge. Arming: the `publish` skill writes a state flag file the Stop hook checks; the hook runs the closed checks, clears the flag on pass or explicit bypass, and is inert when the flag is absent. CI is the async auditor. Publish's concrete effect: sets `status: published` in the project's frontmatter, appends a `verified` event, commits and tags (`published/<project>-<YYYY-MM-DD>-<HHMMSS>`). Project `status` enum: `draft | parked | published | corrected | withdrawn`. Day-one disposition menu: mark-published (full gate run + effects above) / park (sets `status: parked`, nothing else) / keep-draft (no-op); deletion only on explicit request plus typed "discard". **Post-publish lifecycle** (IFCN corrections principle): a blocking-class alert or claim deprecation that targets an already-published project does not merely block the next publish — it opens a correction disposition: re-publish as `corrected` (new gate run, new `verified` event, new tag) or mark `withdrawn`; the original tag is never deleted.
- **Four-state results everywhere**: MATCHED / UNMATCHED / UNREACHABLE / SKIPPED. An outage is never reported as fabrication. The publish gate fails closed on UNREACHABLE (publishing waits); UNREACHABLE warns everywhere else. **SKIPPED is automatic-only and never permanent by silence** — produced when the item lacks the field the check needs (no identifier → identifier checks SKIPPED; no quote claims → quote check SKIPPED); never user- or agent-settable. Before SKIPPED sticks, `import-source` attempts **identifier discovery** (Crossref bibliographic query by title/author/year, PubMed lookup — the Citation-bot pattern): a DOI-less retracted paper must not be structurally exempt from the update-notice gate. Unresolvable items land in the review inbox with a reason code; SKIPPED results from publish-gate runs are recorded there too, so the gate run stays auditable.
- **Offline audit isolation**: synthetic `--offline` network outcomes may appear in explicit output but never mutate trust, markers, events, or inbox state. A genuine attempted outage remains a persisted UNREACHABLE. Surface sets decide blocking only; detection, pass events, current failure projection, markers, and inbox auditing are otherwise surface-independent.
- **Metadata author comparison**: ordered normalized family names; given names match on first initial; any divergence → review inbox.
- Passing results append `verified` events per §5; non-passing results go to the review inbox (§3). Adjacent deterministic lints (wikilinks resolve, frontmatter parses, tags present, managed-region edit warnings) ride the citekey row's placement.
- No adoptable prior art existed for this linter **at audit time (2026-08-16**, four repositories: [research/prior-art/adoptable-skills-audit.md](../../../research/prior-art/adoptable-skills-audit.md)**)** — it was built greenfield to this table. *(Scoped 2026-08-22: a later sweep found MIT citation-verification tools — medsci verify-refs, bibverify, harcx, bibtex-updater, CheckIfExist, hallucinator, HALLMARK's baseline registry — none audited against this substrate; the historical claim stands only as dated.)*

## 7. Skill inventory ([#11](https://github.com/eranroseman/knowledge-harness/issues/11))

**Control model: user-driven (Pocock).** Entry points ship `disable-model-invocation: true` (never in the model catalog — dissolves process-skill collisions); guard/reference skills are model-invoked AND user-invocable; `user-invocable: false` is reserved for future machine contracts (none ship). Plain descriptive names. Invocation policy must be correct in shipped frontmatter — `skillOverrides` cannot patch plugin skills.

- **Maintenance**: no dedicated maintenance skill beyond the nine — doctor mode + refresh mode own it, speaking the **fresh / stale / orphaned** vocabulary. Contradiction-probing and staleness repair form a separate cron-shaped maintenance lane (designed at build time), never the import path.
- **Shipped architecture**: deterministic-Python-core + thin-prompt-skill split (claude-obsidian's proven shape) for every skill with a mechanical core. **CLI, not MCP**: gate surfaces (pre-commit, CI) run where no MCP session exists, so the deterministic core ships as a CLI serving skills, hooks, and CI alike — one binary, one exit-code contract; **dependency discipline** (author ruling 2026-08-20, corrected same day by rethink audit — [research/rethink-audits/2026-08-20-zero-dep-rethink.md](../../../research/rethink-audits/2026-08-20-zero-dep-rethink.md)): minimal, pinned, audited runtime dependencies admitted case-by-case by **contract match** — default to the library for commodity hard problems; homebrew only when the contract mismatch can be named out loud — with nothing heavy imported on the gate path (hooks invoke the CLI per tool call, so import weight is latency; capability deps lazy-import), optional extras (`[pdf]`) lazy and feature-detected, vendoring preferred where behavior must stay frozen. First admissions under the rule: defusedxml in (commodity-hard XML), pydantic out (coercing exception-model validation vs four-state reporting); **diagnosis budget (ruled 2026-08-22, from the mutate4py day): when a pinned tool starts failing undiagnosed, set the budget BEFORE diagnosing — a named bound (e.g. two crashes or three hours), after which the alternative gets piloted in parallel while diagnosis continues — because incremental each-next-step-is-cheap commitment consumed a working day that a pre-set bound would have capped; the diagnosis itself may still be worth it (it was — mechanism, transferable harness hardening, exit criteria), but that call gets made at the bound, not discovered at exhaustion;** an MCP wrapper for external vault clients (Claude Desktop / other hosts querying the vault without the plugin) is a later-map option, and consumed MCP servers stay rejected per #8; `verify-citations` and `factcheck-draft` fork scientific-writing's offline audit scripts (SHA-256 claim hashing, verified-evidence-only counting) as starting points.
- **Dependency doctrine**: load-bearing capability is owned inline — no if-available branching anywhere in shipped text. Personal skills (grilling, domain-modeling, handoff, …) have **no plugin relationship**; composition is user-space (typed invocation, or routing lines in the user's own vault AGENTS.md). Docs may say "pairs well with." Vendored forks coexist harmlessly with installed originals (namespaced, typed-only, gate-protected; doctor reports duplication).
- **Two-flow accounting**: information flow (find → human admits via Zotero → catalog → integrate) fully owned; project flow (question → gap analysis → acquire → draft-under-Iron-Law → verify → publish) owned at minimal viability. Rich pipeline machinery (charter/outline/weave analogs) belongs to the later full-arc map.
- Hooks (§6) ship as plugin hooks, not skills.

## 9. Validation slice ([#14](https://github.com/eranroseman/knowledge-harness/issues/14), project chosen in [#13](https://github.com/eranroseman/knowledge-harness/issues/13))

- **Seed migration (re-ruled 2026-08-22 — just-in-time, superseding the up-front batch)**: this repo's research corpus migrates record-by-record; a migrating record's citations face vault-grade sourcing judgment and admit at migration time, scoped per note (the classification ledger is a candidate list, not a manifest — slice findings 11–12). The library holds what a scholar's search should surface; admission happens when something becomes citable-in-practice, never before.
- **Validation project (re-ruled 2026-08-22, superseding the #13 choice)**: **re-ask one of this project's own workshop research questions under the harness's rigorous process** (selected 2026-08-22: the trust-gates prior-art question) — real research with a real consumer, which makes §9's routing-around falsification clause an honest instrument (a synthetic exercise tolerates friction real work would not), folds the corpus-to-vault migration methodology (findings 11–12: re-author at the vault's bar) into the validation itself, and yields a with/without-harness baseline comparison as the deliverable. The machinery-exercise the retraction question uniquely offered (natural retraction firing, acknowledge-tag flow) is covered by the synthetic gate drill, which exists precisely as that decoupled home. The retraction question (*how much are retracted papers cited after retraction, and do notification tools reduce it?*) is demoted to an optional later exercise if natural-fire evidence is ever wanted beyond the drill.
- **Phases**: (0) scaffold + doctor → (1) seed migration → (2) `project` framing + gap analysis → (3) `find-sources` → human admits 15–25 papers → `import-source` with live hold policy → (4) 1,000–2,000-word evidence brief in `projects/` under the Iron Law, ~10 synthesis pages touched → (5) `verify-citations` + `factcheck-draft` adjudication → (6) `publish`. - **Validated when**: 100% of brief claims resolve mechanically per their tag — quote = normalize-then-exact pass against the source's managed region; paraphrase/inference = citekey + locator resolve to a real item; open-question = exempt from the denominator; `verified` events recorded and trust tier derivable in a Base; all drills caught per §6; seed migration lands with zero unresolved links per migrated note (just-in-time, per the re-ruling above); cold-resume works; the author judges the brief defensible. **Measured output (added 2026-08-22, ruling on the false-positive finding): the slice also records per-check-class review-inbox precision — author-adjudicated actionable findings over total findings — as data, not a pass bar; a numeric budget waits for this measured base rate (HALLMARK's rates are other detectors on other corpora).**
- **Falsified when**: any planted error survives to publish, OR the author routes around the vault to get the work done — friction failure is foundation failure.

### 10.1 Evidence layer and digest

- **Direct-PDF-text quote-verification leg** — day-one target is the managed region (§6); comparison target recorded in events so tiers upgrade retrofit-free. **Primary text source when built: Zotero local API `/fulltext` endpoints** (core-extracted, zero new dependency), pypdf as fallback for index lag and page-resolved locators. ### 10.2 Identity, records, and trust model

- **Rename-cascade record semantics** (claim-anchor red-team review 2026-08-22 — settle before the first real citekey rename) — `citekey#^claim-id`'s citekey half is mutable by design, but the §4 cascade's surface list omits verified-event check strings (events hard-code `quote:<citekey#^id>:<target>`) and the append-only ledgers; either horn breaks a record contract (rewriting events violates ADR 0002; leaving them stale orphans the address, and a post-rename stale UNMATCHED row can never clear). Standing acks key on check+target, so renamed targets silently lapse them. The same settlement decides the ADR-0004 successor question (may a citekey change once records carry it?) and the bulk-Refresh mitigation: whether the harness can DETECT unpinned cited keys (regenerate-preview vs current key over the cited set) — pinning is the one mechanism that makes key stability a guarantee rather than discipline.
- **Human-attestation minting path** (deferred 2026-08-24; issue #17's open half) — `human-reviewed` is derivable but structurally unreachable: no shipped surface mints a `human:` event, and §6's per-quote attestation is specified as an ack while `trust_tier` reads events.
