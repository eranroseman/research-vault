# Provenance schemas & evidence-boundary tags: prior art

Research note, 2026-08-16. Feeds decision ticket #9 (eranroseman/knowledge-harness) — "Provenance schema & evidence-boundary tags". Scope: WHAT gets recorded per claim and HOW it is anchored, in a git-tracked Obsidian vault with citekey-keyed literature notes. Out of scope (sibling tickets): Zotero data flow; verification/gate machinery. Builds on `research/prior-art/prior-art-knowledge-work-harness.md` §5–§6 (Crossref/RW/OpenAlex fields, Elicit quote+locator, scite stance tags, AgriciDaniel claim ledger). All web sources fetched 2026-08-16 unless noted.

**Requirements the schema must satisfy** (from ticket context): (a) every claim traceable to source + locator; (b) evidence-boundary tags — quote / paraphrase / inference / open-question — survive every relay; (c) rot-watching (retractions, dead links, changed sources) possible later without retrofit; (d) claims aggregable across sources by an LLM-owned synthesis layer; (e) queryable in-vault (Obsidian Bases).

## Summary

Eight bodies of prior art were checked at their owning sources. The strongest converging lesson: **every mature system stores redundant anchors** (Web Annotation stores three selectors per target; Hypothesis re-anchors through four fallback strategies; ICD 206 requires an unambiguous identifier *plus* date *plus* page *plus* descriptor) and **none deletes stale knowledge** (Wikidata deprecates with a reason qualifier instead of deleting; ICD 206 retains a record of dynamic sources). The evidence-boundary distinction the harness wants is not novel — it is PROV's quotation/derivation/generation triple, ICD 203's information/assumption/judgment triple, and micropublications' quotation-vs-claim distinction, all independently converging on the same cut. And the claim-level pinpoint locator needs no new convention at all: pandoc's `[@citekey, p. 12]` syntax is machine-parseable into CSL-JSON `locator` + `label`, so the repo's existing citation form already carries it losslessly (§6). The carrier constraint that shapes everything: Obsidian frontmatter is flat (six scalar/list types, nested objects unsupported in the Properties UI) and Bases queries only frontmatter properties plus file metadata — so per-claim provenance cannot live in frontmatter and must ride inline (Dataview-style fields or callout lines) anchored by block IDs, while per-note provenance (source identity, version, retrieval) belongs in frontmatter.

## 1. W3C PROV / PROV-O — the derivation vocabulary

**Core model.** PROV-O (W3C Recommendation, 30 April 2013 — https://www.w3.org/TR/prov-o/) expresses provenance as three Starting Point classes — `prov:Entity`, `prov:Activity`, `prov:Agent` — connected by starting-point properties `prov:wasGeneratedBy`, `prov:wasDerivedFrom`, `prov:wasAttributedTo` (plus `used`, `wasAssociatedWith`, `actedOnBehalfOf`, timestamps). Definitions (quoted from the spec):

- `prov:wasDerivedFrom` — "A derivation is a transformation of an entity into another, an update of an entity resulting in a new one, or the construction of a new entity based on a pre-existing entity."
- `prov:wasQuotedFrom` (expanded term; subproperty of `wasDerivedFrom`) — "cites a potentially larger Entity (such as a book, blog, or image) from which a new Entity was created by repeating some or all of the original".
- `prov:hadPrimarySource` (expanded term) — "cites a preceding Entity produced by some agent with direct experience and knowledge about the topic".
- `prov:wasGeneratedBy` — "Generation is the completion of production of a new entity by an activity."
- `prov:wasAttributedTo` — "Attribution is the ascribing of an entity to an agent."
- `prov:generatedAtTime` — timestamp of entity generation (expanded term).

**What PROV gives the four tags.** The evidence-boundary tags map onto PROV's own derivation taxonomy, which is the strongest argument they are well-founded categories rather than an invention: `quote` ↔ `wasQuotedFrom` (verbatim repetition), `paraphrase` ↔ `wasDerivedFrom` (transformation of a source entity), `inference` ↔ `wasGeneratedBy` a synthesis Activity attributed to an Agent (the claim is *generated*, not derived from any one source), and `open-question` has no PROV edge — it is precisely a claim with **no** derivation, which is itself the useful invariant (an open question carrying a `wasDerivedFrom` is a contradiction a linter can catch).

**Minimal frontmatter-sized projection.** Full PROV is graph-shaped and needs qualified relations (Usage, Generation, Quotation classes) that flat YAML cannot hold. The projection worth keeping: one field naming the derivation *type* (the tag itself), one field naming the source entity (citekey), one field naming the generating agent (`author: human | model-id`), one timestamp (`extracted:` / `generated:`). PROV's Entity/Activity/Agent split also cleanly names the three things a synthesis page must record per claim: what it says (Entity), which run produced it (Activity), who/what ran it (Agent).

**Maturity.** W3C Recommendation since 2013, stable, unrevised; the reference vocabulary every later system in this note (nanopubs, Web Annotation) builds on.

**On a literature note:** implicit — the note *is* an Entity `wasDerivedFrom` the source; only the per-claim tag + locator is recorded. **On a synthesis-page claim:** `wasGeneratedBy` matters — record the agent (model) and time, plus the list of source claims it aggregates (`wasDerivedFrom` each).

## 2. W3C Web Annotation Data Model — robust quote anchoring

**Core model.** The Web Annotation Data Model (W3C Recommendation, 23 February 2017 — https://www.w3.org/TR/annotation-model/) anchors an annotation to a segment of a target document via Selectors:

- **TextQuoteSelector** — `exact`: "A copy of the text which is being selected, after normalization"; `prefix`: "A snippet of text that occurs immediately before the text which is being selected"; `suffix`: the snippet immediately after. This is the reflow-surviving locator: it needs no page or offset, only the text itself plus disambiguating context.
- **TextPositionSelector** — `start`/`end` character offsets ("The first character in the full text is character position 0").
- **FragmentSelector** — `value` holds an IRI fragment, `conformsTo` names the fragment spec; for PDFs that is RFC 3778 (`#page=4`), for plain text RFC 5147, plus media fragments.

Robustness is explicitly multi-selector: "Multiple Selectors SHOULD select the same content, however some Selectors will not have the same precision as others," and "A Selector MAY be `refinedBy` 1 or more other Selectors" (e.g., FragmentSelector for the PDF page, refined by a TextQuoteSelector within the page).

**Deployed proof.** Hypothes.is ("Fuzzy Anchoring", 2013-04-22 — https://web.hypothes.is/blog/fuzzy-anchoring/) stores three selectors per annotation target (RangeSelector/XPath, TextPositionSelector, TextQuoteSelector with 32-character prefix/suffix) and re-anchors through four strategies in order — exact range, position, context-first fuzzy match on prefix/suffix, then fuzzy search on the exact text alone — using a modified google-diff-match-patch (Bitap): "We save the information about each target fragment in three different selectors, and while attempting to re-attach them to the document, we step through four different strategies." Over a decade of production use on arbitrary web pages and PDFs.

**Minimal projection.** The harness's Elicit-style "verbatim quote + locator" record is exactly a TextQuoteSelector (`exact` = the quote) plus a FragmentSelector (`page=N`). Prefix/suffix are cheap to capture at extraction time (Hypothesis uses 32 chars) and are what make re-anchoring possible after the source PDF is replaced by a better scan or a v2 preprint — without them, rot-watching a quote inside a changed document degrades to fuzzy search on the quote alone (Hypothesis's last-resort strategy). Worth carrying: `quote` (exact), `page` (or section), optionally `prefix`/`suffix`. Not worth carrying: character offsets (TextPositionSelector) — they die on any re-extraction of PDF text and are meaningless across text-layer variants.

**Maturity.** W3C Recommendation 2017, stable; Hypothesis implementation battle-tested since 2013.

**On a literature note:** per extracted claim, the verbatim quote and page; prefix/suffix if cheap. **On a synthesis-page claim:** no selectors — the synthesis claim anchors to literature-note *block IDs* (§8), which are the intra-vault equivalent of selectors; the quote lives once, in the literature note.

## 3. Nanopublications & micropublications — claim granularity and the tri-graph

**Core model (nanopublications).** A nanopublication (https://nanopub.net/) is three named RDF graphs: the **assertion** ("the main content of a nanopublication in the form of an small atomic unit of information"), the **provenance** ("describes how the assertion above came to be… for example a reference to the kind of study that was performed"), and **publication info** ("metadata about the nanopublication as a whole, such as when and by whom it was created and the license terms"). The distinction that matters for the harness: *provenance of the claim* (which source, what method) is a different record from *provenance of the record itself* (who wrote this note entry, when). The guidelines (working draft, undated — https://nanopub.net/guidelines/working_draft/) show `prov:wasDerivedFrom`/`prov:wasAttributedTo` in the provenance graph and `dct:creator`/`dct:created` in pubinfo, and recommend Trusty URIs as integrity keys: "The goal of the integrity key is to establish an identifier that can be used to check if a nanopublication has changed, thus enforcing the immutability of nanopublications." Trusty URIs (Kuhn & Dumontier, arXiv:1401.5775, 2014 — https://arxiv.org/abs/1401.5775) embed a cryptographic hash of the content in the identifier itself: "To make digital resources on the web verifiable, immutable, and permanent, we propose a technique to include cryptographic hash values in URIs."

**Core model (micropublications) — the counter-argument on granularity.** Clark, Ciccarese & Goble, "Micropublications: a semantic model for claims, evidence, arguments and annotations in biomedical communications", J Biomed Semantics 5:28, 2014-07-04 (DOI 10.1186/2041-1480-5-28; read via PMC — https://pmc.ncbi.nlm.nih.gov/articles/PMC4530550/ — after link.springer.com bot-blocked, see Dead ends). Micropublications critique the nanopub assertion as too context-free for science: nanopubs "model only assertions without substantive evidence backing", cannot chain claims to "foundational support", and lose the hedging/qualification that makes scientific claims defeasible. The micropublication model: a **Claim** with a **support graph** (DAG of statements, data, methods) and **challenge** relations, where "the minimal form of a micropublication is a statement with its attribution", and *direct quotations from source text are first-class evidence nodes*.

**What this says for the harness.** (a) Claim granularity: one claim = one assertion small enough to verify against one located passage — but *never stripped of its qualifiers*; hedges ("in mice", "n=12", "preprint") stay inside the claim text, not in metadata. (b) The tri-graph maps directly onto the note layers: assertion = the claim line; provenance = citekey + locator + tag; pubinfo = who/when/which-model wrote the line. (c) Support **and challenge** edges between claims (micropub) are the schema slot scite's supporting/contrasting stances need (prior-art note §6) — a synthesis claim should be able to list both `supported-by:` and `contested-by:` sources without retrofit. (d) Hash-based immutability (Trusty URI) is the same move as AgriciDaniel's content-addressed `.raw/` and git blobs (§7).

**Maturity.** Nanopubs: live ecosystem, guidelines still "working draft" (undated), server network operational since ~2013; niche adoption (life sciences). Micropublications: influential 2014 paper; the full model was never mass-deployed — adopt its *distinctions*, not its OWL ontology.

**On a literature note:** the tri-graph collapses to: claim line (assertion) + `[@citekey, p. N]` + tag (provenance) + note-level frontmatter authorship (pubinfo). **On a synthesis-page claim:** assertion = claim text; provenance = list of literature-note block refs with stances; pubinfo = generating model + date + synthesis-run id.

## 4. Wikidata — the mass-deployed claim-provenance schema

**Core model.** A Wikidata statement is property + value + optional qualifiers + **references**, each reference being property-value pairs (Help:Sources — https://www.wikidata.org/wiki/Help:Sources): `stated in` (P248) for publications/databases, `reference URL` (P854) for web sources, `retrieved` (P813) — "the date when the data was taken from the web page", `quotation` (P1683) for exact text excerpts, plus `publication date` (P577), `archive URL` (P1065) and `archive date` (P2960) "for tracking changed URLs". Recommended per source type: books → `stated in` + `page(s)` (P304); databases → `stated in` the database item + the record ID.

**Rank instead of deletion.** Statements carry one of three ranks (Help:Ranking — https://www.wikidata.org/wiki/Help:Ranking): preferred, normal, and **deprecated** — for statements "known to include errors (i.e. data produced by flawed measurement processes, inaccurate statements) or that represent outdated knowledge." Deprecated data is retained, not deleted, which "prevent[s] accidental re-addition, document[s] the evolution of knowledge", and the qualifier `reason for deprecated rank` (P2241) records *why*. This is the largest deployed instance (≈1.6B+ statements) of exactly the rot-watch requirement: when a source is retracted or a claim superseded, the claim's row gains a status + reason — the claim never silently disappears, and downstream synthesis pages can see (and must relay) the deprecation.

**Minimal projection.** Per reference: `source` (citekey ≙ P248), `page` (≙ P304), `retrieved` (≙ P813, for web sources), `quote` (≙ P1683), `archive-url` (≙ P1065) for URL sources. Per claim: `status: live | deprecated` + `deprecated-reason: retracted | superseded-by | dead-link | …` (≙ rank + P2241). The `retrieved` date is the single cheapest rot-watch field — without it, "the source changed" is undetectable in principle.

**Maturity.** Production at Wikimedia scale since 2012; the reference/qualifier/rank model is stable and battle-tested by the messiest editing community there is.

**On a literature note:** references are implicit (the whole note is one source); `retrieved`/`archive-url` matter for web-native sources. **On a synthesis-page claim:** this is the model to copy most directly — claim + per-source references + status/reason lifecycle.

## 5. Intelligence-community sourcing standards — ICD 206 & ICD 203

Primary PDFs at dni.gov return HTTP 403 to programmatic fetch and the FAS mirror (irp.fas.org) sits behind an AWS WAF challenge — both read in full via Wayback Machine snapshots of the dni.gov PDFs (see Dead ends). Page cites below are to the signed documents.

**ICD 206, "Sourcing Requirements for Disseminated Analytic Products" (signed 22 January 2015; supersedes the 2007 version — archived from https://www.dni.gov/files/documents/ICD/ICD%20206.pdf).** Four sourcing mechanisms: source reference citations (SRC), appended reference citations, source descriptors, source summary statements (D.3). An SRC "shall be generated each time a source is directly cited in product text… or a specific aspect of analysis (i.e., judgment, assessment, estimate, alternative hypothesis or view, confidence level) depends on a source" (D.3.a.2) and "should reference the most original source" (D.3.a.4). Required SRC elements (D.3.a.6) include: identification of the originator/author; "An unambiguous source identifier… that enables unambiguous and efficient location and retrieval of the source"; title; "The date of issuance, publication, or posting. If date of online posting is unknown, then date of online access"; "Page number, if applicable"; and a **source descriptor** — glossary: "A brief, narrative exposition of factors that affect or indicate the quality or credibility of a single source", factors including "accuracy and completeness, possible denial and deception, age and continued currency of information, and technical elements of collection as well as source access, validation, motivation, possible bias, or expertise." A **source summary statement** assesses "quality, credibility, or validity factors that pertain for sources considered together". D.5 is the retention rule: for a source that is "dynamic (e.g., from an Internet posting), ephemeral… or not subject to… systematic storage", "a record of the source shall be preserved for retention… for at least one year" — the IC's version of the content-addressed raw copy (§7). The 2024 companion standard ICS 206-01 ("Citation and Reference for Publicly Available Information", 2024-12-02, listed at https://irp.fas.org/dni/icd/) extends this to open sources.

**ICD 203, "Analytic Standards" (signed 2 January 2015 — archived from https://www.dni.gov/files/documents/ICD/ICD%20203%20Analytic%20Standards.pdf).** Tradecraft standard D.6.e(3) is the direct ancestor of the evidence-boundary tags: "Analytic products should clearly distinguish statements that convey underlying intelligence information used in analysis from statements that convey assumptions or judgments. Assumptions are defined as suppositions used to frame or support an argument… Judgments are defined as conclusions based on underlying intelligence information, analysis, and assumptions." Mapping: underlying information ↔ quote/paraphrase; assumption/judgment ↔ inference; ICD 203's "information gaps" and required "indicators that… would alter judgments" ↔ open-question. D.6.e(2) governs uncertainty: likelihood must use one row of a fixed seven-term scale — *almost no chance / very unlikely / unlikely / roughly even chance / likely / very likely / almost certain(ly)* over bands 01–05% / 05–20% / 20–45% / 45–55% / 55–80% / 80–95% / 95–99% — "Analysts are strongly encouraged not to mix terms from different rows"; and (b) confidence in the *basis* for a judgment is a separate dimension: products "must not combine a confidence level and a degree of likelihood… in the same sentence." D.6.e(6) requires products to "acknowledge significant supporting and contrary information affecting judgments" — the stance requirement again.

**Minimal projection.** (a) The tag vocabulary itself, with ICD 203 as the definition donor: `quote`/`paraphrase` = underlying information; `inference` = judgment (and if the schema ever splits it, `assumption` is the proven third value); `open-question` = flagged gap. (b) An optional per-inference `confidence: low | moderate | high` kept *separate* from any likelihood wording inside the claim text (ICD 203's two-dimension rule). (c) A free-text source descriptor slot on literature notes (authority, access, bias, currency) feeding synthesis-time weighing. (d) Access date when publication date is unknown — already Wikidata's P813.

**Maturity.** Binding IC-wide policy for a decade, applied daily across agencies; the most operationally tested evidence-boundary discipline found anywhere in this survey. Its lesson is behavioral, not syntactic: the boundary must be visible *in the product* (per-sentence), not only in back-room records — i.e., tags must ride inline with claims, not live in frontmatter.

**On a literature note:** tag per claim; descriptor per source. **On a synthesis-page claim:** tag survives relay; inference claims may add `confidence:`; contrary sources must be carried, not dropped.

## 6. Scholarly citation locators — CSL, pandoc, JATS

**CSL.** The CSL 1.0.2 specification (https://docs.citationstyles.org/en/stable/specification.html) defines a `locator` variable rendered with `cs:label` ("the required `variable` attribute… must be set to 'locator', 'page', or one of the number variables"); Appendix II lists the locator terms: *book, chapter, column, figure, folio, issue, line, note, opus, page, paragraph, part, section, sub verbo, verse, volume*. The machine carrier is the CSL citation JSON schema (https://raw.githubusercontent.com/citation-style-language/schema/master/schemas/input/csl-citation.json): citation items have `id`, `itemData`, `prefix`, `suffix`, **`locator`**, **`label`**, `suppress-author`, `author-only`, `uris` — with the current `label` enum wider than the 1.0.2 spec appendix: `act, appendix, article-locator, book, canon, chapter, column, elocation, equation, figure, folio, issue, line, note, opus, page, paragraph, part, rule, scene, section, sub-verbo, supplement, table, timestamp, title-locator, verse, version, volume`. Note `timestamp` (audio/video sources) and `table`/`figure` — the pinpoint vocabulary already covers non-paginated media.

**Pandoc.** The manual's citation-syntax section (https://pandoc.org/demo/example33/8.20-citation-syntax.html; manual dated 2026-07-21) shows the locator riding inside the existing `[@citekey]` convention: `Blah blah [see @doe99, pp. 33-35 and *passim*; @smith04, chap. 1]` — prefix ("see"), locator ("pp. 33-35"), suffix, semicolon-separated multiple citations. Locator terms are recognized from the CSL locale ("page/p./pp., chapter/chap./chaps., section/sec./secs., volume/vol./vols.", figure, note, verse…); ambiguity is resolvable with braces — `[@smith{ii, A, D-Z}, with a suffix]` forces locator, `[@smith, {pp. iv, vi-xi} with suffix]` prevents locator parsing. Citation keys "must start with a letter, digit, or underscore and contain only alphanumerics plus internal punctuation (`:.#$%&-+?<>~/`)". So `[@smith2020, p. 12]` is not merely a display convention — it is machine-parseable (citeproc parses it into CSL-JSON `locator` + `label`), meaning **the repo's existing inline citation syntax already carries the claim-level pinpoint locator losslessly**.

**JATS.** The NISO JATS Journal Publishing Tag Library 1.3 (https://jats.nlm.nih.gov/publishing/tag-library/1.3/element/element-citation.html) models a reference as `<element-citation>` (fully structured) or `<mixed-citation>` (structure + free text), with children `<fpage>`/`<lpage>`/`<page-range>` (the cited work's own page extent), `<elocation-id>` (electronic articles without pages), `<volume>`, `<issue>`, and `<pub-id pub-id-type="doi">`. The useful negative finding: JATS locator vocabulary is *bibliography-entry-level* (where the cited article lives), not *claim-level pinpoint* — publishers' XML does not standardize "this sentence cites page 12 of the source". Pinpoint locators exist only in the CSL/pandoc layer. The harness schema must therefore keep both: bibliography-level metadata stays in Zotero/CSL-JSON export (sibling ticket), pinpoints stay with claims.

**Maturity.** CSL: the de-facto standard of Zotero/pandoc/citeproc, spec stable at 1.0.2. Pandoc: actively maintained, the repo's chosen citation surface. JATS: NISO standard underlying virtually all journal XML.

**On a literature note:** every extracted claim ends with `[@citekey, p. 12]` (or `sec.`, `table`, `timestamp` per CSL labels). **On a synthesis-page claim:** the same inline citation is *relayed verbatim* alongside the vault-internal block link — the pandoc form is what survives export to drafts, the block link is what supports in-vault navigation; carrying both is what makes the evidence boundary survive the relay out of the vault.

## 7. Content addressing for immutability — what version was this claim extracted from?

**Git blobs are free content addresses in a git vault.** Git "is a content-addressable filesystem… you can insert any kind of content into a Git repository, for which Git will hand you back a unique key" (Pro Git, Git Internals — Git Objects: https://git-scm.com/book/en/v2/Git-Internals-Git-Objects). The object ID is the SHA-1 of a `"blob <size>\0"` header plus content (`git hash-object`), so identical content always yields the same ID and any file committed to the vault already has an implicit, verifiable content address in history. (That chapter documents SHA-1 only; it does not discuss the SHA-256 object format.) Limitation: this only covers artifacts *inside* the repo — Zotero-managed PDFs on disk are outside git's reach, so a recorded hash field is substrate-independent where a git blob ID is not.

**AgriciDaniel/claude-obsidian — the deployed vault-native precedent.** Its provenance contract (https://raw.githubusercontent.com/AgriciDaniel/claude-obsidian/main/skills/wiki/references/provenance.md; v2.1.0 repo, MIT) uses SHA-256 "for source identity and delta checks". The source ledger (`wiki/meta/ledgers/source-ledger.json`) records per source: stable identity, **authority** ∈ `official | primary | secondary | community | synthetic | unknown`, SHA-256, retrieval/freshness (`refresh_due` — "Compute staleness from `refresh_due`; do not store a second stale flag"), review state ∈ `unreviewed | active | superseded | rejected`, linked pages; "File locators are vault-relative. Remote locators are absolute HTTPS URLs." The claim ledger (`wiki/meta/ledgers/claim-ledger.json`) records "falsifiable claims, note locations, support, contradictions, confidence, risk, and review state", assessment ∈ `accepted | provisional | contested | unsupported | deprecated`, with the instruction "Preserve contradictory evidence. Do not silently select a winner." The `.raw/` capture is described as "content-addressed byte capture" with a `.raw/.manifest.json` of ingestion hashes (exact filename pattern unspecified in the contract doc — see Dead ends).

**Metadata has versions too.** A DOI names the *work*, a hash names the *artifact*, and the registry record checked at extraction time is a third, independently drifting object. Crossref work records carry their own timestamps — live check 2026-08-16 on `https://api.crossref.org/works/10.1038/nature12373`: `indexed: 2026-08-12 (version 3.56.0)`, `deposited: 2023-05-18`, `created: 2013-07-30` — so "checked against Crossref metadata as of DATE" is recordable from the same call the verification pipeline already makes (prior-art note §5). This is what makes a later retraction *detectable as a change*: the claim's record says which metadata vintage was clean.

**Convergent precedents already covered above:** Trusty URIs embed the hash in the identifier itself (§3); ICD 206 D.5 mandates preserving "a record of the source" for dynamic/ephemeral sources (§5); Wikidata pairs `reference URL` with `archive URL` + `archive date` (§4). Four independent traditions, one rule: **record enough at extraction time to later prove what you saw** — hash (artifact identity), retrieval date (when), archive/raw copy (bytes), registry vintage (metadata state).

**Minimal projection.** Literature-note frontmatter: `source-sha256` (hash of the exact PDF/HTML the claims were read from), `retrieved` (date), and for web-native sources `archive-url`. Optional: `crossref-indexed` (date from the verification call). How hashes are later re-checked, and how raw copies are captured, is the verification/gate sibling's scope — the schema's only job is that these fields exist from day one, because none of them can be reconstructed after the source rots.

**On a literature note:** all of the above, once per note. **On a synthesis-page claim:** nothing — version identity is inherited through the citekey + block-ref chain; duplicating hashes at synthesis level would create divergence.

## 8. Obsidian carrier constraints

**Frontmatter properties** (https://obsidian.md/help/properties — note: help.obsidian.md 301s to obsidian.md/help/): six types — Text, List, Number, Checkbox (`true`/`false`), Date (`YYYY-MM-DD`), Date & time (`YYYY-MM-DDTHH:MM:SS`). Property names must be unique per note. **Nested objects are unsupported by the UI**: "Nested properties: To view nested properties, we recommend using the source mode" — i.e., nested YAML survives in the file but is invisible to the Properties editor and to property search. Markdown inside properties is likewise unsupported ("meant for small, atomic bits of information"). Consequence: frontmatter can carry *flat, per-note* facts (identity, version, dates, status, tag lists) but not a per-claim provenance table; a `claims:` list of objects would be uneditable and only partially queryable.

**Bases** (https://obsidian.md/help/bases, https://obsidian.md/help/bases/syntax): "a core plugin that lets you create database-like views of your notes… All the data in Obsidian Bases is stored in your local Markdown files and their properties." Three namespaces: `note.*` — "properties defined in the note's frontmatter"; `file.*` — implicit metadata (`file.name`, `file.path`, `file.ctime`, `file.mtime`, `file.tags`, `file.links`, `file.backlinks`, …); `formula.*` — computed in the `.base` file. Filters and formulas share one syntax. **Bases reads frontmatter, not inline fields** — the docs name no inline-field source, and `file.tags`/`file.links` are the only body-derived data exposed. So: anything that must drive a vault-wide dashboard (rot-watch status, verification state, note type, source identity) must be frontmatter; per-claim data is reachable by Bases only indirectly (via `file.links` backlink counts) or by external scripts reading the markdown.

**Inline fields — a community convention, not core.** Dataview inline fields (`Key:: Value`, bracketed `[key:: value]` inside sentences or list items, `(key:: value)` to hide the key in reading view — https://blacksmithgu.github.io/obsidian-dataview/annotation/add-metadata/) are the established way to attach machine-readable fields to a *line* rather than a note. Core Obsidian and Bases do not parse them (they render as plain text); Dataview (and its successor Datacore) and plain-regex scripts do. For an agent-first harness this is acceptable — the consumer of per-claim fields is the LLM/linter reading the file, not the Obsidian UI — but it is a dependency choice to make explicitly.

**Block references** (https://obsidian.md/help/links): append `^identifier` to a block; "Block identifiers can only consist of Latin letters, numbers, and dashes." Link syntax `[[note#^id]]`. Identifiers are persisted in the note text itself (they survive git, sync, and external editing), auto-generated as 6-hex strings by the picker or hand-written (`^smith2020-claim1`). Caveat from the docs: "Block references are specific to Obsidian and not part of the standard Markdown format" — pandoc and GitHub render `^id` as literal text (harmless but visible). Block IDs are the vault's native stable *intra-vault* claim anchor: a synthesis page cites a literature-note claim as `[[@smith2020#^c1]]`, and the link integrity is checkable mechanically (Obsidian resolves it; a linter can too).

**Consequence for the schema (the carrier verdict).** Two-level layout is forced, not chosen: **note-level provenance in frontmatter** (flat, typed, Bases-queryable: citekey, DOI, source hash, retrieval date, verification status, note kind) and **claim-level provenance inline** (tag + locator + stance riding on the claim's own line or an adjacent field line, anchored by `^block-id`). Filenames carry the citekey (already the repo convention), giving every inline claim a globally unique address `citekey#^block-id` for free.

## Candidate schema elements

Carried-where legend: **FM** = note frontmatter (flat, Bases-queryable); **inline** = on/next to the claim line (Dataview-field or citation syntax, parsed by agent/linter, not by Bases); **FN** = filename. Needed-for: **T** = traceability, **R** = rot-watch, **S** = synthesis.

| Element | Prior art (owning source) | Carried where | Needed for |
|---|---|---|---|
| `citekey` (join key) | CSL/pandoc key grammar (pandoc.org); repo convention | FN + FM | T |
| Evidence-boundary tag `quote \| paraphrase \| inference \| open-question` | PROV `wasQuotedFrom`/`wasDerivedFrom`/`wasGeneratedBy` (w3.org/TR/prov-o/); ICD 203 information/assumption/judgment | inline, per claim | T, S |
| Verbatim quote (exact text) | WADM TextQuoteSelector `exact` (w3.org/TR/annotation-model/); Wikidata P1683; micropub quotation node; Elicit | inline (blockquote under claim) | T, R |
| Quote context `prefix`/`suffix` | WADM; Hypothes.is 32-char contexts (web.hypothes.is) | inline, optional | R |
| Pinpoint locator (`label` + value: p./sec./table/timestamp) | CSL `locator`+`label` (citationstyles.org); pandoc `[@key, p. 3]`; ICD 206 SRC element (f) | inline, inside the citation | T |
| Block ID `^claim-id` | Obsidian block references (obsidian.md/help/links) | inline (end of claim line) | S |
| Source identifier (DOI / URL) | ICD 206 "unambiguous source identifier"; Wikidata P248/P854 | FM | T, R |
| Retrieval/access date | Wikidata P813; ICD 206 SRC (e) "date of online access" | FM | R |
| Artifact hash (SHA-256 of PDF/HTML read) | Trusty URIs (arXiv:1401.5775); AgriciDaniel SHA-256; git blob IDs | FM | R |
| Registry-metadata vintage (Crossref `indexed`/`deposited` at check) | api.crossref.org live record | FM (or check log) | R |
| `archive-url` (+ archive date) | Wikidata P1065/P2960; ICD 206 D.5 retention | FM (web sources) | R |
| Claim status + reason (`live \| deprecated:<reason>`) | Wikidata ranks + P2241; AgriciDaniel assessment enum | inline per claim; FM rollup for Bases | R, S |
| Stance (`supports \| contrasts \| mentions`) | scite; micropub support/challenge graphs; ICD 203 "contrary information" | inline, synthesis-page claims | S |
| Generating agent + timestamp | PROV `wasAttributedTo`/`generatedAtTime`; nanopub pubinfo (`dct:creator`, `dct:created`) | FM (note); inline (synthesis claim) | T |
| Confidence (`low \| moderate \| high`, inference-only) | ICD 203 D.6.e(2)(b) | inline, optional | S |
| Source authority descriptor | ICD 206 source descriptor; AgriciDaniel authority enum | FM (free text or enum) | S |
| Note review/verification state | AgriciDaniel review state; ICD 206 source summary statement | FM | R, S |

The single structural decision the carrier forces (§8): everything Bases must dashboard goes in flat frontmatter; everything per-claim rides inline anchored by block IDs; the citekey filename welds the two levels into one address space (`citekey#^claim-id`).

## Schema options (decision is HITL — ticket #9; none recommended here)

**Option A — "Minimal": tag + pinpoint + retrieval.**
Frontmatter: `citekey`, `doi`/`url`, `retrieved`, `status`. Claim line: tag as an inline field or emoji-free prefix, pandoc citation with locator, block ID; quotes as plain blockquotes.

```markdown
---
citekey: smith2020
doi: 10.1000/xyz
retrieved: 2026-08-16
status: unverified
---
- (quote) "Mortality fell 12% (95% CI 8–16)." [@smith2020, p. 12] ^c1
- (inference) Effect likely generalizes to X. [@smith2020] ^c2
```

Pro: hand-writable, zero new conventions beyond tags + block IDs; everything survives pandoc export. Con: no artifact hash or archive URL (rot-watch limited to DOI-level retraction checks — a silently changed web source is invisible); no stance or confidence slots (synthesis layer must re-derive); no per-claim status (a retracted source deprecates the whole note, not individual claims); no quote contexts (re-anchoring = fuzzy search on quote alone, Hypothesis's last resort).

**Option B — "Standard": the Wikidata-shaped middle.**
Adds to A — frontmatter: `source-sha256`, `archive-url` (web sources), `authority`, `verified` (date of last pipeline check); synthesis-claim inline fields: `stance`, `confidence` (inference only), `status`/`reason` per claim, generating `agent` + date on synthesis pages.

```markdown
- (paraphrase) Cohort mortality dropped by roughly an eighth
  [@smith2020, p. 12] [status:: live] ^c3

<!-- synthesis page -->
- (inference) The effect replicates across settings [confidence:: moderate]
  [supported-by:: [[@smith2020#^c1]], [[@jones2021#^c4]]]
  [contested-by:: [[@lee2022#^c2]]] [agent:: claude-fable-5] [date:: 2026-08-16] ^s1
```

Pro: covers all four ticket requirements (traceability, relay-surviving tags, rot-watch, synthesis) with zero sidecar files; every field maps 1:1 to a mass-deployed precedent (Wikidata/ICD/CSL); claims stay human-readable prose. Con: inline fields depend on the Dataview convention (not Bases-visible per-claim — dashboards see only note-level rollups); agents must maintain field discipline (a linter concern, sibling scope); moderate visual noise in reading view (mitigatable with `(key:: value)` hidden-key syntax). The sketch's exact inline-field syntax — wikilinks nested inside bracketed fields — is unvalidated against Dataview's parser; validate at implementation time.

**Option C — "Rich": annotation-grade anchors + claim ledger.**
Adds to B — per-quote `prefix`/`suffix` (32 chars, Hypothesis-style) for fuzzy re-anchoring; Crossref `indexed`/`deposited` vintage stamps; and a machine-owned ledger file (AgriciDaniel pattern: JSON per vault or per note) mirroring every claim: global ID (`citekey#^c1`), tag, locator, hash, status, stance edges — a flattened nanopub tri-record per claim.

Pro: Hypothesis-grade quote re-anchoring after source replacement; the ledger gives the synthesis layer and rot-watcher a single structured index without parsing prose; closest to the nanopub/micropub ideal of claims as first-class cited objects. Con: **two sources of truth** — note text vs ledger will diverge without a consistency gate (explicitly a dependency on the verification sibling); highest authoring friction (realistically agent-only maintenance); prefix/suffix capture requires extraction-time tooling; ledger JSON is invisible to Obsidian UI and un-reviewable in reading view.

**Cross-option invariants** (safe to fix regardless of choice): tags ride inline with claims, never only in frontmatter (ICD 203's per-sentence boundary; frontmatter tags cannot survive a per-claim relay); `[@citekey, locator]` is the locator carrier (already parseable by citeproc); block IDs are the intra-vault anchor; `retrieved` is recorded on day one (unreconstructable later); deprecation is a status change plus reason, never deletion (Wikidata); contradictory evidence is preserved, not resolved silently (AgriciDaniel, ICD 203 D.6.e(6), micropub challenge graphs).

## Dead ends / negative knowledge

- **dni.gov is closed to programmatic fetch** — both ICD PDFs return HTTP 403; the FAS mirror (irp.fas.org) serves its index page but fronts PDFs with an AWS WAF challenge (verified: `x-amzn-waf-action: challenge`). Both directives were read in full via Wayback Machine snapshots of the dni.gov originals (`web.archive.org/web/<ts>id_/` + local PDF read); WebFetch's own PDF extraction returned empty on these — `curl` + local read is the working path.
- **ICS 206-01** ("Citation and Reference for Publicly Available Information", 2024-12-02, listed on the FAS index) is the open-source-citation companion to ICD 206 — located but **unread**: dni.gov 403, FAS WAF, and Wayback CDX returned 503/empty for it at research time. Worth retrying before finalizing the schema's web-source fields.
- **The micropublications paper is bot-walled at its journal**: jbiomedsem.biomedcentral.com 301s to link.springer.com, which 303s into an auth wall. Read via PMC (PMC4530550). A guessed PMC ID (PMC4110023) resolved to an unrelated fungi paper — never trust recalled PMC IDs.
- **Nanopub guidelines are undated**: nanopub.net/guidelines/working_draft/ carries no status or date line; treat as living-draft convention, not a citable standard version.
- **Obsidian docs nowhere state Bases can read inline Dataview fields** — Bases data is "stored in your local Markdown files and their properties", and only `file.*`/`note.*` (frontmatter)/`formula.*` namespaces exist. Per-claim inline fields are agent/linter-readable only; do not design dashboards that assume otherwise. (help.obsidian.md also 301s wholesale to obsidian.md/help/ — consistent with the prior-art note.)
- **pandoc.org/MANUAL.html defeats single-fetch extraction** (too large; the citations section falls outside the retrieved window). The chunked build at pandoc.org/demo/example33/8.20-citation-syntax.html works; the guessable pandoc.org/chunkedhtml-demo/ path 404s.
- **JATS has no claim-level pinpoint vocabulary** — `<fpage>/<lpage>/<elocation-id>` describe the cited work's own extent, not where in it a claim lives. Pinpoints exist only in the CSL/pandoc layer; nothing to port from JATS beyond confirmation that DOI + page-extent belong to the bibliography layer (Zotero's job, sibling ticket).
- **PROV has no term for an open question** — a claim with no derivation edge is the representation; this absence is usable as a lint invariant (an `open-question` carrying a source citation is malformed).
- **CSL's spec appendix lags its own JSON schema**: the 1.0.2 spec lists 16 locator terms; csl-citation.json's `label` enum has 29 (adds `timestamp`, `table`, `version`, `elocation`…). Use the JSON schema enum as the locator vocabulary, not the spec appendix.
- **AgriciDaniel's `.raw/` filename pattern is unspecified** in its provenance contract (SHA-256 is named as the algorithm; the contract points to `.raw/.manifest.json` for hashes) — the *pattern* (hash-named files + manifest) is adoptable, the exact naming must be our own decision.
- **The Pro Git internals chapter documents SHA-1 only** (`"blob <size>\0"` header + content); it does not cover the SHA-256 repo format — if git blob IDs are ever used as long-lived content addresses in this vault, that format question needs its own check.
- **Obsidian block IDs don't survive outside Obsidian** — "Block references are specific to Obsidian and not part of the standard Markdown format" (obsidian.md/help/links): pandoc renders `^c1` as literal text. Export paths must strip or ignore them; the pandoc citation, not the block ref, is the export-safe locator carrier.
