# Partial adoption of a Claude Code plugin: every mechanism, tested — evidence

- **Date:** 2026-09-05
- **Method:** as the note records below (its own method section is unchanged)
- **Spec:** 2026-09-04-import-redesign-design.md
- **Binds:** nothing — evidence the spec was built from and absorbed; the spec is the current state, this file is not

Research note, 2026-09-05. An enumeration of the ways a third-party plugin can be adopted in part rather than whole, run by installing the shapes rather than by reading the documentation.

**What this artifact is.** A record of what the Claude Code plugin loader at 2.1.260 does when asked to take some of a plugin and not the rest. Every mechanism was tried against the two compile-step candidates at their pins, `AgriciDaniel/claude-obsidian` at `ad67087cad22ad84cc3288f915588ae42c0c2b44` and `nvk/llm-wiki` at `7c94c9bf2968f17deb496b285db0afdb610a01d9`, and against synthetic probe trees where a shape needed isolating. Scratch marketplaces were built under `/tmp`, installed, inventoried, and removed. Nothing in this repository was modified by the probes.

**What consumes it.** The compile section of the ingest redesign spec, `docs/superpowers/specs/2026-09-04-import-redesign-design.md`. Specifically §4.3, which proposes adopting claude-obsidian "through a curated marketplace entry, taking a subset of its components as-is and changing none of them", names the `agent-plugins` superpowers entry as its precedent, and lists two unverified mechanism facts as the plan's first tracer; and §4.3's second fallback, "the same curated-subset treatment of nvk/llm-wiki".

**Nothing here is a decision.** This note reports which shapes load, which shapes work, and what each costs. It does not rank the two candidates, does not recommend a mechanism, and does not choose one. It prices the options and leaves the choice to design.

**Conventions.** Two marks separate runs from reading. `tested` means the shape was installed on this machine on 2026-09-05 or 2026-09-04 and the reported inventory is what the harness printed. `read` means the fact comes from the installed binary, a manifest, or skill prose at the candidate's pin, with no install behind it. A row that was reasoned rather than run says so in its own column and is not stated as a result anywhere else. Component counts come from `claude plugin details` where it is reliable and from `~/.claude/debug/<id>.txt` where it is not; §7 records where the two disagree. Paths into candidate source are repository-relative at that candidate's pin.

## 1. Why this note exists

§4.3 of the consuming spec proposes one mechanism and cites one precedent. The mechanism is a marketplace entry with `strict: false` and an explicit component list against claude-obsidian. The precedent is the `superpowers` entry in `eranroseman/agent-plugins`, which uses that mechanism and demonstrably works.

The precedent works. The proposed mechanism, applied to this candidate, does not: it installs, it passes `claude plugin validate`, and it then loads nothing at all. §2 says why the precedent does not transfer, §3 gives the loader rules that decide it, and §4 prices every other shape that was tried.

## 2. How the sibling repository handles partial adoption today

`eranroseman/agent-plugins` uses three treatments. They are not alternatives to each other; they answer three different questions.

| Treatment                 | What it is                                                                                                                                                                                                                             | What it costs                                                                                                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Curated marketplace entry | The `superpowers` entry: `git-subdir` source, `url` obra/superpowers, `path: skills`, `ref: main`, `sha: b36e0829`, `version: 6.3.0`, `strict: false`, and a 13-element `skills` array of `./<dir>` paths. Upstream is taken unchanged | A pinned sha and a hand-kept name list, re-checked on every bump. A CI test that shallow-clones upstream at the pin and asserts every listed directory exists (spec §10.3), and a drift row watching upstream HEAD (§10.4)                                                        |
| Vendoring                 | `plugins/software-development/skills/brainstorming/`, 8 files copied whole from the pin, with only a provenance header and the `description` changed                                                                                   | A provenance header after the frontmatter, a LICENSE notice naming the sha, a byte-diff CI test against a clone at the pin, and a re-vendor on every bump. The spec's §7 is explicit that `name: brainstorming` stays so bare-name mentions in the other 13 skills keep resolving |
| Symlinked clone           | The Codex route: a clone pinned to the same sha, and 13 symlinks into `~/.codex/skills/`, driven by a hand-run loop with an `[ -e ]` guard (§9.2)                                                                                      | A second copy of upstream on disk, a hand-run loop, and a namespace inherited from upstream's `.codex-plugin/plugin.json` `name` field, which the repository does not control. §10.4 records the resulting drift signal                                                           |

Curation is the cheapest of the three, and the sibling spec reaches for it first. Vendoring is what you pay when you need to change a component rather than drop it: `brainstorming` is dropped from the curated entry and re-added, narrowed, from the local plugin. The symlinked clone is a harness-specific escape hatch, used only because Codex has no way to subset a plugin's `skills/` directory.

### What the precedent proves

`git-subdir` at `path: skills` makes the plugin root the `skills/` directory. That root contains no `skills/` subdirectory, so the default scan finds nothing and the entry's `skills` array is the complete set. The exclusion is geometric. Nothing subtracts `brainstorming`; nothing was ever added.

It is live on this machine and confirmed: `~/.claude/plugins/cache/eranroseman/superpowers/6.3.0/` holds all 14 upstream skill directories on disk including `brainstorming/`, while `claude plugin details superpowers@eranroseman` reports 13 skills, 0 agents and 0 hooks. Upstream's `hooks/hooks.json` and `.claude-plugin/plugin.json` sit outside the chosen root and are invisible. (tested)

### What the precedent does not prove

Six things, each established by probe rather than argued.

1. **It does not prove a `skills` list subtracts.** It proves the question never arises there, because the precedent's plugin root has nothing to auto-discover. Where a root does carry a `skills/` directory, the list adds: a probe root with `skills/pa` and `skills/pb`, `strict: false`, no `plugin.json`, and an entry listing only `./skills/pa`, loaded both. That is the exact shape of claude-obsidian's repo root, and it is the shape a natural reading of the precedent reaches for first. (tested)
2. **It does not prove hooks can be suppressed.** Upstream superpowers' hooks file simply sits outside the `skills` subdirectory. Three probes with `hooks/hooks.json` inside the root, one with no `hooks` key, one with `"hooks": {}`, one declaring only `skills`, all loaded the hook. (tested)
3. **It does not prove anything about a root carrying a `plugin.json`.** The precedent's root has none. Both candidates' natural roots have one. (read, then tested; see §3)
4. **It does not prove `strict: false` is the enabling ingredient.** Omitting `strict` loads fine, and entry lists work under `strict: true` as well; they just add. In the precedent, `strict: false` is doing one job only: permitting a plugin root with no `plugin.json`. (tested)
5. **It does not prove a stale list is caught.** A `git-subdir` entry on claude-obsidian at `path: skills` listing three directory names that do not exist at that pin loaded the plugin with zero skills and a non-fatal "Path not found" line. Nothing falls back to discovery and nothing fails the install. (tested)
6. **It does not prove the components you keep still work.** It proves they load. The precedent checks this precondition for itself at spec line 130: cross-directory references inside those 13 skills are sibling-relative, and no skill uses `${CLAUDE_PLUGIN_ROOT}`. Both candidates fail that precondition.

## 4. The comparison

**Rung criteria, applied uniformly.** The rung is stated relative to delivering this vault's compile step, not relative to loading something.

- **adopt as-is**: upstream's own manifests are used unchanged. Nothing of upstream is copied into this repository and nothing of upstream is edited. We add a marketplace and install.
- **adopt with config**: only our own marketplace entry or our own settings. Still nothing of upstream copied and nothing edited, and the components that load also work.
- **adapt**: a copy of upstream is carried in this repository, or an upstream file is edited in a fork.
- **build**: the behaviour is not present in any component and we write it.
- **unreachable**: the shape does not load at all, or it loads components that cannot work under that shape's geometry and no edit inside that shape repairs them.

A shape that loads the whole plugin takes its rung from what it delivers, so it reads `adopt as-is` even when a component list was written in the hope of subsetting. The list being inert is recorded under "what breaks".

## 5. What each viable mechanism would mean here

One subsection per mechanism that is not `unreachable`. The whole-plugin baselines are in §6. Each says what arrives in every session, what this vault would have to fence off, and what breaks when upstream moves.

**A caveat that applies to every claude-obsidian subsection.** The subsets actually installed were `{wiki-query, wiki-retrieve, wiki-lint, wiki, wiki-cli}` for the fork and shim shapes, and `{wiki, wiki-ingest, wiki-lint, wiki-fold}` plus the three agents for the vendoring shape. Only the last matches the set §4.3 names. Transitive closure over sibling references was checked for `wiki-query` and `wiki-lint`, which point at `../wiki-retrieve/`, `../wiki-cli/` and `../wiki/`. It was **not** checked for `wiki-ingest` and `wiki-fold`, so whether §4.3's four-skill set is closed is unverified.

### 5.1 claude-obsidian by sparse marketplace checkout

Arrives every session: the sparse-checked-out skills only, about 709 always-on tokens against the baseline's 2,313, with no agents and no hooks, because `agents/` and `hooks/` are never checked out. Subtraction happens at the marketplace-checkout layer, before the loader sees the tree, and it persists in `known_marketplaces.json` and survives `marketplace update`. Written with `--scope project`, the curation is a committable block in this repository's `.claude/settings.json`, which is the only shape that carries no copy of upstream and still keeps the curation in tracked configuration.

The vault must fence off the product's own verifier. File-level curation is incompatible with it: `config/capabilities.json` and `config/product-contract.json` enumerate all 15 skills, `bin/*.sh` and `hooks/hooks.json` as required implementation paths, so every removed file becomes a contract error and the report reads `ok=false, valid=false, 34 errors` even after `templates/` and `config/` are added back. `wiki-retrieve` stays `degraded` rather than `verified`, and `wiki-query`'s own protocol reads the prebuilt index only when the report marks it verified, so retrieval routes down the fallback path permanently. Whether that bites at all depends on whether a kept skill runs `contracts --verify`; `wiki-query` does, and §4.3 does not keep `wiki-query`.

When upstream moves: `git sparse-checkout set --cone` exits 0 and silently ignores paths that no longer exist, so a stale list degrades to fewer skills with no error. The drift check is the same shallow-clone-at-the-pin assertion the sibling spec's §10.3 already carries.

### 5.2 claude-obsidian by a one-file fork of its marketplace entry

Arrives every session: exactly the listed skills, plus all 3 agents and both hooks, plus the full working engine. The replace branch applies to `skills` only, so agents and hooks come along unless two further edits are made, one `plugin.json` line for agents and a deletion for hooks. The tree stays whole, so `contracts --verify` is byte-identical to an unmodified clone.

The vault must fence off two things. The hooks, if kept: a SessionStart matching `startup`, `resume`, `clear` and `compact`, and a Stop hook, both measured silent, so the fence is a `python3` spawn rather than tokens. And, if the hooks file is deleted instead, a permanently loud `contracts` report carrying one `missing_implementation_path` error, which upstream's own docs partly sanction: `skills/wiki/SKILL.md:108` calls hooks optional adapters and `references/install-modes.md:33` says they are "adapters, not core workflow logic".

When upstream moves: a fork to rebase on every release, and the skills array re-checked against the new tree, since a stale name degrades silently to fewer skills. This route also keeps upstream's plugin name, so the one qualified `claude-obsidian:` doc reference keeps resolving.

### 5.3 claude-obsidian by an in-tree shim

Arrives every session: exactly the listed skills, no agents and no hooks, and a working engine reached through relative symlinks whose `Path.resolve()` lands inside the vendored tree. Agents and hooks are excluded by geometry, because they sit under the vendored directory and not at the plugin root. No upstream file is edited.

The vault must fence off a collision this note tested today. The shim as originally probed used an empty marketplace root with a `skills` symlink at it, and this repository's root is already a plugin: `.claude-plugin/marketplace.json` names `knowledge-harness` with `"source": "./"`, `.claude-plugin/plugin.json` sits beside it, `skills/` holds nine of this vault's own directories, and `hooks/hooks.json` carries the vault's PreToolUse, PostToolUse and Stop hooks. A probe built to that geometry, with `strict: true` and a `skills` array mixing an own-skill path and a vendor path outside `skills/`, loaded exactly the listed two and left the unlisted own skill behind: the debug log reads `Checking plugin zzkhprobe: skillsPath=none, skillsPaths=2 paths`, and the vault's own `hooks/hooks.json` still loaded. So the shim needs no symlinks here, and it works. The price is that the entry's `skills` array becomes the roster for this vault's own skills as well as the vendored ones, and a tenth vault skill added without a matching array entry stops loading with no error.

When upstream moves: a re-vendor, about 3.8 MB in-tree without `.git`, and the array re-checked. The namespace is whatever the entry is named, since the manifest at the root is ours.

### 5.4 claude-obsidian by vendoring into our own plugin

Arrives every session: the four skills and three agents §4.3 names, about 837 always-on tokens, 36% of the baseline, and no hooks, because `hooks/` is simply not copied. `scripts/` and `claude_obsidian/` sit at the plugin root, so the `PRODUCT_ROOT` gate every skill opens with is satisfiable, which is the one precondition the precedent shape fails. This is the only route that both subsets the components and keeps the engine reachable without a fork.

The vault must fence off dangling advice rather than broken paths. `skills/wiki/SKILL.md:66-75` carries a router table pointing at `wiki-query`, `save`, `autoresearch` and `canvas`, four skills this subset drops. And `PRODUCT_ROOT` is a literal placeholder the model fills from the skill's own location, so vendoring makes the correct answer reachable without making it automatic.

When upstream moves: a re-vendor per sha, against a repository that ran 42 commits in 90 days. The sibling precedent's byte-diff test covered one 8-file skill; here it is 50 files and 1.1 MB including a 20-module Python package, so the drift check becomes a tree diff plus a file-mode check. The provenance header must be reapplied after every re-vendor, and editing the router table is the first thing that costs byte-identity.

### 5.5 claude-obsidian by symlink into `~/.claude/skills`

Arrives every session: each linked skill at a bare, unnamespaced name, with no hooks, no agents and no commands. The whole clone stays on disk beside the link, so the engine is reachable by path.

The vault must fence off nondeterminism. `${CLAUDE_SKILL_DIR}` is substituted to the symlink path unresolved, so a `cd "$DIR" && cd ../..` resolution lands in `~/.claude` and the `test -f` gate fails, while a literal `"$DIR/../../scripts/claude-obsidian.py"` succeeds. Both outcomes are reachable from the same input, and which happens is model behaviour rather than harness behaviour, so `PRODUCT_ROOT` has to be pinned by configuration. Name collisions with existing `~/.claude/skills` entries are silent and need an `[ -e ]` guard, exactly as the sibling spec's Codex loop does. Note also that this route puts skills outside any plugin, which is what makes the `<name>@skills-dir` per-skill mute of §4.3 available.

When upstream moves: the pin is the clone's HEAD, invisible to any manifest, so the drift check has to be a script rather than a CI assertion over a tracked file.

### 5.6 claude-obsidian as a plain dependency on its engine

Arrives every session: nothing. Zero tokens, no catalog entry, no hooks. The engine is 14 subcommands and a 20-module standard-library-only package, invoked by path from a skill this vault writes.

The vault must fence off nothing, which is the appeal. What it must accept is that the compile behaviour is not in the engine: there is no compile subcommand, and the compile step lives in the `wiki-*` skill prose. This route is `adopt as-is` for the mechanical half and `build` for the half §4.3 is actually adopting.

When upstream moves: the CLI flags are the contract and they carry no compatibility promise. There is no `pyproject.toml` or `setup.py` at the repository root, so the dependency is a pinned clone in a data directory rather than a package in `pyproject.toml`, and the pin has no manifest home.

### 5.7 llm-wiki by a pinned `github` source at the repo root

Arrives every session: `compile.md`, `query.md` and `wiki-manager`, about 266 always-on tokens against the baseline's 1,961. No vendoring and no fork, one sha and a three-path list. It is the only shape that delivers the compile command and the compile protocol together without carrying a copy of upstream.

The vault must fence off two mismatches and a cache. `${CLAUDE_PLUGIN_ROOT}/bin/llm-wiki` does not resolve, because `bin` sits one directory deeper, though the compile path never uses it. The literal `skills/wiki-manager/references/compilation.md` path written in `compile.md` does not resolve under this root either, so the model reaches those files through the co-loaded skill rather than through the path the text names. And the entire repository, including `tests/`, `benchmarks/`, a `.git` directory and an unrelated Codex plugin tree carrying six hooks, is copied into the plugin cache; none of those hooks fire, because that tree is not the plugin root. The entry must be named `wiki` or the command text's own cross-references dangle.

When upstream moves: a stale path degrades silently to fewer components, so the drift check is the shallow-clone assertion again, and the `ref` should read `master`.

### 5.8 llm-wiki by a skill-only root

Arrives every session: `wiki-manager` and its 22 reference files, about 268 always-on tokens. This is the exact precedent geometry, one sha and one path, and the smallest always-on cost measured across either candidate.

The vault must fence off the fact that this buys the compile **protocol** and not the `/wiki:compile` command. Nothing in the compile path needs `bin/`: `SKILL.md`'s only CLI mention is an explicit-retraction escape hatch, and `compilation.md` and `indexing.md` invoke no CLI at all. `references/adapters.md` and `references/specialists.md` would fail if reached, since `bin/` is absent from this root.

When upstream moves: one path to re-check. There is only one skill upstream today, so this shape subtracts nothing and will start subtracting the day upstream adds a second.

### 5.9 llm-wiki by composing a commands root and a skills root

Arrives every session: two commands and `wiki-manager`, from two plugin roots, about 268 always-on tokens. It is the minimum-surface way to get both the command and the protocol with no vendoring and no fork.

The vault must fence off a split namespace. The two live under different plugin names, so the commands' `/wiki:lint`-style cross-references and their literal `skills/wiki-manager/references/...` paths are both wrong, and the agent reaches the reference files only because the skill happens to be loaded in the same session.

When upstream moves: two shas to bump in lockstep. They must stay at the same commit or the command text and the protocol it names drift apart, and nothing detects that.

### 5.10 llm-wiki by a one-line fork of `claude-plugin/`

Arrives every session: two commands, `wiki-manager` and `bin/llm-wiki` at the path the docs promise, about 266 always-on tokens. It is the only shape whose kept components are internally consistent: identity stays `wiki`, so every `/wiki:` cross-reference resolves, and the literal reference path in `compile.md` resolves under this root, which no repo-root shape achieves. `skills/` is the one directory a `plugin.json` field cannot narrow, and here that is what keeps `wiki-manager` arriving alongside the two commands.

The vault must fence off nothing measured. What it accepts is a vendored copy of `claude-plugin/`, about 600 KB, everything byte-identical to upstream but one JSON key.

When upstream moves: a fork to re-sync, with the sibling repository's vendoring discipline, a provenance header, a LICENSE notice and a byte-diff test against a clone at the pin.

### 5.11 llm-wiki by vendoring into our own plugin

Arrives every session: the six commands §4.3's second fallback names, `wiki-manager`, and `bin/llm-wiki`, about 653 always-on tokens, 33% of the baseline.

The vault must fence off a namespace problem that is much larger here than for claude-obsidian. 39 of the repository's 147 `/wiki:<command>` references sit inside those six commands, so under any plugin name other than `wiki` all 39 name commands that do not exist. Naming ours `wiki` restores them, collides with an upstream install, and is a poor name for a research-vault plugin. Taking only `compile.md` avoids nearly all of it: one namespace reference and seven files, about 90 KB.

When upstream moves: a re-vendor per sha, plus a namespace-rewrite pass if the plugin is not named `wiki`, reapplied each time, plus a drift test asserting the reference targets each command names still exist upstream.

### 5.12 llm-wiki by a project-scope commands directory

Arrives every session: nothing always-on. The copied `compile.md` becomes a user-invocable slash command with no plugin machinery at all, versioned in this repository like any other file. It needs no `${CLAUDE_PLUGIN_ROOT}` and resolves the wiki from `$HOME/.config/llm-wiki/config.json`.

The vault must fence off two things. The reference files the command reads have to be given a home the model can find, and the relative form the command text uses no longer names anything, so repointing those two lines is the edit that turns a copy into a fork. And the loader labels this source `commands_DEPRECATED` internally and reports the file under "legacy commands", so the route is its own drift row.

When upstream moves: a diff against a shallow clone at the pin, over 7 files and about 90 KB.

### 5.13 llm-wiki by its Codex-side skill tree

Arrives every session: one of the two skills under `plugins/llm-wiki/skills`, a genuine subtraction at the cleanest precedent geometry in the repository, with no `plugin.json` and no hooks file at that root.

The vault must fence off prose written for another harness. The skill carries a "Codex Plugin Notes" section telling the reader to treat `/wiki` and `/wiki:*` examples as shorthand because Codex registers no such commands, which is guidance this vault would be importing into Claude Code.

When upstream moves: this tree is synced from `claude-plugin/` by a script, so it is a derived copy that can lag the primary one, and the pin would be tracking the mirror.

### 5.14 llm-wiki as a plain dependency on its CLI

Arrives every session: nothing. One self-contained 5,965-line standard-library-only file with seven subcommands, callable by path.

The vault must accept the same split as claude-obsidian's engine: `compile`, `ingest`, `query` and `refresh` are not in the CLI. The docstring says so directly, calling the tool "not a replacement for the agentic /wiki workflows".

When upstream moves: one sha and one hash check. Because it is a single stdlib-only file, copying it is indistinguishable from depending on it.

## 7. Open questions

### Findings that contradict the consuming spec

Three, each tested.

1. **§4.3's proposed entry shape loads nothing.** A `strict: false` entry with a component list, pointed at claude-obsidian, is the conflicting-manifests case: `plugin.json` exists at that root, so the plugin installs, validates, and is then dropped at load with `Status: failed to load`. The spec's tracer fact 1 asked whether such an entry suppresses upstream's `hooks/hooks.json`. The answer is that it does not, and the larger answer is that the question does not arise, because the entry never loads. Under `strict: true` the same entry loads and the list is inert, so the whole plugin arrives.
2. **The precedent's precondition fails in substance, not only in shape.** Spec line 130 records that no superpowers skill uses `${CLAUDE_PLUGIN_ROOT}` and that cross-directory references are sibling-relative. All 15 claude-obsidian skills resolve a `PRODUCT_ROOT` and hard-gate on `test -f "$PRODUCT_ROOT/scripts/claude-obsidian.py"`, and the precedent shape copies no `scripts/`. The subset loads and is listed, and its first bash block fails.
3. **The command count is 28, not 27.** `ls claude-plugin/commands/*.md | wc -l` is 28 at the pin, `find` agrees, and the debug log independently reads `Loaded 28 commands from plugin wiki default directory`. §4.2 of the consuming spec records 27.

### What could not be tested and would change the answer

1. **Whether §4.3's four-skill claude-obsidian set is transitively closed.** Sibling references were traced for `wiki-query` and `wiki-lint`, which point at `../wiki-retrieve/`, `../wiki-cli/` and `../wiki/`. `wiki-ingest` and `wiki-fold` were not traced. If either points at a skill the subset drops, the vendoring row's component list is wrong.
2. **Whether the sparse route's degraded contract bites this vault.** The contract failure was observed through `contracts --verify`, which `wiki-query`'s protocol runs as its step 3. §4.3 does not keep `wiki-query`. Whether `wiki`, `wiki-ingest`, `wiki-lint` or `wiki-fold` run the verifier was not checked, and if none do, the degradation may be invisible in practice.
3. **Whether the in-tree shim can be served from a GitHub-hosted marketplace whose `marketplace.json` sits in a subdirectory.** That relies on the `path` field of the `github` or `git` marketplace source, which exists in the schema but has no `marketplace add` flag, so it is settings-only and was not tested. Nor was whether relative symlinks survive a clone into the marketplace cache. The vault-shaped variant tested here avoids symlinks entirely, but was proven through a local-path `marketplace add`, not a remote one.
4. **Whether a full 40-character sha is a supported `git` marketplace `ref`.** It works empirically and the checkout's `rev-parse HEAD` equals the pin, but the schema documents that field as a branch or tag, so it should be treated as version-fragile.
5. **Marketplace name collision on the sparse route.** That route inherits upstream's marketplace name, so a user who already has the full upstream added at user scope collides with a project-scope curated declaration. Which wins was not tested.
6. **Agents by symlink into `~/.claude/agents`.** §4.3 wants claude-obsidian's three agents. The symlink route was probed for skills only, so its "does not load" entry should be read as agents untested rather than agents excluded.
7. **The symlink route against the real trees.** The mechanism was proven on a synthetic clone built to claude-obsidian's exact geometry, not on the candidates' own directories.
8. **A user-typed slash command under a `permissions.deny` rule.** The deny rule was tested through the Skill tool. The slash-command pipeline passes a real permission context to the same gate, so it is likely blocked, but that was not run.

### Instrument warnings, for anyone repeating this

`claude plugin details` is wrong in two opposite directions and would have inverted two conclusions. It under-reports components supplied as individual `.md` file paths: it showed 0 commands for a plugin whose debug log showed two loading, and 0 agents for two shapes whose logs showed one loading. It also files a plugin's default-directory commands under the "Skills" heading, printing "Skills (29)" for a plugin with 28 commands and 1 skill. Directory-based skills are reported correctly. The authoritative instrument is `~/.claude/debug/<id>.txt`, whose three load-bearing line shapes are `Loaded N X from plugin P default directory`, `Loaded N skills from plugin P custom path: <dir>` and `Loaded <kind> from plugin P custom file: <file>`. The line `Sending N skills via attachment` is not a measure of catalog membership: identical configurations produced 94, 126 and 127 across three runs.

Two further notes on method. For marketplaces added by local path, the loader reads components from the source directory rather than the cache copy, which matters for anything resolving a product root and means a local-path install of a fork stays live-editable. And plugin installs are not safe against concurrent Claude Code sessions on this machine: a `marketplace remove` reported success and the marketplace reappeared, because a parallel session's whole-file write to `settings.json` clobbered the removal.
