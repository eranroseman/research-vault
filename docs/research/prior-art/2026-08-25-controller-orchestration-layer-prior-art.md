# Prior art: a controller/orchestrator coordinating parallel AI coding-agent sessions in one shared checkout

Disposition: historical (2026-09-06) [should-be-scoping-review]

Research note, 2026-08-25. Feeds a first-principles design audit of a proposed **controller** role that coordinates several autonomous coding-agent sessions that all operate against **one mutable git checkout** — not separate worktrees, not a single-plan SDD/agent loop. Five angles under investigation: (1) delegation-authority criteria vs. multi-agent LLM framework supervisor/worker patterns, (2) evidence-based dispute adjudication, (3) authority scoping (first-hand vs relayed consent, consent scoped to its granted text), (4) precedent formation thresholds, (5) shared-mutable-state hazards in git itself. Scope is **prior art and its fit/non-fit to this specific system** — not a recommendation. Primary sources only; paraphrase vs. verbatim quote is marked throughout; genuine negatives are reported as negatives rather than stretched into weak matches.

## Summary

Five angles, three distinct outcomes:

1. **Delegation-authority generalizing past one decision is a documented gap in existing multi-agent LLM frameworks**, not a solved problem being reinvented. LangGraph/LangChain (supervisor + handoffs), AutoGen 0.2 (`GroupChatManager.speaker_selection_method`), AutoGen 0.4+ (`SelectorGroupChat`, `Swarm`), and CrewAI's hierarchical process (`allow_delegation`, `manager_llm`) all re-decide every turn — none documents a mechanism where a prior approval generalizes to a *class* of future decisions without a fresh routing/selection/delegation/handoff event. The controller material's "ratify on the third identical instance" rule fills a real, currently-undocumented gap in this class of system.
2. **Evidence-based dispute adjudication has one strong positive match and two near-misses.** NIST SP 800-53 AC-3(2) and PCI-DSS 6.2.3/6.2.3.1 (maker-checker/dual-authorization) are pure second-signature sign-off — the checker doesn't re-derive evidence, just isn't the author. FEMA/NIMS Unified Command is joint objective-setting across jurisdictions, not evidence re-verification. The positive match is MARCH (arXiv:2603.24579): a Checker agent re-answers from retrieved evidence *in isolation, denied the Solver's original output* — deliberately preventing confirmation bias. Topology differs (maker→isolated-checker vs. this system's two-disputants→arbiter) but the mechanism — don't trust the assertion, re-derive it from source, kept blind to the disputed claim while doing so — is the same principle. Multiagent-debate (arXiv:2305.14325) is a clean negative: agents there only ever see each other's *generated text*, never fresh evidence.
3. **Authority scoping is real but mapped by analogy, not direct citation, on the capability-security side; agency law gives a genuinely two-sided answer.** Hardy's "Confused Deputy" and Miller's POLA/name-centric-vs-key-centric distinction are about programs and file authorization, not interpersonal "X said Y approved" claims — the fit is an analogy (bare name standing in for a capability) that this note's own citations do not make about people, so treat the extension to interpersonal authority-relay as this design's move, not the sources'. Restatement (Third) of Agency §2.03 (apparent authority), read via two court-citing secondary sources (primary text paywalled), cuts both ways: apparent authority *does* let a third party act on an indirect signal, softening a blanket first-hand-only rule — but per comment f, that signal must still trace to the *principal's own* manifestation, not to an agent's self-report of its own authority. That specific carve-out is the one that matters here: an intermediary's bare claim "the author consented" does not, by this doctrine, create authority on its own — which is precisely the case the controller material's word-hygiene rule turned on. RACI (via a Smith-&-Erwin-derived practitioner guide; the 2005 original is only in non-OCRable scans) independently confirms single-Accountable-party and a before/after split between Consulted (input before the decision) and Informed (notice after it).
4. **No domain names a numeric ratification threshold except software's rule of three.** Common-law stare decisis needs one ruling; Louisiana's jurisprudence constante needs "a series"/"a long line" of rulings but no source — not even a Louisiana Supreme Court opinion read directly — ever states a count. Fowler et al.'s *Refactoring* (1999, p. 58) is the one primary text with an explicit number: third occurrence of the same pattern triggers the generalization ("the third time you do something similar, you refactor"). The controller material's "ratified on the third instance" lands exactly on software's number, not legal doctrine's open-ended one — worth stating precisely rather than blending the two traditions into one vague "precedent needs repetition" claim.
5. **Shared-checkout topology sits in direct tension with git's own prescribed alternative.** See below — git's own `git-worktree(1)` EXAMPLES section names this exact problem (a second stream of work needing to touch the repo without disturbing an existing session's uncommitted state) and prescribes a separate linked worktree, not stash choreography inside one shared checkout.

## #5 Shared mutable state hazards — git's own documentation

**Live-verified against `git version 2.43.0` man pages (`man git-rebase`, `man git-stash`, `man git-worktree`, `man git-merge`, all read 2026-08-25) plus the upstream Pro Git book source on GitHub.**

### `--autostash` — the mechanism a controller might reach for, and git's own warning about it

`git-rebase(1)`, OPTIONS: "`--autostash`, `--no-autostash` — Automatically create a temporary stash entry before the operation begins, and apply it after the operation ends. This means that you can run rebase on a dirty worktree. However, use with care: **the final stash application after a successful rebase might result in non-trivial conflicts.**" (`man git-rebase`, v2.43.0, OPTIONS section).

If the rebase is aborted mid-flight rather than completed, the created stash is not silently discarded: `git-rebase(1)`, MODE OPTIONS, `--quit`: "Abort the rebase operation but HEAD is not reset back to the original branch... If a temporary stash entry was created using `--autostash`, **it will be saved to the stash list.**" (`man git-rebase`, v2.43.0).

**Fit.** These two sentences are git's own primary-source acknowledgment that `--autostash` is a *convenience for a dirty tree*, not a concurrency-safety mechanism — it can produce conflicts on reapplication, and on abort it leaves an artifact sitting on a shared list rather than cleanly rolling back. Neither sentence contemplates *other sessions'* changes; that composition is documented in the next point.

### The stash is a single, repository-wide stack — not scoped to a session, branch, or actor

`git-stash(1)`, DESCRIPTION: "The latest stash you created is stored in `refs/stash`; older stashes are found in the reflog of this reference and can be named using the usual reflog syntax (e.g. `stash@{0}` is the most recently created stash, `stash@{1}` is the one before it...)" (`man git-stash`, v2.43.0). There is exactly one `refs/stash` per repository; the addressing scheme (`stash@{0}`, `stash@{1}`, ...) is a positional index into one shared reflog, not a per-actor namespace.

`git-worktree(1)`, DETAILS: "In general, all pseudo refs are per-worktree and all refs starting with `refs/` are shared." (`man git-worktree`, v2.43.0, DETAILS section). `refs/stash` starts with `refs/`, so it is confirmed **shared even across linked worktrees of the same repository** — a fortiori shared within one single checkout, which is the topology under audit here.

**Fit.** If two agent sessions in the same checkout both use `git stash` / `--autostash` at overlapping times, they are pushing and popping the *same* stack. `stash@{0}` for session A can silently become session B's most recent stash the moment B pushes one, and a `--quit`-abandoned autostash from a failed rebase sits on that same shared list waiting for either session's next `stash pop` to pick it up. This composition — that a pathspec-less `git stash push` captures the *entire* working tree, including files neither session is touching — is git's ordinary architecture (one working tree, one index, one stash stack per checkout) rather than a sentence any doc states as a warning; it is reported here as an **inference from documented primary facts**, not a direct quote.

### git's own prescribed alternative to stashing over "disarray" is a separate worktree, not the shared checkout

`git-worktree(1)`, EXAMPLES: "You are in the middle of a refactoring session and your boss comes in and demands that you fix something immediately. You might typically use `git-stash(1)` to store your changes away temporarily, however, **your working tree is in such a state of disarray... that you don't want to risk disturbing any of it.** Instead, **you create a temporary linked worktree** to make the emergency fix, remove it when done, and then resume your earlier refactoring session." (`man git-worktree`, v2.43.0, EXAMPLES section, followed by `git worktree add -b emergency-fix ../temp master`).

**Fit — direct tension with the system's premise, not softened.** This is not a generic hazard note; it is git's own documentation naming the *exact* problem class (a second stream of work needing to touch the repo without disturbing an existing session's uncommitted state) and prescribing the *exact* alternative this system's design deliberately does not take: a separate linked worktree per concurrent stream of work, rather than choreographing multiple sessions' stash/autostash traffic through one shared checkout. A controller relying on the shared-checkout topology is operating against git's own documented recommendation for this scenario, not merely in an area git is silent on.

### Rewriting history other sessions may have built on

`git-rebase(1)`, NOTES: "You should understand the implications of using git rebase on a repository that you share. See also RECOVERING FROM UPSTREAM REBASE below." (`man git-rebase`, v2.43.0, NOTES section).

`git-rebase(1)`, RECOVERING FROM UPSTREAM REBASE: "Rebasing (or any other form of rewriting) a branch that others have based work on is a bad idea: anyone downstream of it is forced to manually fix their history. This section explains how to do the fix from the downstream's point of view. **The real fix, however, would be to avoid rebasing the upstream in the first place.**" (`man git-rebase`, v2.43.0).

Pro Git (git-scm.com book), "The Perils of Rebasing" — verified against the upstream asciidoc source, not just the rendered page (`https://raw.githubusercontent.com/progit/progit2/main/book/03-git-branching/sections/rebasing.asc`, section `==== The Perils of Rebasing`, fetched 2026-08-25): "**Do not rebase commits that exist outside your repository and that people may have based work on.** If you follow that guideline, you'll be fine... When you rebase stuff, you're abandoning existing commits and creating new ones that are similar but different. If you push commits somewhere and others pull them down and base work on them, and then you rewrite those commits with `git rebase` and push them up again, your collaborators will have to re-merge their work and things will get messy..." The book's own summary, in the adjacent "Rebase vs. Merge" discussion: "rebase local changes before pushing to clean up your work, but **never rebase anything that you've pushed somewhere**" (same source; this closing-guidance sentence was reported by an AI-mediated fetch of the rendered book page and is marked here as **paraphrase-adjacent, not independently verified against the asciidoc source** — the two "Do not rebase" quotes above are the ones confirmed against raw source text).

**Fit.** This branch of the doctrine ("don't rewrite history others have pulled/pushed") is about a *shared remote*, and is close to, but not identical to, the hazard in a *shared local checkout*: in the audited system, other sessions haven't necessarily "pulled" anything — they may simply have uncommitted or committed-but-unpushed state sitting in the same working directory. The doctrine still applies once any session has built commits on top of another session's commits, but the more acute hazard for *this* topology is the working-tree/stash collision documented above, which git-rebase(1)'s NOTES section does not itself address (it is scoped to published/shared branches, not concurrent local sessions in one checkout).

### `git merge` also warns about uncommitted state, independent of rebase

`git-merge(1)`, DESCRIPTION: "Warning: Running git merge with non-trivial uncommitted changes is discouraged: while possible, it may leave you in a state that is hard to back out of in the case of a conflict." (`man git-merge`, v2.43.0, DESCRIPTION section, following the `--abort` discussion).

**Fit.** Confirms the hazard is not specific to rebase/autostash — any history-integrating operation (merge included) that runs against a working tree carrying uncommitted changes is explicitly discouraged by git's own docs, independent of whose changes they are. In a controller-coordinated shared checkout, "non-trivial uncommitted changes" could easily belong to a *different* session than the one running the merge.

## #1 Delegation-authority criteria vs. multi-agent LLM framework patterns

All quotes below fetched and grepped against raw HTML/Markdown/README source directly, 2026-08-25 (live doc sites; content may move later).

**LangGraph / LangChain supervisor pattern.** `github.com/langchain-ai/langgraph-supervisor-py` README (official repo): "Hierarchical systems are a type of multi-agent architecture where specialized agents are coordinated by a central **supervisor** agent. The supervisor controls all communication flow and task delegation..." — the README itself now recommends the supervisor pattern "directly via tools" over the standalone library. Current docs (`docs.langchain.com/oss/python/langchain/multi-agent`): "All routing passes through the main agent, which decides when and how to invoke each subagent" (Subagents pattern); Handoffs let "Agents transfer control to each other via tool calls" but each handoff is still one fresh tool call. `docs.langchain.com/oss/python/langchain/supervisor`: "The supervisor dispatches tasks to subagents sequentially by default. Each tool call completes before the next one starts."

**AutoGen 0.2** (`microsoft.github.io/autogen/0.2/docs/reference/agentchat/groupchat/`): `speaker_selection_method` picks the next speaker per turn ("auto" by LLM, "manual", "random", "round_robin", or a custom callable) — pure turn-selection, re-run every turn, no standing grant.

**AutoGen 0.4+.** `SelectorGroupChat` (`microsoft.github.io/autogen/stable/.../selector-group-chat.html`): "A generative model... selects the next speaker based on the shared context"; `allow_repeated_speaker=True` only permits back-to-back turns for the same agent, it doesn't grant standing authority — the selector still runs fresh each turn. `Swarm` (`.../swarm.html`) decentralizes the decision itself: "agent[s] delegate tasks to other agents using a special tool call... **This enables agents to make local decisions about task planning, rather than relying on a central orchestrator**"; but "at each turn, the speaker agent is selected based on the most recent `HandoffMessage`" — still a fresh, individually-issued tool call every time, not a persisted authorization.

**CrewAI hierarchical process** (`docs.crewai.com/en/concepts/processes`): "Tasks are not pre-assigned; **the manager allocates tasks to agents** based on their capabilities, **reviews outputs, and assesses task completion**" — every task, every time. Delegation is a tool call (`Delegate work to coworker`, `docs.crewai.com/en/concepts/collaboration`) gated by `allow_delegation` (default `False`). One sentence comes close to a generalizing claim — "With memory enabled, agents learn from previous collaborations and improve their delegation decisions over time" — but read carefully this describes the *delegator's* decision quality improving, not a worker gaining a standing exemption from future approval. Flagged explicitly as paraphrase-adjacent, not a match.

**Cross-framework answer.** No primary source across these three frameworks documents a mechanism where a prior approval generalizes to a *class* of future similar decisions without a fresh routing/selection/delegation/handoff event. All three are turn-taking/routing systems, re-deciding at every step — this is the negative finding of interest: it is a genuine, currently-undocumented gap in existing multi-agent LLM orchestration frameworks, not prior art this design borrows from.

## #2 Evidence-based dispute adjudication

Verified against official PDFs (NIST, PCI-SSC, FEMA) via direct text extraction, and against arXiv PDFs directly, 2026-08-25.

**Maker-checker / dual control.** NIST SP 800-53 Rev. 5, AC-3(2) *Access Enforcement | Dual Authorization*: "Enforce dual authorization for [organization-defined privileged commands and/or other actions]... Dual authorization, also known as two-person control, reduces risk related to insider threats... require the approval of two authorized individuals to execute." This is sign-off language — no requirement the second party re-derive or re-check evidence. (AC-5 *Separation of Duties*, the more commonly guessed control, has no dual-authorization mechanic of its own — "Control Enhancements: None.") One outlier in the family, MP-6(7) *Media Sanitization | Dual Authorization*, adds: dual authorization "protect[s] against errors and **false claims of having performed the sanitization actions**" — closer to "checker confirms the act actually happened," but this is not the norm across the family.

PCI-DSS v4.0.1, **6.2.3/6.2.3.1** (not 6.3.2, which is a software-inventory requirement): manual code reviews must be performed "by individuals other than the originating code author... reviewed and approved by management prior to release." Pure second-person sign-off, role-separation, not evidence re-verification.

**Unified Command** (FEMA "ICS Review Document," March 2018, from ICS 300 training materials): "When no one jurisdiction, agency or organization has primary authority... Unified Command may be established... there is no one 'commander.' Instead, the Unified Command manages the incident by jointly approved objectives." Near-miss: joint decision-making and jurisdiction-sharing, not independent re-verification of a disputed claim before ruling. (Span of control: current 2017 NIMS doctrine states "the optimal span of control for incident management is one supervisor to five subordinates," a flexible guideline superseding the older fixed 3–7 range some secondary sources still cite.)

**Multi-agent LLM papers.** Du et al., "Improving Factuality and Reasoning in Language Models through Multiagent Debate" (arXiv:2305.14325): each agent's response is "concatenated and given as context to each agent," which then "verif[ies]... and refin[es] its own response based on other agents' responses" — verification here means cross-examining stated arguments, never fresh/external evidence. Confirmed negative: a near-miss, not a match.

**Positive match**: MARCH — "Multi-Agent Reinforced Self-Check for LLM Hallucination" (arXiv:2603.24579, Alibaba Qwen team): "a Solver, a Proposer, and a Checker... the Checker validates these propositions against retrieved evidence **in isolation, deprived of the Solver's original output**. This well-crafted information asymmetry scheme breaks the cycle of self-confirmation bias." The Checker "re-answer[s] questions solely based on the retrieved evidence, without access to the Solver's original output." Topology differs from a two-disputants-plus-arbiter shape (this is maker → isolated re-verifier), but the underlying mechanism — don't trust the assertion, re-derive it from source while blind to what's being disputed — is the precise principle at stake. (Unverified leads, not fetched in full: Tool-MAD arXiv:2601.04742, DebateCV arXiv:2507.19090, AgentAuditor arXiv:2602.09341.)

## #3 Authority scoping — first-hand vs relayed consent, consent scoped to its granted text

**Capability security / POLA.** Mark Miller, "Robust Composition" (PhD dissertation, Johns Hopkins, 2006, `erights.org/talks/thesis/markm-thesis.pdf`), §3.1: "The Principle of Least Authority (POLA) recommends that you grant each program only the authority it needs to do its job." §3.2 draws the name-centric ("cp" style — pass a name through a shared namespace) vs. key-centric ("cat" style — pass an unambiguous, unforgeable reference that itself both designates and authorizes) distinction, crediting Norm Hardy's "The Confused Deputy" (ACM SIGOPS OSR, 1988) as the paper that first explained why designation and authorization must be bundled. Hardy, verbatim: "The capability both identifies the file and authorizes the compiler to write there... The fundamental problem is that the compiler runs with authority stemming from two sources... **It has no way to keep them apart.**" Fit is by analogy, not direct citation: both sources are about programs and files, not interpersonal "X told me Y approved" claims — but the analogy is exact in shape: a bare name (or a bare relayed claim) is being mistaken for an unforgeable grant.

**Agency law — actual vs. apparent authority.** Restatement (Third) of Agency's primary text is paywalled; read here via two court-citing secondary sources (Colorado's official model civil jury instructions, and a University of Houston Law Center course packet quoting the black-letter text with pinpoint citations). §2.02(1): actual authority covers what the agent "reasonably understands" from "the principal's manifestations... and acts necessary or incidental to achieving the principal's objectives" — scope is designated-plus-strictly-incidental, not generally-adjacent. §2.03: apparent authority arises when a third party's belief "is traceable to the principal's manifestations" — and comment f is the load-bearing sentence: apparent authority is absent when the third party deals with someone believed to be a self-representing principal, i.e. the doctrine still requires the signal to trace to the *actual principal's* own words or conduct, not to an *agent's own self-report* of having authority. Genuinely two-sided: apparent authority softens a blanket "only first-hand counts" rule (indirect signals CAN bind), but it still excludes exactly the case this design turns on — an intermediary's bare relay of "the author consented," unconnected to the author's own manifestation reaching the actor, does not create authority under this text.

**RACI.** PMI/PMBOK's own hosted text was inaccessible (403-blocked PDFs); read via a TNTP practitioner guide explicitly derived from Smith & Erwin's 2005 "Role & Responsibility Charting" (the 2005 original itself only located as non-OCRable scans): "Only one person can be assigned accountability" (Accountable); Consulted "must provide input **prior to** a final decision or action" vs. Informed "needs to be informed **after** a final decision or action" — a clean before/after, input-vs-notice split. RACI's Linear-Responsibility-Chart lineage (1950s–70s, variously attributed) has no locatable primary document — treated as unverified folklore, not cited as a source.

## #4 Precedent formation — threshold patterns

**Common-law stare decisis** (Cornell LII, Wex): a single prior ruling from a court of appropriate authority is precedent — no numeric threshold.

**Louisiana jurisprudence constante** (verified against the actual opinion PDF, *Willis-Knighton Medical Center v. Caddo-Shreveport Sales & Use Tax Comm'n*, 903 So. 2d 1071, 1085 n.17 (La. 2005), quoting *Doerr v. Mobil Oil*): "a single case affords sufficient foundation for stare decisis, while **a series of adjudicated cases, all in accord, form the basis for jurisprudence constante**." Every source checked — including a law review survey of Louisiana precedent doctrine — uses only "a series of," "a long line of," never a specific count; one surveyed appellate judge reported sometimes treating even a *single* intermediate decision as though it had the force of law. The threshold is doctrinally left unquantified, not fixed at any particular N.

**Software's rule of three** — the one domain with an explicit number. Verified via a dated verbatim quotation (Ward Cunningham's WikiWikiWeb, citing page and book) of Fowler, Beck, Brant, Opdyke & Roberts, *Refactoring: Improving the Design of Existing Code* (1999), p. 58: "The first time you do something, you just do it. The second time you do something similar, you wince at the duplication, but you do the duplicate thing anyway. **The third time you do something similar, you refactor.**" No standalone martinfowler.com bliki page for this could be located despite extensive searching — the rule lives in the book, not the website; treat "Fowler's bliki" framing as inaccurate if it recurs elsewhere.

**Google SRE, toil definition** (`sre.google/sre-book/eliminating-toil/`): "If you're performing a task for the first time ever, or even the second time, this work is not toil. Toil is work you do **over and over**." Structurally similar (excludes the 1st and 2nd occurrence) but never states a number — "over and over," not "three."

**The controller material's own number** — "ratified on the third instance of an identical... question" — lands exactly on software's rule of three, not on legal doctrine's deliberately open-ended "a series of." Worth keeping that distinction sharp: this is one specific, numbered convention borrowed from (or convergent with) software practice, not a generic appeal to "precedent needs repetition."

## Dead ends / negative knowledge

- No multi-agent LLM framework (LangGraph, AutoGen, CrewAI) documents a delegation-authority-generalizes concept — a real gap, reported as a finding in #1, not filled with a weak analogy.
- Multiagent-debate (arXiv:2305.14325) looks on-topic for dispute adjudication but is a clean negative: agents there never touch fresh evidence, only each other's generated text.
- FEMA/NIMS Unified Command and NIST/PCI maker-checker are near-misses for dispute adjudication — real, well-documented, but neither requires independent re-verification against fresh evidence, which is the specific mechanism this design needs prior art for.
- Capability-security prior art (Confused Deputy, POLA) fits authority-scoping only by analogy (programs/files, not interpersonal consent-relay); reported as analogy, not citation.
- Restatement (Third) of Agency's primary text is paywalled; read only via two court-citing secondary sources. Treat §2.02/§2.03 quotes above as verified-by-citation, not independently confirmed against the Restatement itself.
- RACI's Linear-Responsibility-Chart origin (1950s–70s) and even the 2005 Smith & Erwin paper have no locatable clean primary text — origin lineage is unverified folklore; only a 2023 practitioner derivative was fetched directly.
- No jurisdiction's precedent doctrine (common-law or civilian) names a numeric ratification threshold; only software's rule of three does. Don't blend the two into one undifferentiated "precedent needs repetition" claim.
- Martin Fowler's "rule of three" is real (verified, p. 58 of *Refactoring*) but not documented as a standalone martinfowler.com bliki page — it's book content, not a web reference.
- git's own docs never state "don't touch another engineer's uncommitted state" as a single sentence; the hazard for a *shared local checkout* (as opposed to a shared *remote*) is assembled here from several separate primary facts (one repo-wide `refs/stash`, autostash's own reapplication-conflict warning, `git merge`'s uncommitted-changes warning) — marked as inference, not verbatim quote, in the #5 section above.
