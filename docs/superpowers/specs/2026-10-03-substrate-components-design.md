## Shape of this spec (decided 2026-10-04)

**One spec, one argument:** decision 12's three legs for the components research-vault cannot pin — declare, provision, observe — with *observe* covering both a component's state (doctor) and its effects (machine-surface detection and the capture monitor). Rulings 5 and 6 exempt ordinary editing and commands on the selection only because research-vault sees every change to what it owns, so the detection work and the declarations it licenses belong in one document.

**Plans are the plan writer's call; one ordering constraint binds them:** the detection and capture-monitor work lands before the seeded `.obsidian/` ships, and #190 (doctor's preference grammar) and #193 (prevent or detect machine-surface writes by agents) land before lane 4 opens.

**Lane 4 keeps annotation handling** (operator, 2026-10-04, #18): assembly decision 28 stands, and the ingest spec's `:137` claim to supersede it is amended in this spec's commits. #18's surviving requirement — pass Zotero's annotation colour through raw, adopt no colour taxonomy — becomes a lane-4 screening must.

## Rulings that shaped the screens

Recorded in each evidence file's "Standards as applied" section, in the order the operator gave them (2026-10-03 to 2026-10-04):

1. Machine surfaces are the guard's roster (`hooks/pretooluse_guard.py:11-23`); `system/` outside `system/propagations/` and `system/bibliography.json` is hand-edited.
2. Merging duplicates is Zotero's own behaviour and is not judged in an add-on (#183).
3. Approval gates and unmonitored backups count for nothing: a confirm dialog, a preview, a backup line or git history nobody watches does not make a write safe.
4. Written values must be right by construction: by identifier from an authoritative source, or a lossless format change. Removals only by a definite test (an exact placeholder, a nonexistent file, an exact duplicate kept on the item). A re-key passes because lifecycle detects it and `propagate` repairs it.
5. A component is judged on what it adds beyond ordinary editing: for Obsidian, beyond editing the open note; for Zotero, beyond commands the person runs on the items they selected. Obsidian's own vault operations (rename with link update, move, delete, and creating a note by following a link or from a menu) are app behaviour. A direct edit to one specific note shown in another view (a Bases cell, a checkbox in a query result) is editing that note. A handler that only inserts into the open note is open-note editing. This holds only because research-vault detects machine-surface changes whoever makes them; closing the detection gaps (#203–#212) and the capture monitor (below) are part of this spec.
6. **Selection: include anything that aids one of the five workflows and does no harm** (2026-10-04; supersedes §1's original "one add-on per job"). The five workflows: research; analysis and reports; personal knowledge management; long-form writing; daily logs. The step map gains steps for analysis/reports and knowledge management. Harm is an unconfined counted path under ruling 5, a load failure, or a destructive write. Two add-ons whose writes fight each other are not both declared.
7. **An OKF conformance break is accepted where the value justifies it**, as a row in the deviation register (`docs/agents/okf-conformance.md`) together with the verify exemption or type mapping that keeps the commit gate open for that plugin's files (2026-10-04).
8. **A redistribution licence decides only how an Obsidian plugin is declared**: seeded (vendored in `.obsidian/`, licence must permit it) or recommended (the person installs it; declared settings; doctor observes). It is not harm (2026-10-04).
9. **Agent access to Zotero is research-vault's own client** (`research_vault/zotero.py`); an add-on whose job is agent access is not declared (2026-10-04).
