Facts: capture is the sole writer of literature/ (one note per source, wholly machine-written); the assembly spec retired archive.py for being a second machine writer into a record capture owns (§7.2). OKF conformance rules: docs/agents/okf-conformance.md.

MUSTS

- **C1** Writes no literature note and touches no machine surface (or can be configured so — name the setting). A plugin whose purpose is generating literature notes fails C1 unless that can be switched off and it still serves something.
- **C2** Resolves citation keys through Better BibTeX at the observed 9.0.6x line: name the channel (BBT JSON-RPC, CAYW, an auto-exported .bib/.json, direct read of zotero.sqlite / better-bibtex.sqlite) with cites, and any known breakage at BBT >= 9.0.57.
- **C3** Loads on the current Obsidian. Always needs-live; record manifest minAppVersion / isDesktopOnly.
- **C4** Licence permits redistributing its released files inside a public repository.
- **C5** What it inserts into a note is Pandoc [@key] (or configurable to it) and OKF-conformant.

### Second ruling (2026-10-04): judged on what it does by itself

On 2026-10-04 the operator ruled a principle that supersedes the first pass's invocation readings for C1: the **C1** paragraph above, and readings 1 and 5. For screens A and B it does the same for A3 and B3. The machine-surface roster above stands, and so does the merge exclusion. A second normalisation pass re-judged all 14 C1 cells under the principle, first by re-judgement and then by an adversarial verifier. The verifier refuted none on result. Where the two differ on basis, §4 says so and uses the verifier's version. A cell whose result changed carries § in §3. §4 records every changed cell, and every cell whose basis or seed keys moved, on a line beginning "§ 2026-10-04 by-itself".

**The principle.** A component is judged on what it does by itself. That covers what it does when an item is added or a file is created, on startup or load, on a schedule or sweep, on open, and in the background. It covers what it does through a notifier or event hook reacting to any writer. It also covers what it does remotely, through a REST, MCP, URI or CLI handler, a sync, a git pull, or any request not made by the person in the app at that moment. What the person deliberately does through the component counts as the person's own edit, the same as editing by hand, and is not judged. That means a command or menu action the person runs on items or files they selected, a button the person presses, and a bulk change the person confirms in a prompt. A confirm or preview dialog is deliberate whatever its scope. A component passes if a setting turns the counted behaviour off, and §4 names the key and value. For an Obsidian plugin that setting is a seedable data.json, app.json or core-plugin setting. For a Zotero add-on it is a preference: research-vault declares it in README.md's "Automatic-mode preference" column, and doctor reports it. Disabling the component outright is not a confining setting. (superseded 2026-10-04, third ruling)

**The musts under the principle.** C1 and B3: the plugin does not by itself write into a machine surface. A3, recorded here for the spec, has two parts. (a) The add-on does not by itself destroy or rewrite another writer's data in Extra, tags, fields or child notes. (b) The add-on does not by itself change an existing citation key, and filling an empty key is not a change. Merging stays out of A3: it is Zotero's own behaviour (issue #183). (superseded 2026-10-04, third ruling; merging stays out of A3)

**Formerly unruled readings the principle settles.**

- CLI, URI and REST handlers are remote, so they are counted. Examples here are ZotLit's obsidian://zotlit handlers and its Companion HTTP push, and Zotero Lib View's obsidian://zotero-library handler, which only opens views.
- A confirm modal is deliberate, so a change behind one is not counted. An example is ZotLit's BatchModal and its child-note overwrite confirm. (superseded 2026-10-04, third ruling)
- Sending output outside the vault confines it. An example is an absolute `exportFolderPath` in Simple Citations (reading 5).
- A person choosing a location in a dialog is deliberate. An example is ZotLit's Pandoc export and Integration Pair destinations. (superseded 2026-10-04, third ruling)
- Reading 1, the §1 purpose clause: a plugin is judged on what it does by itself, not on its purpose. No 2026-10-04 cell turns on it.
- Reading 5, Simple Citations' docx export: execute-pandoc is a command the person runs on the active file, so it is not judged. (superseded 2026-10-04, third ruling)
- Reading 4, ZotLit's data invariant: the re-judgement held that the principle does not settle it. The verifier settled it: the in-place rewrite reaches only files stamped `zotero-key` or `zotero-note-key`, no research-vault writer stamps them, and a person hand-stamping a roster note is the person's own edit (§4 ZotLit). (superseded 2026-10-04, third ruling)

### Third ruling (2026-10-04): trigger-neutral, right by construction

On 2026-10-04 the operator ruled a third time. The ruling supersedes the first and second rulings' invocation readings: the second ruling's exemption for the person's deliberate act is withdrawn, as approval-gate theater, and so is any reasoning that a write is acceptable because it is recoverable or backed up, since a backup or history nobody monitors counts for nothing. The machine-surface roster above (hooks/pretooluse_guard.py:11-23) stands, and so does the exclusion of merging from A3 (issue #183). A third normalisation re-judged all 14 C1 cells under the ruling, by re-judgement and then an adversarial verifier. The verifier refuted none on result; where it corrected a cite or added a path, §4 says so. In §3, ∆ marks a C1 cell whose result this pass changed, and existing †, ‡ and § marks are kept. §4 carries a line beginning "∆ 2026-10-04 third ruling" for every C1 cell whose result or basis moved, naming the failing paths and any setting as key=value. C2 to C5 were not re-judged.

**The standard.** Every write or removal path a component offers is judged alike, whatever starts it: an automatic or on-add write, a notifier, a schedule, a remote route, a menu command, a button, or a change the person confirms in a preview or dialog. A confirmation, a preview, a backup, an undo or restore command, and history nobody monitors change no result. A component has to be right by construction:

- Writes (screen A's A3): every value an add-on writes into a field, Extra, a tag or a child note is looked up by identifier from an authoritative source (a DOI resolved through doi.org, Crossref or DataCite; a PMID or PMCID from NCBI; an ISBN; an arXiv ID), or is a format change that keeps all the information (the case of a case-insensitive identifier, a short DOI expanded to the long one, reversible punctuation or dash normalisation). A value found by fuzzy matching, a bibliographic-query hit taken without an identifier check, a guess from the title or any other heuristic fails, even when it only fills an empty field.
- Removals (A3): it blanks, truncates, trashes, deletes or strips only what a definite test shows is invalid (an exact placeholder token, a file that does not exist, a link to nothing), or an exact duplicate of information kept on the same item. A heuristic or pattern-match removal fails, and so does removing something merely redundant, such as a snapshot beside a PDF.
- Identity (A3): it does not change an existing citation key, except where research-vault already detects and repairs the change. lifecycle classifies a re-key and propagate maps the old key to the new one, so a re-key passes. Filling an empty key passes.
- An add-on passes A3 only if a setting removes every failing path from every trigger. A failing path still reachable from a menu command or a remote route keeps the cell a fail. Screen A's record carries that judgement.

**C1** (and screen B's B3): every write path into a machine surface fails, whoever triggers it, unless an existing research-vault mechanism detects that write (for example a lint that fails on a modified machine-written line, verify's drift check, or the vault commit gate), or a seedable setting removes the path from every trigger. The §4 ∆ line names the detecting mechanism with a cite, or the setting's key and value. There is no hand-edit exemption. C5 is unchanged: it is judged at the configuration research-vault would seed.

**Detection, as surveyed for this pass** (§7 items 26–33). Only literature/ is reliably detected: evidence-layer blocks the commit gate on a changed note or capture-owned key. In an existing wiki/ page, an inserted plain-text passage, markdown link or captured `[@key]` is not detected. Root log.md is detected only when a write breaks its heading or date order. fulltext/ is gitignored and unseen at the commit gate. An append to log/, system/propagations/ or inbox/review-queue.md is not reported.

**Readings this pass applied (not part of the ruling; open to the operator).**

1. An insert or rewrite a plugin makes in the active note, through a command, menu, ribbon, button, suggester, or paste or drop handler, is a write path. Its destination is whichever note is open, which can be a wiki/ page, root log.md, a log/ day file or a fulltext/ file, and no plugin or Obsidian setting limits which note is active or makes wiki/ read-only. Because the ruling withdrew the hand-edit exemption, these writes are judged by whether research-vault detects them at each destination, and on a wiki/ page it does not. The re-judgement offered this reading as its own; the verifier concurred, because the withdrawn exemption covered exactly the commands run on files the person chose, and the ruling judges every write whoever triggers it. Every one of the 11 C1 fails is decided by this class (a). Each ∆ line separates (a) active-note writes from (b) path-directed writes, so a result under the other reading can be read off.
1. On a reading that counts only (b) path-directed writes, nine of the eleven fails would pass. Zotero Integration, Reference Map, Citations, Better Pandoc Reference List, Citation Suite, Citation Extended and Deep Sit would pass at the seeds their ∆ lines list, and Zotero Annotation Citations and Zotero Deep Linker have no (b) path. ZotLit would still fail: its in-place rewrite of notes carrying `zotero-key` has no confining setting, and its Pandoc export and Integration Pair destinations are chosen in a dialog. Simple Citations is borderline: only a machine-specific absolute `exportFolderPath` keeps its .docx from landing beside the note. The verifier added that Citation Extended's batch update accepts a vault-wide unique basename match, the same data-invariant shape as ZotLit's `zotero-key` rewrite, so under a (b)-only reading it should be treated like ZotLit. Without seeds, root log.md collisions are real at defaults for Zotero Integration's Import notes, Zotero Lib View's note writes, and ZotLit's attachment copies at Obsidian's default root attachment folder.
1. A write counts as detected when a commit-closing verify check catches it at the vault pre-commit hook. No C1 cell turns on whether the append-only lint's review-queue filing also counts, because every class (a) fail is decided on wiki/, which that lint does not cover. Screen B's record counts such filing as detection.
1. For fulltext/, the verifier found that a worktree verify snapshots ignored files, so a new untyped fulltext/\*.md is caught there by okf-frontmatter but not at the index-candidate commit gate, and an insert into an existing typed fulltext/ file is undetected either way (§7 item 31). One C1 corner leans on it: the click path the verifier added for Citation Links could create an empty `fulltext/@key.md`, which only a worktree verify catches.
