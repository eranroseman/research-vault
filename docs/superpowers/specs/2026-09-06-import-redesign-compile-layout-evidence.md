Research note, 2026-09-05. A layout-configurability probe of the two compile-step candidates, run against scratch vaults rather than against their documentation.

**What this artifact is.** A record of what `AgriciDaniel/claude-obsidian` and `nvk/llm-wiki` do to a directory tree they are pointed at. Five questions were asked of each: whether the caller can name the directories, what the tool writes per source, whether its pages carry a frontmatter `type`, whether its lint reaches folders it did not write, and what it does with `index.md`. Each candidate was cloned at its pin into `/tmp`, a scratch vault with the research-vault folder shape was built beside it, and the tool's deterministic parts were run against that vault: config load, path resolution, lint, transaction scope validation, and the page writers. The LLM legs (ingest drafting, compile) were not driven; where a fact could only come from prose or a template, that is marked.

**What consumes it.** The compile section of the ingest redesign spec, `docs/superpowers/specs/2026-09-06-import-redesign-design.md`. Specifically §4.3, whose proposed adoption rests on "the two things that must fit this vault are configuration, not code"; §4.4, which names pointing the tool at `synthesis/` as a tracer and leaves the source page's home open; §4.3's second tracer, that `wiki-lint` leaves `literatures/` untouched; and §8 item 7, the open question about whether compiled pages carry a `type` the vault's structure check accepts.

**Nothing here is a decision.** This note reports what the probes found and, per candidate, what the findings imply about the treatment rung. It does not rank the candidates, does not recommend one, and does not choose a home for the source page. It lays out the options and their costs and leaves the choice to design.

**Conventions.** Two marks separate runs from reading. `tested` means a command was run at the pin and the quoted output is what it printed. `read` means the fact comes from source, a shipped template, an example, or skill prose, with no run behind it; a paragraph that cites only a source location is `read` whether or not it says so. Where the two split inside one answer, the answer says which part is which. Quotes from `research_vault` are restored from the source in this repository; quotes from tool output are reproduced as the probe recorded them and are not edited to look tidier. Paths to candidate source are repository-relative at that candidate's pin, not the `/tmp` clone path.

## 1. The question

### The vault's folder contract

| Folder                                   | What it holds                                                                                                                                                                  | The machine's relationship to it                                                                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `literatures/`                           | One note per source, projected from Zotero, one per citation key                                                                                                               | A managed region the machine owns and rewrites on every capture, above a free region the machine never touches |
| `synthesis/`                             | The cross-source arrangement layer. The author's stated intent: `synthesis/` is the LLM-wiki's non-source-summary folder, the concept and topic pages a compile step maintains | Notes carry frontmatter `type: synthesis`                                                                      |
| `log/`, `inbox/`, `projects/`, `system/` | The rest                                                                                                                                                                       | Not at issue here                                                                                              |

Four rules from `research_vault/structure.py` and `research_vault/scaffold.py` bound every answer below.

| Rule                            | Where                                               | What it says                                                                                                                                                                                                   |
| ------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type is required                | `structure.py:63` (`check_note_frontmatter`)        | Every non-reserved markdown file must carry a non-empty frontmatter `type`. Failure reads `schema-violation — missing type (OKF §11 rule 2)`                                                                   |
| Type is derived from the folder | `structure.py:29-34`, `:43-58`                      | `literatures` derives `literature`, `synthesis` derives `synthesis`, `log` derives `daily`, `inbox` derives `fleeting`. A file under any other top-level folder derives `None`, so any non-empty `type` passes |
| Reserved names                  | `structure.py:125-151` (`check_reserved`)           | A nested `index.md` must carry no frontmatter at all; the root `index.md` may carry `okf_version` and nothing else; `log.md` at any depth admits only `## YYYY-MM-DD` second-level headings, newest first      |
| The tree is attested            | `scaffold.py:14` (`VAULT_DIRS`), `structure.py:172` | `inbox`, `literatures`, `synthesis`, `log`, `projects`, `system/templates`, `system/bases` must all exist                                                                                                      |

Two facts about the gate itself, both read from this repository. The vault's pre-commit hook (`research_vault/templates/git/pre-commit`) runs `python3 -m research_vault verify --vault "$vault" --offline --surface commit`, and `okf-frontmatter`, `okf-structure` and `tree` are all in the commit surface's closing set (`verify.py:54-71`). The frontmatter leg walks `sorted(vault.rglob("*.md"))` and skips only paths containing `.git`, plus the names `index.md` and `log.md`, which `check_reserved` takes instead (`verify.py:1003-1008`). So dot-directories other than `.git` are walked: a markdown file under `.raw/` or `.vault-meta/` is a subject of the type rule like any other. The `inbox/` fleeting exemption (`structure.py:39-41`) covers everything under `inbox/` except `inbox/review-queue.md`.

### The five sub-questions

- **Q1.** Can the tool be pointed at caller-named directories, specifically concept pages into `synthesis/` and its raw store somewhere we choose, or does it hard-code its own layout?
- **Q2.** What exactly does the tool write per source, what shape does it have, and could it live inside an existing file's free region rather than in a folder of its own?
- **Q3.** Do the pages the tool writes carry a frontmatter `type`, or can they be made to? Does the tool's own lint require a fixed frontmatter set that would collide with an added `type` key?
- **Q4.** Does the tool's lint walk directories it did not write, and would it relocate, quarantine, or flag files in `literatures/`, `inbox/` or `log/`?
- **Q5.** Does it write an `index.md`, where, and does that index carry frontmatter?

## 3. AgriciDaniel/claude-obsidian at `ad67087`

### Q1. Layout configurability: partly, with the decisive part fixed

Three separable knobs, one of them a false one.

**The vault root is fully caller-named.** `--vault`, the `CLAUDE_OBSIDIAN_VAULT` environment variable, or the `vault` key in `.claude-obsidian.json`, resolved by `paths.resolve_vault_root`.

**The wiki root name is the literal string `wiki`, in four independent places, none of them configuration.** `mode_config.validate_wiki_folder` and `validate_wiki_route` reject any path whose `parts[0]` is not `wiki` (`claude_obsidian/mode_config.py:44`). `transaction._validate_operation_write_scope` refuses non-`wiki/` writes for every operation in `_WIKI_ONLY_OPERATIONS` (`save`, `lint-fix`, `markdown`, `generic`) and `_WIKI_AND_RAW_OPERATIONS` (`ingest`, `autoresearch`) (`claude_obsidian/transaction.py:3140-3245`). `lint_engine._wiki_location` accepts only `root/wiki` or a directory literally named `wiki` (`claude_obsidian/lint_engine.py:393-401`). `paths.is_initialized_vault` requires `(path / "wiki").is_dir()` (`claude_obsidian/paths.py:279-292`).

**Per-kind subdirectory names are configurable, but only within `wiki/`.** `.vault-meta/mode.json` carries `config.generic.{sources,entities,concepts,sessions}_folder`, with `lyt`, `para` and `zettelkasten` variants. Tested: writing `sources_folder: "literatures/"` and running `mode get` produced `ERR VAULT_OPERATION: existing mode configuration is unsafe: config.generic.sources_folder must be a canonical wiki/ folder`. Rewritten as `wiki/literatures/` with `concepts_folder: wiki/synthesis/`, `mode get` returned both verbatim. Called directly, `mode_config.validate_wiki_folder('synthesis/')` raised `ValueError` reading `concepts_folder must be a canonical wiki/ folder`, and `'wiki/synthesis/'` was accepted. So the reachable target is `wiki/synthesis/`, which is a different folder from the one the vault's structure check derives `synthesis` for.

The transaction scope validator confirms this independently. A hand-built bundle with `operation_type: generic` writing to `synthesis/compiled-concept.md` was refused by `transaction inspect` with `ERR WRITE_SCOPE_VIOLATION: generic operations may write only wiki content`. The same bundle retargeted to `wiki/synthesis/compiled-concept.md` was accepted and an `approval_sha256` was emitted. (tested)

**The raw store is a false knob.** `CaptureConfig.raw_store` in `.vault-meta/capture/config.json` is honoured by `capture plan` and refused by `capture apply`. Tested with `raw_store: "sources"`: `capture plan` planned `sources/captured/<sha>.md`, and `capture apply` on that same plan died with `ERR WRITE_SCOPE_VIOLATION: capture operations may only create content-addressed captured files: sources/captured/...`, because the scope validator hard-requires `parts[:2] == (".raw", "captured")`. Any non-default `raw_store` produces a plan that can never be applied. (tested)

**The symlink workaround is closed on purpose.** `ln -s ../synthesis wiki/concepts` followed by a lint left `pages_scanned` unchanged at 6, because `_walk_files` drops symlinked directories: the two pages behind the symlink were never scanned. A vault whose `wiki` was itself a symlink to `synthesis` produced `pages_scanned: 0`, because `_wiki_location` requires `not candidate.is_symlink()`, and `paths.assert_unaliased_directory` on that path raised `OSError [Errno 40] path is a symlink or directory junction`. (tested)

**`adopt` accepts a foreign layout but does not map it.** `adopt` on a bare directory holding only `literatures/a.md` and an empty `synthesis/` was accepted, with no `.obsidian/`, no `wiki/` and no sentinel present. Its `changed_paths` were `.claude-obsidian.json`, `.gitignore`, `.obsidian/*`, `.raw/.manifest.json`, `inbox/.gitkeep`, `wiki/hot.md`, `wiki/index.md`, `wiki/log.md`, `wiki/meta/ledgers/*` and `wiki/overview.md`. Not one references `literatures/` or `synthesis/`. It writes its own tree beside the caller's folders. (tested)

### Q2. What it writes per source, and whether it can go in a free region

Per ingested source the tool produces a coupled set, all inside one transaction:

1. A source page at `<sources_folder>/<Title>.md`, by default `wiki/sources/<Title>.md`. Frontmatter is `type: source` plus `title`, `status`, `created`, `updated`, `tags`, plus `source_type`, `author`, `date_published`, `url`, `source_id`, `sha256`, `authority`, `independence_key`, `review_state`, `key_claims`. The body is LLM-drafted summary prose with wikilinks. (read: `skills/wiki/references/frontmatter.md` for the property list, `examples/sample-vault/wiki/sources/Example Source.md` for a rendered example)
2. An immutable content-addressed copy at `.raw/captured/<sha256>.<ext>`, create-only.
3. A record in `wiki/meta/ledgers/source-ledger.json` and claims in `claim-ledger.json`.
4. At least one index or MOC update, `wiki/index.md` when it is an active catalog.
5. One batch entry appended at the top of `wiki/log.md`, and a refreshed `wiki/hot.md`. (read: `skills/wiki-ingest/SKILL.md`, "Build one Ingest transaction")
6. Optionally an address request stamping an `address: c-000001` line into the page frontmatter.

So the tool does not produce one file per source. It produces a page, a raw blob, two ledger records, and edits to three reserved files.

**It cannot write into an existing file's free region, and it is blocked twice, independently.**

The first block is write scope. `ingest` is in `_WIKI_AND_RAW_OPERATIONS`, so it may write only `wiki/` or `.raw/` paths. A bundle with `operation_type: ingest` writing `literatures/smith-2024-attention.md` in mode `replace` was refused by `transaction inspect` with `ERR WRITE_SCOPE_VIOLATION: ingest operations may write only wiki or raw-source content: literatures/smith-2024-attention.md`. (tested)

The second block is that no region-aware write mode exists. The transaction engine accepts only mode `create` and mode `replace`, each carrying whole-file content plus a whole-file expected SHA-256. `claude_obsidian/transaction.py:3400` and `:3875` both read `if mode not in {"create", "replace"}`, and those are the only two write modes in the file. There is no append, no anchor, no insert-after-marker, and no partial write anywhere in the 4,771-line engine. The worker contract matches: `agents/wiki-ingest.md` has the worker return proposals carrying `path`, `action` of `create` or `replace`, `expected_sha256`, and `content`, which is whole-file again. (read, by grep over the source rather than by run) A `replace` against a literature note would rewrite the entire file including the machine-owned managed region, which is exactly the boundary the vault protects.

**What routing would cost.** A post-apply step outside the tool would have to read `wiki/sources/<Title>.md`, splice its body into the literature note's free region under the managed region, and then either delete the `wiki/sources` page or keep it. Deleting it breaks every wikilink the same transaction wrote, the index catalog entry, and the ledger locator, and the tool's own lint would then report `dead_links` and `stale_index_entries`. Keeping it means two files per source, plus the `.raw/captured/<sha>.md` copy, so three artifacts. Building region-aware writing instead means adding a third write mode to an engine whose scope validator, journal, hashing and recovery all assume whole-file semantics.

### Q3. Type field: yes, natively, and the collision runs the other way

`type` is one of the six `REQUIRED_FRONTMATTER_FIELDS` in `claude_obsidian/lint_engine.py:49`, alongside `title`, `status`, `created`, `updated` and `tags`. Every template and example the tool ships carries it: `type: meta` on `wiki/index.md`, `wiki/hot.md` and `wiki/log.md`, and `type: overview`, `source`, `concept`, `entity`, `question`, `comparison`, `fold` elsewhere. The vault's rule 2 is therefore satisfied by construction on every compiled page.

**No key collision.** The tool's lint is presence-only. It never validates the `type` value against a vocabulary and never rejects extra keys. Tested: a page at `wiki/synthesis/tool-shaped.md` carrying `type: "synthesis"`, a value outside the tool's own documented vocabulary, plus the other five required fields plus an extra `okf_version: "0.2"` key, drew zero findings from `lint --format json`.

**Two real collisions exist, in opposite directions.**

The first is value against folder, and the vault side accommodates. `structure.expected_type('wiki/synthesis/compiled-concept.md')` returns `None`, so any non-empty `type` passes there; `expected_type('synthesis/x.md')` returns `'synthesis'` and `expected_type('literatures/x.md')` returns `'literature'`. If compiled pages landed in top-level `synthesis/` while the tool wrote `type: concept`, the vault would report `schema-violation — type 'concept' but folder derives 'synthesis'`. Under `wiki/` the question does not arise. Run against the four wiki pages `adopt` wrote, `structure.check_note_frontmatter` returned `MATCHED` on all four: their `type: meta` and `type: overview` pass precisely because `wiki/` derives no type. (tested)

The second is required-set asymmetry, and the vault side is the one that suffers. The tool requires six fields; the vault requires one. A vault-minimal page carrying only `type` and `title`, placed at `wiki/synthesis/vault-shaped.md`, drew `missing_frontmatter [{path: wiki/synthesis/vault-shaped.md, has_frontmatter: true, missing_fields: [status, created, updated, tags]}]`. Every hand-written vault page that migrates under `wiki/` becomes a standing lint finding until it grows the other five fields. The allowlist cannot suppress this: `_ALLOWLIST_KEYS` (`lint_engine.py:71-78`) are all dangling-link keys (`dangling_links`, `allowed_dangling_links`, `allowlisted_dangling_links`, `allowlist`, `dead_links`) and only `_is_allowlisted()` consults them. The `missing_frontmatter` loop (`:1055-1070`) has no allowlist path at all. (tested)

### Q4. Lint scope: it walks foreign folders, and checks none of them

`lint_vault` calls `_walk_files(root)` over the entire vault root (`lint_engine.py:370-391`), skipping only `.git`, `.obsidian`, `.vault-meta`, `.cache`, `.pytest_cache`, `__pycache__`, `node_modules`, and any symlinked directory or file (`:56-63`). Every walked `.md` becomes a target and a page. But `wiki_pages`, the set every check iterates, is filtered on `page.is_wiki_page`, meaning the relative path equals the wiki prefix or starts with `wiki/` (`:347-369`, `:941-950`). So `dead_links`, `ambiguous_targets`, `duplicate_basenames`, `orphans`, `missing_frontmatter`, `empty_sections` and `stale_index_entries` are all computed over `wiki/` pages only.

Tested with six decoys: `literatures/{smith-2024-attention,jones-2023-graphs,hot}.md`, `inbox/{loose-thought,no-frontmatter-decoy}.md`, `log/{2026-09-05,decoy-non-date}.md`. One carried no frontmatter at all, one (`literatures/hot.md`) duplicated the basename of `wiki/hot.md`, and one (`inbox/no-frontmatter-decoy.md`) carried the dangling wikilink `[[definitely-not-a-page]]`. `lint --format json` reported `pages_scanned: 4`, `issues_found: 0`, every category empty. Not one decoy appeared in `missing_frontmatter`, `orphans`, `duplicate_basenames` or `dead_links`.

The control proves the walk really does reach them rather than the resolver being dead. Adding `See [[smith-2024-attention]] and [[attention-mechanisms]] and [[hot]].` to `wiki/overview.md` gave `links_scanned: 3, dead_links: 0`: all three resolved into `literatures/` and `synthesis/`, with `wiki/hot.md` winning the `[[hot]]` basename race through the wiki-prefix query option, so not even ambiguous. Adding `[[nonexistent-xyz]]` produced exactly one `dead_link`. (tested)

**Nothing is relocated, quarantined, renamed or flagged.** The lint engine performs no filesystem writes; its module docstring says so and a `sha256sum` over every file in the vault before and after `lint --format markdown` produced an empty `diff`, a byte-identical tree. Repair is a separate, explicitly gated LLM operation (`skills/wiki-lint/SKILL.md`: "Never auto-fix a lint result"), and `lint-fix` is itself in `_WIKI_ONLY_OPERATIONS`, so even the repair path cannot touch `literatures/`, `inbox/` or `log/`. This closes the spec's §4.3 tracer 2 in the affirmative. Pointing lint at a foreign folder does nothing useful either: `lint --vault <vault>/synthesis` returned `ERR VAULT_SENTINEL_MISSING`, and calling `lint_vault()` on that path directly returned `pages_scanned: 0`. (tested)

**The intrusion is capture, not lint.** `CaptureConfig.source_roots` returns `<vault>/inbox` plus `<vault>/.raw` (`claude_obsidian/capture.py:487-493`), and `capture plan` with no arguments enumerates every file in the vault's `inbox/` and plans to copy it into `.raw/captured/<sha256>.<ext>` (`:865-889`). Run on the scratch vault, `capture plan` returned 2 items, both `inbox/*.md`, and `capture apply --apply --approved-plan-sha256 ...` returned `status: complete` with the files present on disk. The originals are not moved or deleted, since capture is copy-only and `.raw` is create-only, but the copies are markdown files with no frontmatter. `structure.check_note_frontmatter` on both returned `UNMATCHED` with `missing type (OKF §11 rule 2)`. Given that the vault's verify walker rglobs the whole tree and skips only `.git` (`verify.py:1003-1005`), those copies are walked and reported as `okf-frontmatter` failures, which is a commit-closing check. Whether a reported but unstaged file actually closes the commit is open question 2 below. (tested; the walker behaviour read from this repository)

**Escape hatches.** For lint, none is needed: foreign folders are out of scope by default, and the `.vault-meta/lint-allowlist.json` file is not a scope hatch, only a dangling-link suppressor. For capture, two: pass explicit source paths as positional arguments instead of letting it discover, or redirect discovery with `--inbox <dir>` or the `inbox` key in `.vault-meta/capture/config.json`. `capture plan --inbox system` returned 0 items. The inbox must be visible: `--inbox .staging` returned `ERR INBOX_NOT_VISIBLE`, so it cannot be hidden as a dot-directory. `raw_store` is not a usable hatch, per Q1. (tested)

### Q5. Index: `wiki/index.md`, and the two checkers fail it in opposite directions

`wiki/index.md` is written by both `init` and `adopt` from `templates/vault/wiki/index.md`, is in `_BOOTSTRAP_COMMON_PATHS` (`transaction.py:108-123`), and is updated by every canonical-page operation. The fold scope validator (`transaction.py:3200-3265`) literally requires the bundle to contain `wiki/index.md` and `wiki/log.md` alongside the fold page. A second index, `wiki/canvases/index.md`, is the only other index path any operation may write. Both are nested `index.md` files by the vault's definition. The vault's own root `index.md` was left untouched by `adopt`, so there is no collision at the root.

The template ships `type: meta`, `title: Wiki Index`, `status: evergreen`, `created`, `updated`, `tags: [meta, index]`.

Both directions were run against that one file. `structure.check_reserved` on the scratch vault after `adopt --apply` returned exactly one finding: `Outcome(check='okf-structure', target='path-bytes:wiki/index.md', result=UNMATCHED, reason='schema-violation — nested index.md must be frontmatter-free')`. The root `index.md` carrying only `okf_version` passed. Stripping the frontmatter block off `wiki/index.md` and re-running `lint --format json` produced `missing_frontmatter [{path: 'wiki/index.md', has_frontmatter: false, missing_fields: ['title','type','status','created','updated','tags']}]`. Neither side offers an escape: the vault rule is unconditional, and the tool's allowlist covers only dangling links. (tested)

`structure.check_tree` on the scratch vault returned `UNMATCHED` for `missing ['projects','system/templates','system/bases']`, which is an artifact of the minimal scratch vault rather than of the tool: the tool's `wiki/`, `.raw/` and `.vault-meta/` additions do not trip `check_tree`, which only asserts the presence of `VAULT_DIRS`. (tested)

One adjacent risk is read rather than run. `wiki/log.md` is a reserved name the vault polices at any depth, admitting only `## YYYY-MM-DD` second-level headings, newest first. The shipped template passes because it carries no `## ` headings, but the skills append LLM-drafted top-of-file entries to it (`skills/save/SKILL.md:68`, `skills/wiki-fold/SKILL.md:81`) with no deterministic heading format specified anywhere in the repository, so continued conformance is not established. (read)

## 4. nvk/llm-wiki at `7c94c9b`

### Q1. Layout configurability: only the root moves

`llm-wiki lint <path>` takes an explicit root; `--local` resolves `cwd/.wiki`; `--wiki <name>` resolves through the hub registry at `~/.config/llm-wiki/config.json` to `hub_path` or `resolved_path` and then `wikis.json`.

Everything inside the root is a Python module constant in `scripts/llm-wiki` with no config key, environment variable or CLI flag feeding it: `RAW_TYPES` at line 29, being `articles`, `papers`, `repos`, `notes`, `data`; `ARTICLE_DIRS` at line 31, mapping `concept` to `concepts`, `topic` to `topics`, `reference` to `references`; `ROOT_ALLOWED` at line 99; `RAW_ALLOWED` at line 147; `WIKI_ALLOWED` at line 148. `check_structure()` hard-requires `raw/`, the five `raw/<type>/` folders, `wiki/`, `wiki/{concepts,topics,references,theses}`, and `output/`. The hub `config.json` is read only for `hub_path` and `resolved_path`; the wiki's own `config.md` is read only for `title` (`topic_title`, line 2182); `LLM_WIKI_CONFIG_DIR` relocates only the adapter registry, not the hub config. A grep for `os.environ` and `getenv` across the script found only `LLM_WIKI_TODAY`, `LLM_WIKI_CONFIG_DIR` and `LLM_WIKI_NOW`. A grep for `ROOT_ALLOWED`, `RAW_TYPES` and `ARTICLE_DIRS` found definition sites and consumption sites, with no assignment from config anywhere.

The tool's own reference says this outright. `claude-plugin/skills/wiki-manager/references/wiki-structure.md`: "the physical layout stays raw/ -> wiki/concepts|topics|references/, and the required-frontmatter set stays fixed." (read)

There is no `init` subcommand; the CLI is `lint`, `archive`, `schema`, `retract`, `specialist`, `adapter`, `checkpoint`, and init is agentic-only. `scripts/llm-wiki` and `claude-plugin/bin/llm-wiki` are byte-identical (`diff -q` reports no difference), so the plugin ships the deterministic logic tested here.

Three runs establish the consequence. `lint <vault> --json` on a research-vault-shaped root returned 14 critical and 4 warning findings, including 12 of "Required directory is missing" for the `raw/*`, `wiki/*` and `output` paths. `lint --fix` on that root created all 13 directories with their `_index.md` inside the vault root: it does not adapt to `literatures/`, `synthesis/` and `log/`, it scaffolds its own tree alongside them. And aiming the root at the caller-named directory, `lint --fix <vault>/synthesis`, did not make `synthesis/` the concepts directory: it scaffolded `synthesis/raw/`, `synthesis/wiki/concepts/` and `synthesis/output/`, and quarantined the pre-existing `synthesis/attention-mechanisms.md` and `synthesis/index.md` into `synthesis/inbox/.unknown/`. (tested)

### Q2. What it writes per source, and whether it can go in a free region

The source page is the raw file: `<root>/raw/<articles|papers|repos|notes|data>/YYYY-MM-DD-<slug>.md`, declared immutable after ingest. Required frontmatter, enforced by `check_frontmatter_schema`, is `title`, `source`, `type`, `ingested`, `tags`, `summary`. The per-source summary is a two-to-three-sentence frontmatter scalar under `summary:`, not body prose; the body holds the extracted full content. Ingest also appends a row to `raw/<type>/_index.md` and `raw/_index.md`, and a `## [date] ingest | ...` line to `log.md`. (shape read from `claude-plugin/skills/wiki-manager/references/wiki-structure.md`, "Source File Format (raw/)", and `references/ingestion.md`, since ingest is an LLM workflow with no CLI entry point; the field requirements were tested through `require_fields` and `check_enum` in lint)

There is no separate per-source summary page and no compile-time per-source page. Compile produces cross-source concept, topic and reference articles. The only deterministic page writer in the whole CLI is `create_or_update_coverage_reference` at line 1624, which writes `wiki/references/uncompiled-source-coverage.md`, a single backlog table of raw sources that no article cites.

**Nothing in the tool writes into an existing file's region.** There is no managed or free region concept anywhere in the source. The nearest thing is `fix_legacy_wiki_frontmatter`, which rewrites the frontmatter block of files under `wiki/` only. Placement is actively enforced in the other direction: `canonical_path_for()` and `check_canonical_placement()` `shutil.move` a raw file to `raw/<frontmatter type>/<name>.md` whenever it sits elsewhere, so a source page cannot be parked outside its type folder. Tested: `raw/papers/jones2021-retrieval.md` carrying `type: articles` drew the critical "File is in the wrong directory; expected raw/articles/jones2021-retrieval.md", and `--fix` reported "Moved raw/papers/jones2021-retrieval.md to raw/articles/jones2021-retrieval.md". Files under `literatures/` are never even parsed: `is_schema_checked_path` gates on `parts[0]` being one of `raw`, `wiki`, `inventory`, `datasets`.

**What routing would cost.** A wiki article may cite a path outside `raw/` with no complaint. Tested: a concept page carrying `sources: [../../literatures/smith2020-attention.md]` drew no source-resolution warning, and `--fix` left the sources list byte-identical and never touched `literatures/smith2020-attention.md`. But `check_coverage` only counts references under `<root>/raw/`, so a source cited that way stays permanently in the "not referenced by any compiled article" backlog and is swept into the auto-written coverage page. The only working route is a mirror: each literature note gets a `raw/papers/<slug>.md` copy carrying `type`, `source` and `ingested`, kept in sync, with nothing ever written back into the literature note's free region. That is a second file per source. (tested)

### Q3. Type field: split three ways

**Raw pages carry `type`, enum-locked.** `check_frontmatter_schema` calls `check_enum(doc, 'type', RAW_TYPES)`, so the value must be one of `articles`, `papers`, `repos`, `notes`, `data`. Tested: a raw page carrying `type: literature` drew `Critical: Invalid type: 'literature'; expected one of articles, data, notes, papers, repos`, and `--fix` could not repair it, because `canonical_path_for` returns `None` for a value outside `RAW_TYPES`; it persisted through the fix run. The vault side is asymmetric here in the tool's favour: `expected_type('raw/papers/x.md')` returns `None`, so a raw page carrying `type: papers` passes the vault gate. Raw pages are gate-clean.

**Wiki article pages carry no `type`.** The template's required set is `title`, `category`, `created`, `updated`, `tags`, `summary`; `type` appears only in the special case `frontmatter.get('type') == 'thesis'`. An added `type` is tolerated: `require_fields` only checks the presence of its own list and never rejects extra keys. Tested: `wiki/concepts/attention-mechanisms.md` carrying the full required set plus `type: synthesis` drew nothing about type, only an info line about a missing volatility field, and after `lint --fix` reported "Repaired frontmatter in wiki/concepts/attention-mechanisms.md" the file still read `type: synthesis`, with only `volatility: warm` appended. The tool's own article vocabulary (`concept`, `topic`, `reference`) lives in `category`, not `type`, so it does not contend for the key.

**Every file the lint itself writes carries no `type` at all.** The 13 `_index.md` files, `schema.md`, and `wiki/references/uncompiled-source-coverage.md`. Running the vault's own checker over the fixed tree reported 16 `okf-frontmatter` failures: `_index.md`, `config.md`, `schema.md`, the other 11 `_index.md` files, and the coverage page, all reading `schema-violation — missing type (OKF §11 rule 2)`. The coverage page's actual frontmatter is `title`, `category`, `sources`, `created`, `updated`, `verified`, `tags`, `confidence`, `volatility`, `summary`, with no `type` key. (tested)

**Lint collision:** yes on `raw/`, no on `wiki/`. The tool requires a fixed frontmatter set per folder but never forbids extra keys, so `type: synthesis` coexists with the required six on a wiki page and survives auto-repair. The collision is on `raw/`, where `type` is the tool's own routing key: it both validates the value against `RAW_TYPES` and moves the file by it, so the vault's `type: literature` and the tool's `type` cannot occupy the same file.

### Q4. Lint scope: one level at the root, and it moves foreign root files

`check_unknown_files()` iterates `ctx.root.iterdir()` and compares each child name against `ROOT_ALLOWED`, then recurses only into `raw/`, `wiki/`, `inventory/` and `datasets/`. `load_documents()` is gated by `is_schema_checked_path()`, which returns `False` unless `parts[0]` is one of those four, so nothing under `literatures/`, `synthesis/`, `log/` or `projects/` is ever parsed. `markdown_files()` does `rglob`-stat the whole tree, but the contents of foreign directories are never read or modified. `check_index_consistency` is likewise scoped to `raw`, `wiki`, `inventory`, `datasets` and `output`.

**Foreign directories draw a warning and are never moved.** `handle_unknown()` short-circuits on `path.is_dir()` and emits "Unexpected file or directory at wiki root. Unknown directories are not auto-fixed." A baseline `sha256` over all seven vault files before the run and again after `lint --fix` showed `literatures/smith2020-attention.md`, `literatures/jones2021-retrieval.md`, `synthesis/attention-mechanisms.md`, `synthesis/index.md`, `log/2026-09-05.md` and `inbox/scratch-idea.md` all byte-identical. But a warning is enough to return exit 1, and the three unknown-directory warnings persisted after the fix, so lint can never pass on a research-vault-shaped root. (tested)

**Foreign root-level files are moved.** `handle_unknown()` `shutil.move`s them into `<root>/inbox/.unknown/`. The vault's root `index.md` is a file, is not named `_index.md`, and is not in `ROOT_ALLOWED`, so `lint --fix` reported "Moved index.md to inbox/.unknown/index.md" among its 28 auto-fixes. Repeating with `git init` at the vault root produced the same move: `GIT_ROOT_META_ALLOWED` covers `.git`, `.github`, `AGENTS.md`, `CLAUDE.md`, `LICENSE` and similar, not `index.md`. Running the vault's own checks over the fixed tree then gave 13 `okf-frontmatter` failures (the scaffolded `_index.md` files plus `schema.md`) and a `check_reserved` `UNMATCHED` on `inbox/.unknown/index.md` reading `nested index.md must be frontmatter-free`, because the quarantined root index still carries `okf_version`. (tested)

**Second effect: it scaffolds into the vault.** `check_structure(--fix)` creates 13 directories, each with a frontmatter-free `_index.md`, plus `schema.md` and `inbox/.processed/`. The untouched vault scored 0 `okf-frontmatter` failures; after one `--fix` pass it scored 13, all of them files the tool created and none of them files the vault authored. (tested)

**Third effect, not tested.** `inbox/` is the one vault folder name llm-wiki claims, with opposite semantics: it is a consumable drop zone, and step 3 of `/wiki:ingest --inbox` is "Move each processed file to inbox/.processed/ (or delete if user did not pass --keep)". The vault's fleeting captures in `inbox/` would be consumed or deleted by default. (read from `claude-plugin/commands/ingest.md` and `references/ingestion.md`; ingest has no CLI entry point, so this leg was not run)

**Escape hatch: none.** There is no allowlist input of any kind: no config key, no environment variable, no CLI flag, no ignore file. `ROOT_ALLOWED` is a module constant; the only two variations are `HUB_ALLOWED`, selected when `wikis.json` and `topics/` exist and narrower rather than wider, and the union with `GIT_ROOT_META_ALLOWED` when `.git` is present, which covers conventional VCS and project files only. The only mitigation is to never point the tool at the vault root.

### Q5. Index: `_index.md`, everywhere, with no frontmatter

The tool writes `_index.md`, not `index.md`, at the wiki root and in every managed directory: `raw/`, the five `raw/<type>/` folders, `wiki/`, the four `wiki/` article folders, `output/`, and lazily `inventory/*` and `datasets/*`. `regenerate_directory_index()` picks a renderer by a declared contract (`raw-root`, `wiki-root`, `inventory-root`, `datasets-root`, `output-root`, `dataset-root`, `direct-files`) and overwrites the file wholesale.

None of them carries frontmatter. `render_direct_file_index`, `render_category_pointer_index`, `render_inventory_index` and `render_output_index` all begin with a `#` heading line and no `---` block. Tested: `wiki/concepts/_index.md` after a fix run reads `# Concepts Index`, then a "Generated by local llm-wiki lint." line, a "Last updated" line, a `## Contents` heading and a four-column table. `schema.md` does carry frontmatter (`title`, `schema_state`, `created`, `updated`, `summary`) but no `type`.

Under the vault's rules `_index.md` is not a reserved name, since `check_reserved` knows only `index.md` and `log.md`, so each one is an ordinary note with no `type` and fails the OKF gate. The inverse rule collides head-on: llm-wiki treats any `.md` under `wiki/` as a content document, so a frontmatter-free `wiki/concepts/index.md` drew `Critical: Markdown file is missing YAML frontmatter`, `--fix` could not repair it (it recurred five times in the post-fix findings), and the regenerated `wiki/concepts/_index.md` added the row `| [index](index.md) |  |  |  |`. The vault's own `check_reserved` called that same file `MATCHED`. Both directions verified. (tested)

Patching `type:` into these files does not stick: `regenerate_directory_index` rewrites them from scratch on any `--fix` that finds a missing entry or a dead link, and `create_or_update_coverage_reference` likewise overwrites its page wholesale.

Two findings never clear. The master root `_index.md` issue is reported with `fixable=True`, but no code path ever creates the file, since init is agentic-only. `config.md` is critical and not marked fixable at all. Both persisted through the fix run, so lint at a vault root cannot reach exit 0 no matter how many `--fix` passes run. (tested)

## 5. Where the per-source summary could live

The spec (§4.4) leaves this open and names two candidates. The probes establish a third, and price all three.

| Option                            | claude-obsidian                                                                                                         | llm-wiki                                                                                                                | One file per source?                                                                    | Vault type rule                                                                                                                |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| The literature note's free region | Not reachable. `ingest` is scope-refused from `literatures/`, and the engine has only whole-file `create` and `replace` | Not reachable. No region concept exists; `literatures/` is never parsed, and raw placement is enforced by `shutil.move` | Yes, if a splice step outside the tool is built and the tool's own page is then deleted | Satisfied: the note already carries `type: literature`                                                                         |
| A folder of the tool's choosing   | `wiki/sources/<Title>.md`, plus `.raw/captured/<sha>.<ext>`, plus two ledger records                                    | `raw/<one of five fixed names>/<date>-<slug>.md`, which is the source page and the raw store at once                    | No. Two artifacts at minimum for claude-obsidian, plus a mirror-in copy for llm-wiki    | Passes for both page kinds, since `wiki/` and `raw/` derive `None`. Fails for `.raw/captured/*.md`, which carry no frontmatter |
| A caller-named folder             | Only inside `wiki/`, so `wiki/sources/` can be renamed but not moved out of `wiki/`                                     | Not at all. `RAW_TYPES` and the `raw/` root are module constants                                                        | No                                                                                      | Any non-empty type passes wherever the folder is not one of the four the vault maps                                            |

**The literature note's free region.** This is the option the vault would prefer and the one neither tool supports. For claude-obsidian the block is doubled: the write-scope validator refuses `literatures/` for `ingest`, and even if it did not, a `replace` carries whole-file content and a whole-file expected hash, so applying one would rewrite the machine-owned managed region along with the free region. That is the exact boundary the managed region exists to protect. For llm-wiki the block is simpler and just as firm: the tool has no notion of writing part of a file, and `literatures/` sits outside `is_schema_checked_path`, so the tool does not read those files at all. Taking this option means building the splice outside the tool, in capture or in a step after compile, and then deciding what happens to the page the tool wrote. Deleting it costs claude-obsidian its wikilinks, its index catalog entry and its ledger locator, and the tool's own lint would report `dead_links` and `stale_index_entries` on the next run. Deleting it costs llm-wiki nothing structurally, because the raw page is the source of the compile, but then there is no compile input, so the mirror has to stay. Either way the one-file-per-source property survives only in the vault's own tree, not in the tool's.

**A folder of the tool's choosing.** This is the cheapest option in mechanism and the most expensive in file count. claude-obsidian writes `wiki/sources/<Title>.md` and a content-addressed copy at `.raw/captured/<sha>.<ext>` in the same transaction, so two files per source before the ledgers, and the copy carries no frontmatter, so it fails the `type` rule wherever the vault's walker reaches it. Since the vault's verify leg rglobs the whole tree and skips only `.git`, it reaches `.raw/`. Whether that file is also staged, and therefore whether the commit is actually blocked as opposed to reported, depends on `.gitignore`, and adopt's shipped `.gitignore` does not ignore `.raw/`. llm-wiki's raw page is the source page, so the count is one file inside the tool's tree, but it is a mirror of a literature note that already exists, so two per source across both trees. Both are compatible with the vault's `type` rule for the page itself, because `wiki/` and `raw/` derive no expected type and any non-empty value passes.

**A caller-named folder.** Neither tool offers this in the sense the vault wants. claude-obsidian's per-kind folder names are genuinely configurable and were confirmed to round-trip through `mode get`, but only within `wiki/`: `wiki/synthesis/` is reachable and top-level `synthesis/` is refused by four independent checks. llm-wiki offers nothing at all inside the root, and pointing the root at `synthesis/` produced `synthesis/raw/`, `synthesis/wiki/` and `synthesis/output/` and quarantined the page already there. The version of this option that does work is to accept the tool's folder and rename it inside the tool's own root, which does not answer the vault's question, because the vault's structure check derives a type from top-level folder names only.

**The one thing that transfers cleanly.** Cross-folder linking already works for claude-obsidian: a `wiki/` page can carry `[[smith-2024-attention]]` and it resolves into `literatures/` with no dead link. For llm-wiki a wiki article can cite `../../literatures/x.md` in its `sources` list and lint says nothing, but coverage counting only sees `raw/`, so the source stays in the backlog. Reading across the boundary is possible in both. Writing across it is not.

## 6. Rung, once layout is accounted for

Both probes land on `adapt`, and the shape of the adapt differs. The spec's §4.3 proposal rests on the claim that the only things that must fit this vault are configuration; both probes contradict that claim, for different reasons.

|                                                 | claude-obsidian                                                                   | llm-wiki                                                                                                  |
| ----------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| What blocks as-is adoption                      | The wiki root name is fixed in four places, and no region-aware write mode exists | The whole interior layout is module constants, and `--fix` writes into the vault                          |
| Where the change would go                       | Inside the tool: scope validators and the transaction engine                      | Around the tool: a sidecar root plus shims on both sides                                                  |
| What the vault must accept unchanged            | Five extra required frontmatter fields on every page that moves under `wiki/`     | The five-value `type` enum on raw pages, and `type`-less machine pages                                    |
| Whether a fix pass can be run at the vault root | Yes; lint writes nothing and repair is scope-locked to `wiki/`                    | No; one `--fix` pass moves the root `index.md` and takes the `okf-frontmatter` failure count from 0 to 13 |

**claude-obsidian: adapt, by forking named checks inside the engine.** The vault contract needs `synthesis/` and `literatures/` as write targets, and every content operation is scope-locked to a directory literally named `wiki`, proved four ways: `validate_wiki_folder` rejects `synthesis/`, the transaction scope validator rejects `generic` writing to `synthesis/` and `ingest` writing to `literatures/`, `_wiki_location` scans zero pages when pointed at `synthesis/`, and both symlink routes are closed. The configurable subfolder names are a decoy, because they are configurable only within the fixed root. Separately, the two lints impose contradictory and unsuppressable requirements on `wiki/index.md`, and each was run and each failed it. A concrete adapt forks at minimum `mode_config.validate_wiki_folder` and `validate_wiki_route`, `transaction._validate_operation_write_scope` (both the `wiki/` prefix tests and the `('.raw','captured')` capture scope), `lint_engine._wiki_location`, `paths.is_initialized_vault`, `templates/vault/wiki/index.md`, the application of `REQUIRED_FRONTMATTER_FIELDS` to `index.md`, and, for the free-region goal, a new write mode with matching journal, hashing and recovery semantics. What is already as-is: the tool runs cleanly against a research-vault-shaped directory, `adopt` accepts the foreign layout without complaint, lint provably leaves `literatures/`, `inbox/` and `log/` byte-identical, and `type` is already a required key, so the vault's rule 2 is satisfied by construction on every page the tool writes.

**llm-wiki: adapt, by keeping the tool outside the vault and shimming both sides.** The layout is not configurable past the root, the tool's own reference says the physical layout is fixed, and pointing the root at `synthesis/` scaffolded a tree there rather than adopting the folder. Pointed at the vault root, `--fix` quarantines the root `index.md` into `inbox/.unknown/` and scaffolds 13 frontmatter-free `_index.md` files plus `schema.md`. `literatures/`, `synthesis/` and `log/` are left byte-identical but generate permanent unknown-directory warnings, so lint cannot exit 0, and neither can it on its own terms, since the master `_index.md` is marked fixable with no fix path and `config.md` is unfixable. The vault's one-file-per-source goal has no counterpart: `raw/<type>/<slug>.md` is the source, placement is enforced by `shutil.move` keyed on `type`, and `type: literature` there is a hard unfixable enum violation. Every machine-written page lacks `type`, and patches do not stick, because `regenerate_directory_index` and `create_or_update_coverage_reference` rewrite their files wholesale on each `--fix`. The adapt shape is an llm-wiki root outside the vault, a mirror-in step from literature note to `raw/papers/*.md` carrying `type`, `source` and `ingested`, and a copy-out step that adds `type: synthesis` and drops `_index.md`, `schema.md` and `config.md`. The genuinely as-is bit is that `type: synthesis` survives on a wiki article: extra frontmatter keys are tolerated and preserved through auto-repair.

## 7. Surprises and open questions

### Findings that contradict the consuming spec

- **§4.3 says the two things that must fit are configuration, naming `.claude-obsidian.json` for the source inbox directory and the vault root.** The probe found that `paths.py` parses only `schema` and `vault`. The keys `role`, `source_inbox` and `legacy_raw` are written by `init` and `adopt` and read by nothing in the package. Tested: setting `legacy_raw: "sources"` and `source_inbox: "literatures"` and re-running `capture plan` still enumerated `inbox/` and still planned `.raw/captured/`. They look exactly like the layout knobs a caller would reach for first, and they are inert. The working inbox knob is `--inbox <dir>` or the `inbox` key in `.vault-meta/capture/config.json`.
- **§4.4 says the tool's `.raw/captured/` store "is gitignored with the cache".** The probe found that the `.gitignore` `adopt` writes ignores `.vault-meta/` but not `.raw/`, and that `adopt` skips an existing `.gitignore` without `--force` (`build_vault_bundle` has `if adopt and not force: continue` on a hash mismatch). The real vault already has a `.gitignore`, so it would never receive the tool's rules at all, which also leaves `.vault-meta/` tracked. The transaction journals under `.vault-meta/transactions/*/bundle.json` embed full page bodies verbatim, so every applied operation would commit a second copy of its own content.

### Findings that close open items

- **§4.3 tracer 2, that `wiki-lint` leaves `literatures/` untouched:** confirmed. The lint engine performs no filesystem writes at all, verified byte-for-byte with `sha256sum` before and after, and repair is scope-locked to `wiki/`. The second half of the tracer, that a source page can be reached from a citation key, is confirmed in the read direction: `[[smith-2024-attention]]` on a `wiki/` page resolved into `literatures/` with no dead link.
- **§8 item 7, whether compiled pages carry a `type` the vault's structure check accepts:** answered for both. claude-obsidian carries `type` on every page and the vault derives no expected value for `wiki/`, so any value passes. llm-wiki carries `type` on raw pages only, enum-locked, and no `type` at all on wiki article pages or on any file its lint writes. The corollary the item anticipated is real and points one way: adding `wiki/` to `_FOLDER_TYPES` and demanding one derived value would fail every claude-obsidian page except the one kind whose `type` happened to match.

### Surprises

- **claude-obsidian's `capture` treats the vault's `inbox/` as its own.** `capture plan` with no arguments planned to copy every file in the vault's `inbox/`, the vault's recorded fleeting exemption, into `.raw/captured/<sha>.md`. Applied, both fleeting notes were duplicated as untyped markdown. It is a name collision: both projects independently chose `inbox`. The fix is a flag that nothing prompts you to pass.
- **llm-wiki's `inbox/` collision is destructive rather than duplicating, and read rather than run.** The tool treats `inbox/` as a consumable drop zone, and `/wiki:ingest --inbox` step 3 moves each processed file to `inbox/.processed/` or deletes it when `--keep` is absent.
- **claude-obsidian's `capture` contradicts itself between plan and apply.** With `raw_store: "sources"`, `plan` emitted `sources/captured/<sha>.md` and `apply` refused it. The config surface advertises a knob the write-scope validator forbids.
- **claude-obsidian's `adopt` accepts literally any directory.** No `.obsidian/`, no `wiki/`, no markdown: a folder containing only `literatures/a.md` was accepted and the full bootstrap plan was emitted. The sentinel check is bypassed on the explicit-path adopt route, and `adopt` never maps the existing layout, it writes its own tree beside it.
- **llm-wiki's `--fix` is a net negative for the vault's gate.** The untouched vault scored 0 `okf-frontmatter` failures; after one pass it scored 13, all of them files the tool created.
- **Both tools disagree with the vault about `index.md`, in opposite directions.** claude-obsidian's `wiki/index.md` must carry six frontmatter fields and the vault requires nested indexes to carry none. llm-wiki calls a frontmatter-free `index.md` under `wiki/` a critical and lists it as a content row in the regenerated `_index.md`, while the vault requires exactly that file to be frontmatter-free.
- **llm-wiki's `append_lint_log` writes a log heading the vault rejects.** It appends `## [2026-09-05] lint | local command: ...` to an existing root `log.md`; `structure._log_shape_problems` rejects that verbatim as a `non-date second-level heading`. Verified by planting a `log.md`, running `--fix`, and feeding the result to the vault's checker.
- **`LLM_WIKI_CONFIG_DIR` looks like a configuration escape hatch and is not one.** It relocates only the adapter registry; the hub config path is hardcoded in `resolve_hub`.
- **llm-wiki has a deployment hazard.** `lint --fix` with no path argument falls back to `cwd/.wiki`, then to the hub, then to `~/wiki`, so running it from inside a checkout with no explicit path would scaffold a wiki tree wherever that resolves. Every probe run passed an explicit `/tmp` path.

### Open questions

1. Whether claude-obsidian's `wiki/log.md` stays conformant to the vault's `§9` log shape once the skills start appending LLM-drafted entries. The shipped template passes; no deterministic heading format is specified anywhere in the repository. Read, not run, and it can only be settled by driving the LLM leg.
2. Whether the `.raw/captured/*.md` copies block the commit or merely appear in the report. The vault's verify leg walks them (it skips only `.git`) and `okf-frontmatter` is commit-closing, but `verify` is invoked with `--git-base` and `--git-candidate index`, and whether that narrows the reported set to staged paths was not probed.
3. What the shape of the compile input file should be, given that claude-obsidian's per-source page is drafted by an LLM from whatever lands in the inbox. The page shape in §3 Q2 is read from templates and one worked example, not from a driven run.
4. Whether llm-wiki's compile step, which was not run, writes anything beyond concept, topic and reference pages and the coverage reference. Only the deterministic writers were exercised.
5. Whether either tool's ledger or coverage tracking can be pointed at a citation key rather than at a content hash or a `raw/` path, which is what would let a compiled page be traced back to `literatures/<citation key>.md`.
